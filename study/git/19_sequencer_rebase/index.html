rebase는 커밋을 옮기지 않는다

sequencer 해부 — todo list · apply/merge 백엔드 · patch-id · 중단과 재개

Part 1: "옮긴다"는 착각

rebase는 커밋을 다른 브랜치 위로 옮기는 것 아닌가요?

커밋 객체는 불변입니다(02편). 옮길 수가 없습니다. rebase가 실제로 하는 일은 "기존 커밋들의 변경 내용을 뽑아내, 새 base 위에서 똑같은 변경을 적용해 새 커밋들을 만드는 것"입니다.

rebase 전
main: A←B←C
feature: A←B←D←E
→
rebase 후
main: A←B←C
feature: A←B←C←D'←E'
→
D와 E는?
디스크에 그대로 존재. 아무도 안 가리킬 뿐. reflog가 기억함

D′은 D와 내용은 같지만 다른 객체입니다. 부모가 달라졌으므로(B → C) 커밋 OID가 반드시 달라집니다. 05편에서 본 "커밋 OID는 모든 바이트에 의존한다"의 직접적 귀결입니다.

이것이 "공유 브랜치를 rebase하지 마라"의 근거입니다. 동료가 D를 가지고 작업 중인데 내가 D′을 push하면, 동료 입장에서는 D와 D′이 서로 무관한 두 커밋입니다. 다음 pull에서 같은 변경이 두 번 들어오거나 대규모 충돌이 납니다.

🎯 비유로 이해하기

rebase는 이사가 아니라 필사(筆寫)입니다.

원고를 새 공책에 옮겨 적는 것과 같습니다. 글자는 같지만 새 공책의 새 종이에 쓴 것이고, 원래 공책은 그대로 남아 있습니다. 누군가 옛 공책의 페이지 번호를 참조하고 있었다면, 그 참조는 새 공책에서 통하지 않습니다.

그럼 rebase가 하는 일을 plumbing으로 풀면 어떻게 되나요?
bash — rebase를 손으로 재현
# feature(D, E)를 main(C) 위로 옮긴다
$ git checkout --detach main           # C에 HEAD를 두고
$ git cherry-pick D                    # D의 변경을 적용 → D' 생성
$ git cherry-pick E                    # E의 변경을 적용 → E' 생성
$ git branch -f feature HEAD           # feature를 E'로 이동
$ git checkout feature

# 이것이 rebase의 전부다.
# 즉 rebase = "detach + cherry-pick 반복 + 브랜치 ref 이동"

그래서 rebase와 cherry-pick이 같은 엔진을 공유합니다. 바로 sequencer(sequencer.c)입니다. revert도 같은 엔진을 씁니다 — "변경을 거꾸로 적용하는 cherry-pick"이기 때문입니다.

Part 2: sequencer와 todo list

sequencer는 어떤 구조인가요?

"할 일 목록을 읽어 한 줄씩 실행하고, 진행 상태를 디스크에 기록하는 상태 기계"입니다. 중단·재개·취소가 가능해야 하므로 상태를 반드시 파일로 남깁니다.

.git/rebase-merge/ 디렉토리
$ git rebase -i main
$ ls .git/rebase-merge/
git-rebase-todo        # 남은 할 일 (앞에서부터 소비)
done                   # 이미 끝낸 항목들
onto                   # 새 base의 OID
head-name              # 원래 브랜치 이름 (refs/heads/feature)
orig-head              # rebase 시작 시점의 HEAD (취소용)
interactive            # 대화형 여부 표식
msgnum / end           # 진행률 (3/7 같은 표시용)

$ cat .git/rebase-merge/git-rebase-todo
pick d4e5f6a feat: 로그인 폼 추가
pick a7b8c9d fix: 검증 로직 수정
pick 1a2b3c4 refactor: 중복 제거

todo에 쓸 수 있는 명령은 소스에 표로 정의되어 있습니다.

sequencer.c — todo_command_info
} todo_command_info[] = {
        [TODO_PICK]       = { 'p', "pick" },
        [TODO_REVERT]     = { 0,   "revert" },
        [TODO_EDIT]       = { 'e', "edit" },
        [TODO_REWORD]     = { 'r', "reword" },
        [TODO_FIXUP]      = { 'f', "fixup" },
        [TODO_SQUASH]     = { 's', "squash" },
        [TODO_EXEC]       = { 'x', "exec" },
        [TODO_BREAK]      = { 'b', "break" },
        [TODO_LABEL]      = { 'l', "label" },
        [TODO_RESET]      = { 't', "reset" },
        [TODO_MERGE]      = { 'm', "merge" },
        [TODO_UPDATE_REF] = { 'u', "update-ref" },
        [TODO_NOOP]       = { 0,   "noop" },
        [TODO_DROP]       = { 'd', "drop" },
        [TODO_COMMENT]    = { 0,   NULL },
};
명령동작언제 쓰나
pick (p)커밋을 그대로 적용기본
reword (r)적용 후 메시지만 편집오타·컨벤션 수정
edit (e)적용 후 멈춤. 내용을 고치고 --continue커밋 분할, 내용 수정
squash (s)이전 커밋에 합치고 메시지 편집WIP 커밋 정리
fixup (f)이전 커밋에 합치되 메시지 버림--autosquash와 조합
drop (d)커밋 제거실수로 들어간 커밋 제거
exec (x)임의의 셸 명령 실행커밋마다 테스트 돌리기
break (b)그 지점에서 일시 정지중간 점검
label/reset/merge브랜치 구조 재현--rebase-merges에서 자동 생성
update-ref (u)그 지점에서 지정 ref 갱신스택형 브랜치를 한 번에 rebase

update-ref가 최근 추가된 강력한 기능입니다. feature-A → feature-B → feature-C처럼 쌓아 올린 브랜치들을 git rebase --update-refs 한 번으로 모두 이동시킵니다. 각 브랜치를 따로 rebase하던 번거로움이 사라집니다.

bash — exec와 update-refs 활용
# 모든 커밋에서 테스트가 통과하는지 검증 (bisect 가능한 히스토리 보장)
$ git rebase -i --exec 'make test' main

# 생성된 todo
pick d4e5f6a feat: A
exec make test
pick a7b8c9d fix: B
exec make test

# 스택형 브랜치를 한 번에
$ git config --global rebase.updateRefs true
$ git rebase main feature-C        # feature-A, feature-B도 함께 이동

# autosquash: "fixup! <제목>" 커밋을 자동 배치
$ git commit --fixup=a7b8c9d
$ git rebase -i --autosquash main  # fixup 커밋이 대상 바로 뒤로 자동 정렬
중단과 재개는 어떻게 동작하나요?

상태 파일이 전부입니다. 각 명령의 의미가 명확해집니다.

명령하는 일
--continue현재 항목을 커밋하고, git-rebase-todo의 다음 줄로 진행
--skip현재 항목을 버리고 다음 줄로
--abortorig-head로 완전 복구. 상태 디렉토리 삭제
--quit상태 디렉토리만 지우고 현재 HEAD를 유지 (위험)
--edit-todo남은 todo를 편집기로 열어 수정
bash — rebase 중 상태 직접 확인
$ git rebase -i main
# 충돌 발생, 멈춤

$ cat .git/rebase-merge/done            # 여기까지 했다
pick d4e5f6a feat: A
pick a7b8c9d fix: B

$ cat .git/rebase-merge/git-rebase-todo # 여기부터 남았다
pick 1a2b3c4 refactor: C

$ cat .git/rebase-merge/orig-head       # 취소하면 돌아갈 곳
e7f8a9b0c1d2...

# 남은 계획을 지금 바꿀 수 있다
$ git rebase --edit-todo

# 완전히 없던 일로
$ git rebase --abort
$ git rev-parse HEAD                     # = orig-head

rebase 중에 "내가 지금 어디쯤인가"를 잃어버렸다면 .git/rebase-merge/를 직접 들여다보는 것이 가장 빠릅니다. git status도 이 정보를 요약해 보여 주지만, 원본 파일이 더 정확합니다.

Part 3: 두 가지 백엔드 — apply와 merge

rebase에 백엔드가 두 개라는 게 무슨 뜻인가요?

"변경을 어떻게 적용하는가"의 방식이 둘입니다. Git 소스의 열거형이 그대로 보여 줍니다.

builtin/rebase.c
enum rebase_type {
        REBASE_UNSPECIFIED = -1,
        REBASE_APPLY,
        REBASE_MERGE
};
구분apply 백엔드merge 백엔드 (현재 기본)
방식 커밋을 패치(텍스트)로 뽑아 git apply로 붙임 3-way 머지(merge-ort)로 적용
기반 명령format-patch + amsequencer + merge-ort
상태 디렉토리.git/rebase-apply/.git/rebase-merge/
rename 처리약함 (패치는 경로 기준)강함 (rename 감지 활용)
충돌 품질패치 적용 실패 시 정보가 적음base를 알기에 3-way 충돌 마커 제공
대화형/exec불가가능
속도단순 케이스에서 빠를 수 있음rename 캐싱으로 대개 더 빠름
지정--apply, -C<n>, --whitespace 사용 시기본. -i, -x, --rebase-merges 사용 시 강제

Git 2.26부터 merge 백엔드가 기본입니다. 설정 문서가 밝히듯 "merge 백엔드가 apply 백엔드의 남은 기능을 모두 갖추면 이 설정은 쓸모없어질 것"이라고 명시되어 있습니다 — apply는 단계적으로 퇴역 중입니다.

백엔드가 바뀌면서 동작이 미묘하게 달라진 부분이 있습니다. 대표적으로 apply 백엔드는 --whitespace=fix 같은 패치 레벨 옵션을 지원하지만 merge 백엔드는 지원하지 않습니다. 옛 스크립트가 이런 옵션을 쓰면 자동으로 apply 백엔드로 넘어갑니다.

"이미 적용된 커밋"을 rebase가 건너뛰는 건 어떻게 아는 건가요?

patch-id입니다. 커밋 OID가 아니라 변경 내용의 해시로 동일성을 판단합니다.

patch-id란
커밋의 diff에서
  - 공백을 정규화하고
  - 줄 번호(@@ 헤더)를 제거하고
  - 컨텍스트를 정리한 뒤
해시한 값.

⇒ 같은 변경이면 어느 base 위에서 적용되었든 같은 patch-id
   (커밋 OID는 다르지만)
bash — patch-id 직접 확인
$ git show D | git patch-id
9f8e7d6c5b4a3210...  d4e5f6a...
   ↑ patch-id           ↑ commit OID

$ git show D-prime | git patch-id
9f8e7d6c5b4a3210...  1a2b3c4...
   ↑ 같은 patch-id!     ↑ 다른 commit OID

# upstream에 이미 있는 커밋 찾기
$ git cherry -v main feature
+ a7b8c9d fix: 아직 main에 없음
- d4e5f6a feat: main에 이미 있음 (patch-id 일치)
# '+'는 미적용, '-'는 이미 적용됨

이 덕분에 rebase는 "upstream에 이미 cherry-pick된 내 커밋"을 자동으로 건너뜁니다. 메인테이너가 내 패치를 먼저 적용했더라도 rebase 시 중복이 생기지 않습니다.

단, patch-id는 변경 내용이 정확히 같을 때만 일치합니다. cherry-pick 과정에서 충돌을 해결하며 내용이 조금이라도 달라졌으면 다른 patch-id가 되어 중복이 발생합니다. --no-reapply-cherry-picks/--reapply-cherry-picks로 이 동작을 제어할 수 있습니다.

15편의 한계와 연결됩니다. git branch --merged는 조상 관계로 판정하므로 squash/rebase된 브랜치를 잡지 못합니다. 그럴 때는 git cherry(patch-id 기반)를 쓰는 것이 답입니다.

Part 4: 실전 — 안전한 히스토리 재작성

rebase 중 사고가 났을 때 복구 방법은요?

reflog가 전부입니다(11편). rebase는 새 커밋을 만들 뿐 옛 커밋을 지우지 않으므로, OID만 알면 완전 복구됩니다.

bash — rebase 사고 복구
# 1) rebase가 진행 중이라면 — 가장 쉬움
$ git rebase --abort

# 2) 이미 끝나 버렸다면 — reflog에서 rebase 직전을 찾는다
$ git reflog
a1b2c3d HEAD@{0}: rebase (finish): returning to refs/heads/feature
a1b2c3d HEAD@{1}: rebase (pick): refactor: C
f7d3c0e HEAD@{2}: rebase (pick): fix: B
c9d0e1f HEAD@{3}: rebase (start): checkout main
e5f6a7b HEAD@{4}: commit: refactor: C     ← rebase 직전 상태

$ git reset --hard e5f6a7b
# 또는
$ git reset --hard HEAD@{4}

# 3) 브랜치별 reflog로 더 정확히
$ git reflog show feature
$ git branch feature-backup feature@{1}

# 4) reflog도 없다면 — 미아 커밋 탐색 (20편)
$ git fsck --lost-found --no-reflogs
dangling commit e5f6a7b...
$ git show e5f6a7b

습관 하나로 모든 위험이 사라집니다. 위험한 작업 전에 백업 브랜치를 만드십시오. git branch backup/before-rebase 한 줄이면 됩니다. 41바이트짜리 파일이므로 비용이 없습니다(11편).

팀에서 rebase를 어떻게 운영해야 하나요?

원칙은 단순합니다. "내 브랜치는 rebase, 공유 브랜치는 merge."

상황권장이유
내 feature 브랜치를 최신 main에 맞추기 rebase 히스토리가 선형이 되어 리뷰·bisect가 쉬움
PR을 main에 통합 merge / squash merge 통합 시점이 기록에 남음. 팀 정책에 따름
이미 push한 공유 브랜치 rebase 금지 동료의 히스토리와 갈라짐
내가 혼자 쓰는 브랜치 (push했어도) rebase + --force-with-lease CAS로 동료 작업 덮어쓰기 방지 (11편)
bash — 안전한 재작성 워크플로
# 0) 백업
$ git branch backup/pre-rebase

# 1) 최신 upstream 확보
$ git fetch origin

# 2) rebase (base를 명시 — CI에서도 동일하게 동작, 15편)
$ git rebase origin/main

# 3) 검증: 변경 내용이 보존되었는지 확인
$ git diff backup/pre-rebase HEAD        # 비어 있어야 정상!
# (커밋 구성은 달라도 최종 트리는 같아야 한다)

# 4) 각 커밋이 빌드되는지 (선택이지만 강력 권장)
$ git rebase -i --exec 'make test' origin/main

# 5) 안전한 force push
$ git push --force-with-lease origin feature

# 6) 문제없으면 백업 제거
$ git branch -D backup/pre-rebase

3번의 git diff backup HEAD가 비어 있어야 한다는 검증이 특히 유용합니다. rebase는 커밋 구성을 바꾸지만 최종 트리는 그대로여야 합니다. 이 diff에 내용이 나오면 충돌 해결에서 무언가를 잃어버린 것입니다.

대규모 히스토리 재작성(git filter-repo로 민감 정보 제거 등)은 차원이 다릅니다. 모든 커밋 OID가 바뀌므로 팀 전원이 다시 클론해야 하고, 태그·PR·CI 설정·commit-graph가 전부 영향을 받습니다. 반드시 사전 공지하고 정해진 시각에 수행하십시오.

bash — 재작성 후 정리
# 히스토리 대규모 재작성 후
$ git reflog expire --expire=now --all
$ git gc --prune=now --aggressive
$ git commit-graph write --reachable --changed-paths   # 낡은 항목 제거 (14편)

# 팀원은 다시 클론하는 것이 가장 안전하다.
# 굳이 기존 클론을 쓰려면:
$ git fetch --all
$ git reset --hard origin/main
$ git reflog expire --expire=now --all && git gc --prune=now

📌 핵심 정리

  • rebase는 커밋을 옮기지 않고 새로 만든다. 부모가 달라지므로 OID가 반드시 바뀌며, 원래 커밋은 디스크에 남아 reflog로 복구 가능하다. 공유 브랜치 rebase가 위험한 이유가 이것이다.
  • rebase = detach + cherry-pick 반복 + 브랜치 ref 이동이고, 엔진은 sequencer다. rebase·cherry-pick·revert가 같은 구현을 공유한다.
  • 상태는 .git/rebase-merge/에 전부 파일로 남는다. git-rebase-todo(남은 일), done(끝난 일), orig-head(취소 지점). --continue/--skip/--abort의 의미가 이 파일들로 설명된다.
  • 백엔드는 apply(패치 적용)와 merge(3-way, 현재 기본) 둘이다. merge 백엔드는 rename 감지와 3-way 충돌 마커를 제공하고 -i/exec/--rebase-merges를 지원하며, apply는 단계적으로 퇴역 중이다.
  • "이미 적용된 커밋" 판정은 patch-id(변경 내용의 해시)로 한다. squash/rebase된 브랜치는 조상 관계가 없으므로 --merged 대신 git cherry로 확인해야 한다. 재작성 전 백업 브랜치 생성과 --force-with-lease가 안전 습관이다.
