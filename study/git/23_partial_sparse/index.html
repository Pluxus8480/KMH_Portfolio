Part 1: 세 가지 규모 축

거대 저장소에서 Git이 느려지는 원인은 하나가 아니라고 하던데요?

Git 문서 sparse-index.adoc이 워킹 디렉토리의 세 가지 규모 축을 정의합니다. 이 구분이 처방을 나눕니다.

축질문비용이 드는 작업
HEADHEAD에 파일이 몇 개인가?인덱스 파싱/쓰기, 트리 순회
Populated희소 체크아웃 범위 안에 몇 개인가?워킹 트리 스캔, 체크아웃
Modified사용자가 몇 개를 수정했나?diff, 커밋

문서가 지적하듯 이 셋은 크기 순서가 정해져 있습니다. 수정한 파일 ≤ 채워진 파일 ≤ HEAD의 파일입니다. 문제는 극단적 불균형이 생길 때입니다.

문서의 예시입니다. "HEAD에 수백만 개의 경로가 있는데 populated set은 수만 개뿐이라면, git status와 git add가 O(Populated)가 아니라 O(HEAD) 연산에 지배당한다. 주된 비용은 인덱스를 파싱하고 다시 쓰는 것이며, 인덱스는 대부분 SKIP_WORKTREE로 표시된 HEAD의 파일들로 채워져 있다."

즉 "파일을 받지 않았는데도 인덱스에는 다 들어 있어서 느린" 상황입니다. 여기서 세 가지 기술이 각각 다른 축을 공략합니다.

(다운로드 · 디스크)
+
희소 체크아웃
Populated를 줄임
(워킹 트리 파일 수)
+
희소 인덱스
인덱스 엔트리 수를 줄임
(O(HEAD) → O(Populated))
🎯 비유로 이해하기

백화점 전체 재고를 다루는 상황입니다.

부분 클론은 "창고에서 상품 실물을 다 가져오지 않고, 필요할 때 주문하는 것"입니다.

희소 체크아웃은 "매장 진열대에 내 담당 코너 상품만 꺼내 두는 것"입니다.

희소 인덱스는 "재고 장부에서 남의 코너는 '3층 전체'라고 한 줄로 요약하는 것"입니다. 앞의 둘을 해도 장부가 수백만 줄이면 매번 장부를 읽고 쓰는 것만으로 느립니다.

Part 2: 부분 클론 — promisor remote

부분 클론은 무엇을 안 받는 건가요?

Git 문서 partial-clone.adoc이 동기를 명확히 밝힙니다. "clone과 fetch에서 Git은 저장소의 전체 내용과 히스토리를 다운로드한다. 극단적으로 큰 저장소에서는 clone이 수 시간(또는 며칠)이 걸리고 100GiB 이상을 소비한다."

불필요한 것의 예로 문서가 드는 두 가지입니다.

  1. 작업 영역 밖의 파일 — "디렉토리 50만 개, 커밋마다 파일 350만 개인 저장소에서, 사용자가 좁은 '콘(cone)'만 필요하다면 많은 객체를 받지 않아도 된다"
  2. 큰 바이너리 에셋 — "머지할 수 없는 대형 빌드 산출물의 과거 버전을 전부 받을 필요 없이, 실제로 참조되는 버전만 받으면 된다"

핵심 개념은 promisor remote입니다. 문서의 정의: "나중에 누락된 객체를 제공해 줄 수 있는 원격을 promisor remote라 부른다. 요청하면 객체를 보내 주겠다고 약속(promise)하기 때문이다."

필터 종류 (rev-list-options.adoc)
--filter=blob:none          모든 blob을 생략 (커밋·트리는 전부 받음)
--filter=blob:limit=<n>     <n> 이상 크기의 blob 생략. k/m/g 접미사 가능
                            (blob:limit=1k = blob:limit=1024)
--filter=tree:0             모든 트리를 생략 (가장 공격적)
--filter=object:type=<t>    해당 타입만 남기고 생략
--filter=sparse:oid=<blob>  희소 체크아웃 명세 파일을 기준으로 필터
--filter=combine:A+B        여러 필터 조합
필터받는 것적합한 용도
blob:none 모든 커밋 + 모든 트리 일상 개발. git log·diff의 경로 정보가 살아 있고, 파일 내용만 필요 시 받음
blob:limit=10m 10MB 미만 blob까지 대형 에셋이 섞인 저장소
tree:0 커밋만 CI 빌드 등 히스토리 메타데이터만 필요한 경우
bash — 부분 클론
$ git clone --filter=blob:none https://github.com/torvalds/linux
# 커밋·트리는 전부, blob은 현재 체크아웃에 필요한 것만

$ cat .git/config
[remote "origin"]
	url = https://github.com/torvalds/linux
	fetch = +refs/heads/*:refs/remotes/origin/*
	promisor = true                    # ← "이 원격이 나머지를 약속했다"
	partialclonefilter = blob:none
[extensions]
	partialClone = origin              # ← 어느 원격이 promisor인가

# 옛 파일 내용이 필요해지면 자동으로 받아 온다
$ git show HEAD~1000:kernel/fork.c
remote: Enumerating objects: 1, done.
# ↑ 이 순간 네트워크 요청이 발생한다

# 미리 받아 두기 (오프라인 대비)
$ git fetch --refetch --filter=blob:none origin

문서가 분명히 경고합니다. "부분 클론을 쓰려면 사용자가 온라인이어야 하고 promisor remote가 on-demand fetch에 응답 가능해야 한다." 오프라인 환경이나 네트워크가 불안정한 곳에서는 git log -p 한 번이 수천 번의 개별 요청을 일으킬 수 있습니다.

shallow clone과는 뭐가 다른가요?
구분shallow (--depth)부분 클론 (--filter)
자르는 축히스토리의 깊이 (커밋 수)객체의 종류 (blob/tree)
남는 것최근 N개 커밋의 완전한 스냅샷전체 커밋 그래프 + 필요한 객체만
git logN개까지만 보임전체 히스토리 조회 가능
git blame/bisect제한적 또는 불가가능 (필요 객체를 받아 옴)
복구--unshallow로 전체 받기on-demand로 점진적
적합CI (일회성 빌드)일상 개발

shallow는 "과거를 잘라내는" 것이고 부분 클론은 "덩어리를 미루는" 것입니다. CI 빌드에는 shallow가, 개발자 워크스테이션에는 부분 클론이 맞습니다. 14편에서 본 것처럼 shallow는 commit-graph의 세대 번호까지 왜곡하므로, 장기 사용에는 적합하지 않습니다.

Part 3: 희소 체크아웃 — cone 모드

희소 체크아웃은 어떻게 동작하나요?

06편에서 본 skip-worktree 비트가 핵심입니다. 인덱스에는 엔트리가 있지만 "워킹 트리에 없어도 정상"이라고 표시합니다.

bash — 희소 체크아웃
$ git sparse-checkout init --cone
$ git sparse-checkout set services/payment shared/proto

$ ls
services/  shared/            # 나머지 디렉토리는 워킹 트리에 없다

$ git ls-files | wc -l
2847                          # 인덱스에는 여전히 다 있다

$ git ls-files -t | grep '^S' | wc -l
1203847                       # S = skip-worktree 표시된 것들

$ cat .git/info/sparse-checkout
/*
!/*/
/services/
/shared/

cone 모드가 중요합니다. Git 문서는 "core.sparseCheckoutCone으로 활성화되는 cone 모드 패턴은, HEAD의 어떤 파일이 희소 체크아웃 cone에 속하는지 매우 빠르게 판별할 수 있게 해 준다"고 설명합니다.

구분비-cone (레거시)cone 모드 (권장)
패턴임의의 gitignore 스타일 glob디렉토리 경로만
매칭 비용경로마다 모든 패턴 검사 — O(경로 × 패턴)접두사 해시 조회 — 사실상 O(1)
표현력높음 (*.md만 같은 것도 가능)제한적 (디렉토리 단위)
희소 인덱스불가가능

"cone"이라는 이름은 디렉토리 트리에서 잘라낸 원뿔 모양에서 왔습니다. 포함된 디렉토리의 모든 조상 디렉토리도 함께 포함되므로, 루트에서 목표 디렉토리로 퍼져 가는 원뿔 형태가 됩니다. 이 제약 덕분에 "이 디렉토리 전체가 범위 밖"을 판정할 수 있고, 그것이 다음 절의 희소 인덱스를 가능하게 합니다.

skip-worktree를 수동으로 조작하지 마십시오. 06편에서 언급했듯 --assume-unchanged와 혼동하기 쉽고, 희소 체크아웃 명령이 관리하는 상태를 망가뜨립니다. 반드시 git sparse-checkout 명령을 쓰십시오.

Part 4: 희소 인덱스 — sparse directory 엔트리

희소 체크아웃을 해도 느린 이유가 뭔가요?

인덱스는 여전히 HEAD의 모든 파일을 담고 있기 때문입니다. 파일 350만 개짜리 모노레포에서 services/payment/만 체크아웃해도, 인덱스에는 350만 개 엔트리가 그대로 있고 대부분이 skip-worktree로 표시되어 있을 뿐입니다.

git status는 이 인덱스를 전부 파싱하고, git add는 전부 다시 씁니다. 문서의 표현대로 O(Populated)여야 할 작업이 O(HEAD)에 지배당합니다.

해법은 인덱스 포맷을 바꾸는 것입니다. Git 문서: "희소 인덱스는 이 명령들을 O(HEAD)에서 O(Populated)로 바꾸려 한다. 이를 위해 인덱스 포맷을 상당히 변경해야 한다 — sparse directory 엔트리를 추가하는 것이다."

sparse directory 엔트리
[일반 인덱스 — 350만 엔트리]
100644 aaa... 0  services/payment/src/main.go
100644 bbb... 0  services/payment/src/util.go
100644 ccc... 0  services/billing/src/main.go       ← skip-worktree
100644 ddd... 0  services/billing/src/util.go       ← skip-worktree
... (350만 줄)

[희소 인덱스 — 수천 엔트리]
100644 aaa... 0  services/payment/src/main.go
100644 bbb... 0  services/payment/src/util.go
040000 eee... 0  services/billing/              ← 디렉토리 하나로 압축!
                                                     mode 040000, SKIP_WORKTREE,
                                                     경로가 '/'로 끝남,
                                                     HEAD의 트리 OID를 가리킴

06편에서 읽은 인덱스 포맷 문서가 이를 명시합니다. "cone 모드가 활성화되고 extensions.sparseIndex가 켜지면, 인덱스는 희소 체크아웃 정의 밖의 디렉토리에 대한 엔트리를 담을 수 있다. 이 엔트리들은 모드 040000이고, SKIP_WORKTREE 비트를 포함하며, 경로가 디렉토리 구분자로 끝난다."

디렉토리 안의 내용이 필요해지면 그 트리 OID로 트리를 파싱해 펼치면 됩니다. 04편의 트리 객체가 바로 그 정보를 갖고 있기 때문에 가능한 설계입니다.

구현상의 어려움은 없었나요?

문서가 솔직하게 기록합니다. "작성 시점에 sparse-directory 엔트리는 인덱스 포맷과 그 인메모리 자료구조에 대한 기대를 위반한다. 코드베이스에는 모든 인덱스 엔트리를 순회하며 파일만 볼 것이라 기대하는 소비자가 많다. 사실 이 루프들은 스테이징된 모든 파일에 대한 참조를 보리라 기대한다."

해결 방식도 밝힙니다. 한 가지 방법은 인덱스를 로드할 때 sparse-directory 엔트리를 그 안의 파일들로 펼쳐 놓는 것인데, "트리를 파싱하는 것이 인덱스 포맷을 파싱하는 것보다 느리므로 오히려 더 느린 연산"이 됩니다.

전략
희소 인덱스를 있는 그대로 다루도록 명령들을 하나씩 개조
→
미개조 명령
호출 전에 ensure_full_index()로 임시로 펼침 (느리지만 정확)
→
점진적 개선
status, add, commit, checkout, merge... 순서대로 희소 인식 전환

이 방식이 훌륭한 엔지니어링 사례입니다. "전부 고칠 때까지 기다리지 않고, 안전한 폴백(ensure_full_index)을 두고 핵심 경로부터 이득을 본다." 덕분에 git status는 이미 빠르고, 드물게 쓰는 명령은 느리지만 정확하게 동작합니다.

18편에서 본 merge-ort가 인덱스 대신 메모리에서 계산하는 것도 이 흐름의 일부입니다. 희소 인덱스를 펼치지 않고 머지할 수 있어야 했기 때문입니다.

bash — 희소 인덱스 사용과 측정
# 전체 구성: 부분 클론 + cone 희소 체크아웃 + 희소 인덱스
$ git clone --filter=blob:none --sparse https://.../monorepo
$ cd monorepo
$ git sparse-checkout set --cone services/payment shared/proto
$ git config index.sparse true              # 희소 인덱스 활성

# 인덱스 엔트리 수 비교
$ git ls-files | wc -l
2847                                         # 희소 인덱스
$ git -c index.sparse=false ls-files | wc -l
3512094                                      # 전체 인덱스

# 인덱스 파일 크기
$ ls -lh .git/index
-rw-r--r-- 1 me me 412K .git/index           # 희소
# (전체였다면 약 280MB)

# 체감 성능
$ time git status
real	0m0.21s                               # 전: 8.4s

# 디버깅: 어떤 명령이 인덱스를 펼치는지 확인
$ GIT_TRACE2_PERF=1 git <command> 2>&1 | grep ensure_full_index
# 출력이 있으면 그 명령은 아직 희소 인식이 안 된 것

주의할 점들입니다. (1) cone 모드가 필수입니다 — 임의 패턴에서는 "디렉토리 전체가 범위 밖"을 판정할 수 없습니다. (2) extensions.sparseIndex는 repositoryformatversion = 1을 요구하므로 구버전 Git이 거부합니다(22편과 같은 장치). (3) 범위 밖 파일을 실수로 수정하면 희소성이 깨지므로, git sparse-checkout add로 범위를 명시적으로 넓히십시오.

면접 포인트: "모노레포에서 Git이 느린데 어떻게 하겠는가"에는 축을 나눠 답하는 것이 좋습니다. 다운로드/디스크는 부분 클론, 워킹 트리 파일 수는 희소 체크아웃, 인덱스 크기는 희소 인덱스, 커밋 그래프 탐색은 commit-graph + Bloom filter(14편), 객체 조회는 MIDX(10편), 서버의 clone은 비트맵(10편). 병목마다 다른 도구가 있다는 것을 아는 것이 핵심입니다.

📌 핵심 정리

  • 워킹 디렉토리의 규모 축은 HEAD · Populated · Modified 세 가지다. HEAD가 수백만인데 Populated가 수만이면 status/add가 O(Populated)가 아니라 O(HEAD)에 지배당한다.
  • 부분 클론은 promisor remote가 "나중에 주겠다"고 약속한 객체를 미루는 것이다. blob:none이 일상 개발에 가장 실용적이며, 히스토리를 자르는 shallow와 달리 log·blame·bisect가 살아 있다. 대신 온라인이어야 한다.
  • 희소 체크아웃은 skip-worktree 비트로 워킹 트리 파일 수를 줄인다. cone 모드는 패턴을 디렉토리 단위로 제한해 매칭을 사실상 O(1)로 만들고, 이 제약이 희소 인덱스를 가능하게 한다.
  • 희소 인덱스는 범위 밖 디렉토리를 엔트리 하나(mode 040000 + SKIP_WORKTREE + 경로 끝 / + 트리 OID)로 압축한다. 인덱스 엔트리가 350만 개에서 수천 개로 줄어든다.
  • 미개조 명령은 ensure_full_index()로 임시 확장하는 안전한 폴백을 쓴다. "전부 고칠 때까지 기다리지 않고 핵심 경로부터 이득을 보는" 점진적 전환 전략이며, merge-ort가 메모리에서 머지하도록 바뀐 것도 같은 흐름이다.
