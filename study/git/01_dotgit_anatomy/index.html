폴더 하나를 지우면 왜 역사가 통째로 사라질까?

.git 디렉토리 해부 — 저장소는 파일 시스템 위에 얹힌 작은 데이터베이스다

Part 1: git init이 실제로 하는 일

git init을 치면 "Initialized empty Git repository"라는 한 줄만 나옵니다. 내부에서는 뭘 하는 건가요?

거창한 일은 일어나지 않습니다. 디렉토리 몇 개와 파일 세 개를 만드는 것이 전부입니다. Git 소스에서 이 작업은 setup.c의 init_db() 함수가 담당하며, 하는 일을 요약하면 다음과 같습니다.

  1. .git/objects, .git/refs/heads, .git/refs/tags 디렉토리 생성
  2. 템플릿 디렉토리(/usr/share/git-core/templates)의 내용 복사 — 여기서 hooks/ 샘플들이 따라옵니다
  3. .git/config에 저장소 설정(core.repositoryformatversion, core.bare 등) 기록
  4. .git/HEAD에 ref: refs/heads/main 한 줄 기록

중요한 사실: 이 시점에는 객체가 단 하나도 없습니다. .git/objects는 텅 빈 디렉토리이고, refs/heads/main이라는 파일조차 존재하지 않습니다. HEAD는 아직 존재하지 않는 파일을 가리키고 있으며, 이 상태를 Git은 "unborn branch"라고 부릅니다.

🎯 비유로 이해하기

git init은 도서관 건물을 짓는 것이 아니라, 빈 책장과 대출 카드 서랍, 그리고 "현재 보고 있는 책" 메모지 한 장을 준비하는 것에 가깝습니다.

책(객체)은 아직 한 권도 없습니다. 메모지(HEAD)에는 "나는 'main'이라는 이름표가 붙은 선반을 보고 있다"고 적혀 있지만, 정작 그 선반은 첫 책이 들어오는 순간에야 만들어집니다.

그래서 .git 안에는 정확히 무엇이 들어 있나요?

실제 저장소의 .git 디렉토리를 펼쳐 보면 이런 구조입니다. 각 항목이 무슨 역할인지가 곧 Git 전체의 설계도입니다.

.git/
HEAD — 지금 어디에 서 있는가 (symref 또는 raw OID)
config — 이 저장소만의 설정 (remote, branch, core.*)
index — 스테이징 영역 (바이너리, DIRC)
objects/ — 모든 내용물이 저장되는 객체 DB
refs/ — 브랜치·태그 이름 → OID 매핑
packed-refs — refs/를 한 파일로 압축한 것
logs/ — reflog (ref가 움직인 이력)
hooks/ — 이벤트 훅 스크립트
info/exclude — 커밋되지 않는 개인용 .gitignore
COMMIT_EDITMSG, MERGE_HEAD, ORIG_HEAD — 진행 중 상태 파일

이 구조를 한 문장으로 요약하면 이렇습니다. objects/는 "무엇이 있는가", refs/는 "무엇이 중요한가", index는 "다음에 무엇을 저장할 것인가", HEAD는 "나는 지금 어디인가"입니다. 나머지는 전부 부가 기능이거나 캐시입니다.

Part 2: 네 개의 축 — objects, refs, index, HEAD

이 네 가지가 서로 어떻게 맞물려 돌아가나요?

Git의 모든 명령은 결국 이 네 축 사이를 오가는 일입니다. git add는 워킹 트리 → objects + index, git commit은 index → objects + refs, git checkout은 objects → index + 워킹 트리로 데이터를 옮깁니다.

워킹 트리
평범한 파일들. Git이 관리하지 않는 보통의 디스크 내용
→
index (.git/index)
git add: 내용은 blob으로 objects에 쓰고, 경로 + OID + stat 정보를 index에 기록
→
objects + refs
git commit: index를 tree로 굳히고, commit 객체를 만들고, HEAD가 가리키는 ref를 새 OID로 갱신

반대로 git checkout <branch>는 이 흐름을 거꾸로 탑니다. ref → commit → tree를 읽어 index를 통째로 갈아끼우고, index에 맞춰 워킹 트리 파일을 쓰고, 마지막으로 HEAD의 symref 대상을 바꿉니다.

주의: 흔한 오해와 달리 git add 시점에 이미 객체가 저장됩니다. 커밋 전이라도 blob은 .git/objects에 존재합니다. 그래서 git add 후 파일을 지워도 git cat-file -p <oid>로 내용을 되살릴 수 있습니다.

HEAD 파일은 정확히 어떻게 생겼나요?

두 가지 형태밖에 없습니다. 브랜치 위에 있으면 symbolic ref, detached 상태면 원시 OID입니다.

.git/HEAD — 두 가지 상태
# 1) 브랜치에 붙어 있을 때 (symref)
$ cat .git/HEAD
ref: refs/heads/main

# 2) detached HEAD (git checkout <커밋해시> 이후)
$ cat .git/HEAD
a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0

이 한 줄의 차이가 git commit의 결과를 완전히 바꿉니다. symref 상태에서 커밋하면 Git은 refs/heads/main 파일을 새 커밋 OID로 덮어씁니다. detached 상태에서 커밋하면 갱신할 ref가 없으므로 HEAD 자체에 새 OID를 직접 씁니다. 그래서 다른 브랜치로 이동하는 순간 그 커밋을 가리키는 이름이 아무것도 남지 않고, 나중에 GC 대상이 됩니다.

"detached HEAD에서 작업하면 잃어버린다"는 경고의 정체가 바로 이것입니다. 커밋 객체는 멀쩡히 존재하지만 도달 가능한 이름이 없어서 사라질 운명이 됩니다. reflog가 유일한 생명줄입니다.

Part 3: 삭제하면 왜 모든 게 사라지는가

워킹 트리에 소스 코드가 멀쩡히 있는데, .git만 지우면 왜 히스토리가 통째로 날아가나요?

Git은 중앙 서버가 아니라 로컬 디렉토리에 완전한 데이터베이스를 가지고 있는 분산 VCS이기 때문입니다. SVN처럼 서버가 원본을 들고 있고 로컬은 체크아웃 사본인 구조가 아닙니다.

.git 디렉토리는 다음을 전부 담고 있는 유일한 사본입니다.

구분 워킹 트리 .git 디렉토리
담고 있는 것 현재 커밋(또는 수정 중인) 시점의 파일 한 벌 역사상 존재한 모든 버전의 파일 내용, 커밋 그래프, 브랜치, 태그, 원격 설정
복구 가능성 .git이 있으면 git checkout .으로 언제든 재생성 사라지면 로컬에서는 복구 불가 (원격 clone만이 유일한 백업)
크기 특성 파일 크기 합 델타 압축 덕에 종종 워킹 트리보다 작음

반대로 말하면 .git 디렉토리만 통째로 복사하면 저장소 전체가 복제됩니다. git clone이 하는 일도 본질적으로는 "원격의 객체 DB와 refs를 내 .git으로 옮겨 오고, 마지막에 워킹 트리를 펼치는 것"입니다.

🎯 비유로 이해하기

워킹 트리는 책상 위에 펼쳐 놓은 원고 한 장이고, .git은 지금까지 쓴 모든 초고가 들어 있는 캐비닛입니다.

책상 위 원고를 잃어버리면 캐비닛에서 다시 꺼내면 됩니다. 하지만 캐비닛을 통째로 버리면, 책상 위의 마지막 한 장 말고는 아무것도 남지 않습니다.

bare 저장소(--bare)는 뭐가 다른가요?

bare 저장소는 워킹 트리 없이 .git의 내용물만 최상위에 펼쳐 놓은 것입니다. myrepo.git/ 안에 곧바로 objects/, refs/, HEAD가 있습니다.

config 차이
# 일반 저장소 .git/config
[core]
	repositoryformatversion = 0
	filemode = false
	bare = false
	logallrefupdates = true

# bare 저장소 config
[core]
	repositoryformatversion = 0
	bare = true            # ← 이 한 줄이 핵심

서버(GitHub, GitLab, 사내 Gitea)가 bare를 쓰는 이유는 명확합니다. 서버에는 체크아웃된 파일이 필요 없고, 오히려 워킹 트리가 있으면 push가 워킹 트리와 불일치를 일으키기 때문입니다. 그래서 일반 저장소의 체크아웃된 브랜치로 push하면 Git이 거부합니다(receive.denyCurrentBranch).

Part 4: 실전 — .git을 직접 들여다보기

실제로 명령어를 쳐 가면서 확인하려면 어떤 순서가 좋을까요?

빈 디렉토리에서 시작해 파일 하나를 커밋하며 .git이 어떻게 변하는지 관찰하는 것이 가장 빠릅니다. 아래 순서를 그대로 따라 하면 이 시리즈의 나머지 주제가 전부 눈에 보이기 시작합니다.

bash — .git 관찰 실습
# 1) 빈 저장소를 만들고 구조를 본다
$ git init lab && cd lab
$ find .git -type f | sort | head
.git/config
.git/description
.git/HEAD
.git/hooks/applypatch-msg.sample
...
# objects/ 아래에는 파일이 하나도 없다. refs/heads도 비어 있다.

# 2) 파일 하나를 add 한다 (아직 커밋 아님)
$ echo "hello" > a.txt && git add a.txt
$ find .git/objects -type f
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
# ← 커밋도 안 했는데 blob이 벌써 생겼다!

# 3) 그 객체가 뭔지 물어본다
$ git cat-file -t ce013625030ba8dba906f756967f9e9ca394464a
blob
$ git cat-file -p ce013625030ba8dba906f756967f9e9ca394464a
hello

# 4) 커밋하면 tree와 commit 객체가 추가된다
$ git commit -m "first"
$ find .git/objects -type f | wc -l
3                      # blob + tree + commit

# 5) 이제 refs가 생겼다
$ cat .git/refs/heads/main
f7d3c0e...             # 커밋 OID 40자 + 개행 = 41바이트
$ cat .git/HEAD
ref: refs/heads/main

여기서 얻는 결론은 단순합니다. Git의 "마법"은 전부 파일 몇 개의 내용입니다. 브랜치는 41바이트짜리 텍스트 파일이고, 커밋은 zlib으로 압축된 텍스트 덩어리이며, 스테이징 영역은 바이너리 파일 하나입니다.

내부를 뜯어볼 때 쓸 만한 저수준(plumbing) 명령에는 뭐가 있나요?

Git 명령은 사용자용 porcelain(add, commit, log)과 스크립트용 plumbing으로 나뉩니다. 내부 학습에는 plumbing이 필수입니다.

명령 하는 일 언제 쓰나
git cat-file -t / -s / -p <oid> 객체의 타입 / 크기 / 내용 출력 모든 객체 해부의 출발점
git hash-object -w <file> 파일을 blob으로 저장하고 OID 출력 해시가 어떻게 계산되는지 검증
git ls-files --stage index 내용을 사람이 읽게 출력 스테이징 영역 관찰, 충돌 stage 확인
git ls-tree <tree-ish> 트리 객체의 엔트리 나열 디렉토리 구조 표현 방식 확인
git rev-parse <rev> 모든 표기법을 OID로 해석 HEAD~3^2 같은 표현 검증
git rev-list --objects --all 도달 가능한 모든 객체 나열 GC/용량 분석
git fsck --lost-found 무결성 검사 + 미아 객체 찾기 사고 복구

이 시리즈의 나머지 22편은 위 명령이 보여 주는 결과물이 디스크에서 실제로 어떤 바이트열인지를 하나씩 따라가는 여정입니다.

📌 핵심 정리

  • git init은 디렉토리 몇 개와 파일 세 개(config, HEAD, description)를 만드는 것이 전부다. 이 시점에 객체도, refs/heads/main 파일도 존재하지 않는다.
  • Git은 네 축으로 돌아간다. objects("무엇이 있는가"), refs("무엇이 중요한가"), index("다음에 무엇을 저장하나"), HEAD("나는 지금 어디인가").
  • git add 시점에 이미 blob이 디스크에 기록된다. 커밋은 index를 tree로 굳히고 commit 객체를 만들어 ref를 옮기는 작업일 뿐이다.
  • HEAD는 symref(ref: refs/heads/main) 또는 원시 OID 두 형태뿐이다. detached HEAD가 위험한 이유는 커밋을 가리킬 이름이 남지 않기 때문이다.
  • .git은 로컬에 존재하는 완전한 데이터베이스이자 유일한 사본이다. 워킹 트리는 그중 한 시점을 펼쳐 놓은 사본에 불과하다.
