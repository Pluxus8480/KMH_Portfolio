Part 1: pkt-line — Git의 와이어 프레이밍

Git은 네트워크로 무엇을 어떻게 주고받나요?

모든 통신이 pkt-line이라는 단순한 프레이밍 위에서 이루어집니다. HTTP, SSH, git:// 어느 전송 계층을 쓰든 그 안에 흐르는 것은 pkt-line입니다.

pkt-line 포맷 (gitprotocol-common.adoc)
  data-pkt     =  pkt-len pkt-payload
  pkt-len      =  4*(HEXDIG)              ← 길이를 4자리 16진수 ASCII로
  pkt-payload  =  (pkt-len - 4)*(OCTET)

  flush-pkt    = "0000"

pkt-len은 자기 자신 4바이트를 포함한 전체 길이다.

예시 (C 문자열 표기):
  "0006a\n"       →  "a\n"          (6 = 4 + 2)
  "0005a"         →  "a"            (5 = 4 + 1)
  "000bfoobar\n"  →  "foobar\n"     (0x0b = 11 = 4 + 7)
  "0000"          →  flush (구분자)

길이를 바이너리가 아니라 16진수 ASCII 4자로 쓴 것이 특징입니다. 디버깅할 때 tcpdump나 로그에서 눈으로 읽을 수 있고, 엔디언 문제가 없습니다. 페이로드 최대 길이는 65,516바이트입니다(ffff = 65535에서 헤더 4바이트와 여유를 뺀 값).

프로토콜 v2에는 세 가지 특수 패킷이 있습니다.

패킷이름의미
0000flush-pkt메시지의 끝
0001delim-pkt메시지 내부의 섹션 구분
0002response-end-pktstateless 연결에서 응답 하나의 끝
🎯 비유로 이해하기

pkt-line은 "봉투마다 앞면에 두께를 적어 두는 우편"입니다.

받는 쪽은 앞 4글자만 읽으면 이 봉투가 몇 바이트인지 정확히 알 수 있어, 딱 그만큼만 읽고 다음 봉투로 넘어갑니다. 내용물에 무엇이 들었든(바이너리 팩 데이터라도) 경계를 잃지 않습니다.

빈 봉투 세 종류가 구두점 역할을 합니다 — 0000은 마침표, 0001은 쉼표, 0002는 단락 끝입니다.

실제 통신을 눈으로 볼 수 있나요?
bash — 프로토콜 추적
# 모든 패킷을 덤프
$ GIT_TRACE_PACKET=1 git ls-remote https://github.com/git/git 2>&1 | head -20
packet:        git< version 2
packet:        git< agent=git/github-...
packet:        git< ls-refs=unborn
packet:        git< fetch=shallow wait-for-done filter
packet:        git< server-option
packet:        git< object-format=sha1
packet:        git< 0000
packet:        git> command=ls-refs
packet:        git> agent=git/2.56.0
packet:        git> 0001
packet:        git> peel
packet:        git> symrefs
packet:        git> ref-prefix HEAD
packet:        git> 0000
packet:        git< a1b2c3d... HEAD symref-target:refs/heads/master
packet:        git< 0000

#  < 는 서버 → 클라이언트, > 는 클라이언트 → 서버
#  0001(delim)이 "명령/능력" 구간과 "인자" 구간을 나누는 것이 보인다

# 프로토콜 버전 강제
$ GIT_TRACE_PACKET=1 git -c protocol.version=0 ls-remote ...   # v0(구버전)
$ GIT_TRACE_PACKET=1 git -c protocol.version=2 ls-remote ...   # v2

# 더 자세히
$ GIT_TRACE=1 GIT_TRACE_PACKET=1 GIT_CURL_VERBOSE=1 git fetch 2>&1 | less

GIT_TRACE_PACKET=1은 전송 문제 디버깅의 1순위 도구입니다. 인증 실패, 프록시 문제, 서버 능력 불일치가 이 출력에서 대부분 드러납니다.

Part 2: 프로토콜 v2가 고친 것

v0(구버전)의 문제가 뭐였나요?

Git 문서가 v2의 개선점을 다섯 가지로 나열하는데, 뒤집어 보면 그것이 v0의 문제입니다.

v0의 문제v2의 해법
무조건 전체 ref 광고. 연결하자마자 서버가 모든 ref를 쏟아냄 명시적으로 요청하지 않으면 광고하지 않음. ls-refs 명령으로 필요한 것만
서비스 이름이 여러 개(git-upload-pack, git-receive-pack) 하나의 서비스에 여러 명령
능력(capability)이 NUL 바이트 뒤에 숨어 pkt-line 크기 제한을 받음 능력이 독립 섹션으로 분리되어 확장 자유로움
agent, symref 같은 정보가 NUL 뒤에 섞임 각각 별도 능력/인자로 분리
HTTP stateless 환경과 잘 안 맞음 처음부터 stateless를 전제로 설계. flush 의미가 명확해 HTTP 헬퍼가 단순 프록시로 동작

첫 번째 항목이 실무에서 가장 큽니다. ref가 86만 개인 저장소(12편)에서 git fetch origin main 한 번에 86만 줄의 ref 광고가 오갔습니다. v2에서는 ref-prefix refs/heads/main만 보내면 되므로 초기 왕복 데이터가 수십 MB에서 수 KB로 줄었습니다.

gitprotocol-v2.adoc — 설계 목표
  * 여러 서비스 이름 대신 하나의 서비스가 여러 명령을 지원
  * 능력이 별도 섹션으로 분리되어 확장이 쉬움 (NUL 뒤에 숨지 않음)
  * agent 문자열, symref 등을 별도 능력/인자로 분리
  * 명시적으로 요청하지 않으면 ref를 광고하지 않음
  * ls-refs 명령으로 필요한 ref만 요청
  * http와 stateless-rpc를 염두에 두고 설계
v2의 통신 흐름은 어떻게 되나요?

"능력 광고 → 명령 요청 → 응답"의 반복입니다. 한 연결에서 여러 명령을 이어서 쓸 수 있습니다.

1. 버전 선언
클라이언트가 전송 계층별 채널로 version=2 전달 (GIT_PROTOCOL 환경변수 / HTTP 헤더)
→
2. 능력 광고
서버가 version 2, agent=..., ls-refs=unborn, fetch=shallow filter ..., object-format=sha1 등을 보냄
→
3. 명령 요청
command=ls-refs 또는 command=fetch + 능력들 + 0001 + 인자들 + 0000
→
4. 응답 & 반복
응답 수신 후 같은 연결에서 다음 명령 가능

ls-refs가 받는 인자들이 최적화의 핵심입니다.

인자의미
symrefssymbolic ref가 가리키는 대상까지 함께 보여 달라 (HEAD → refs/heads/main)
peel주석 태그가 최종적으로 가리키는 커밋까지 (11편의 fully-peeled와 같은 개념)
ref-prefix <prefix>이 접두사로 시작하는 ref만 보내 달라. 여러 번 지정 가능
unbornHEAD가 아직 없는 브랜치를 가리켜도 알려 달라 (빈 저장소 대응)

문서가 명시하는 중요한 단서: ref-prefix는 순수한 최적화이며, 서버는 접두사에 맞지 않는 ref를 보내도 된다. 따라서 클라이언트가 스스로 한 번 더 필터링해야 합니다. 프로토콜 구현자가 놓치기 쉬운 지점입니다.

Part 3: 네고시에이션 — want와 have의 협상

fetch에서 "필요한 것만 받는다"는 걸 어떻게 정하나요?

클라이언트가 원하는 것(want)을 말하고, 이미 가진 것(have)을 조금씩 흘리면 서버가 공통 지점을 찾아 "준비됐다"고 답하는 구조입니다.

fetch 명령의 주요 인자
want <oid>        내가 원하는 객체 (보통 원격 브랜치의 tip)
have <oid>        내가 이미 가진 객체
done              협상 종료. 지금까지의 정보로 팩을 보내라

thin-pack         base가 없는 thin pack을 받아도 좋다 (08편)
ofs-delta         OBJ_OFS_DELTA를 이해할 수 있다
no-progress       진행률 메시지 불필요
include-tag       받는 객체를 가리키는 주석 태그도 함께 보내 달라
deepen <depth>    shallow: 이 깊이까지만
filter <spec>     부분 클론 필터 (23편)

서버의 응답은 섹션으로 나뉩니다. acknowledgments, shallow-info, wanted-refs, packfile-uris, 그리고 마지막에 packfile입니다.

네고시에이션 왕복의 실제 모습
C: command=fetch
C: 0001
C: thin-pack
C: ofs-delta
C: want a1b2c3d...          ← origin/main의 최신 커밋
C: have f7d3c0e...          ← 내 로컬 커밋들을 최근 것부터
C: have c9d0e1f...
C: have 3f4a5b6...
C: 0000

S: acknowledgments
S: ACK c9d0e1f...           ← "이건 나도 있다" (공통)
S: NAK                       ← 또는 "아무것도 공통이 아니다"
S: 0000

C: (더 오래된 have들을 추가로 전송...)
C: done                      ← 이제 그만. 팩을 보내라
C: 0000

S: packfile
S: (사이드밴드로 팩 데이터 스트리밍)
S: 0000

문서가 정리하는 acknowledgments 섹션의 규칙이 명확합니다.

  • 클라이언트가 done을 보내 팩을 요구했다면 이 섹션은 생략되어야 합니다.
  • 공통인 have가 하나도 없으면 NAK, 있으면 각각에 ACK <oid>를 보냅니다.
  • ACK와 NAK가 같은 응답에 함께 올 수는 없습니다.
  • 서버가 충분한 공통 기반을 찾으면 ready를 보내고, 같은 응답의 packfile 섹션에 팩을 담습니다.
  • ready를 보내기로 했다면 ACK들을 생략해도 됩니다 — 이미 보낼 객체가 확정되어 더 협상할 필요가 없기 때문입니다.
🎯 비유로 이해하기

전집을 빌려주는 상황입니다. "전체를 다 주면" 낭비이므로 어디까지 갖고 있는지를 확인해야 합니다.

빌리는 쪽: "50권이 필요합니다. 참고로 저는 20권, 19권, 18권을 갖고 있습니다."
빌려주는 쪽: "20권은 저도 있는 판본이네요(ACK). 그럼 21~50권만 준비하겠습니다(ready)."

한 번에 전부 말하지 않고 최근 것부터 조금씩 흘리는 이유는, 대개 최근 것에서 금방 공통점이 나오기 때문입니다. 100만 권 목록을 통째로 보내는 것은 낭비입니다.

클라이언트는 have를 어떻게 고르나요?

네고시에이션 알고리즘이 담당하며, 13편의 리비전 워크를 씁니다. 기본은 "최근 커밋부터 지수적으로 간격을 벌리며" 보냅니다.

알고리즘방식특징
default커밋 날짜 역순으로 훑으며 have 전송범용
skipping지수적으로 건너뛰며 전송왕복 수 감소. 히스토리가 길 때 유리
noophave를 아예 안 보냄서버가 전부 보냄. 협상 비용 0, 전송량 최대
bash — 네고시에이션 튜닝
# 알고리즘 선택
$ git config fetch.negotiationAlgorithm skipping

# 협상 왕복에 쓸 최대 커밋 수 (기본 100)
$ git -c fetch.negotiationAlgorithm=skipping fetch origin

# 네고시에이션 과정 추적
$ GIT_TRACE_PACKET=1 git fetch origin 2>&1 | grep -E 'have|ACK|NAK|ready' | head -20

# 협상 자체를 건너뛰기 (첫 clone처럼 동작)
$ git fetch --negotiation-tip=HEAD origin
# 특정 커밋들만 have로 보냄 — 거대 저장소에서 협상 비용 절감

협상이 끝나면 서버는 "want에서 도달 가능한 객체 − have에서 도달 가능한 객체"를 계산해 팩으로 만듭니다. 이것이 13편에서 본 UNINTERESTING 전파이고, 10편의 도달 가능성 비트맵이 결정적으로 기여하는 지점입니다 — 집합 차집합이 비트 연산 몇 번으로 끝납니다.

그리고 08편의 thin pack이 여기서 쓰입니다. 클라이언트가 thin-pack 능력을 선언했으므로, 서버는 클라이언트가 이미 가진 객체를 base로 하는 REF_DELTA를 보낼 수 있습니다. base를 포함하지 않으므로 전송량이 크게 줍니다. 클라이언트는 index-pack --fix-thin으로 로컬 base를 덧붙여 자기 완결적 팩으로 만든 뒤 저장합니다.

Part 4: 실전 — 전송 최적화와 문제 진단

push는 fetch와 어떻게 다른가요?

방향이 반대이고, ref 갱신 요청이 추가됩니다. 서버 측 명령은 receive-pack입니다.

push의 흐름
1. 서버가 현재 ref 목록을 광고 (클라이언트가 무엇을 보낼지 판단하기 위해)

2. 클라이언트가 ref 갱신 명령을 보냄
   <old-oid> <new-oid> <refname>
   ↑ old-oid가 compare-and-swap의 기대값 (11편)
     --force-with-lease가 이 값을 내가 마지막으로 본 값으로 채운다

3. 클라이언트가 팩을 전송 (서버가 없는 객체만)

4. 서버가 검증하고(receive.fsckObjects, 20편) 훅을 실행
   pre-receive → update(ref마다) → (ref 갱신) → post-receive

5. 서버가 결과 보고
   unpack ok
   ok refs/heads/main
   ng refs/heads/protected  pre-receive hook declined

서버 측 훅이 실행되는 지점이 여기입니다. pre-receive는 전체 push를 한 번에 거부할 수 있고, update는 ref별로 거부할 수 있습니다. 브랜치 보호, 커밋 메시지 검증, 서명 확인이 전부 이 지점에서 이루어집니다.

git push --atomic을 쓰면 11편의 ref 트랜잭션이 적용되어 "일부 ref만 갱신되는" 중간 상태가 생기지 않습니다. 릴리스 태그와 브랜치를 함께 밀어야 하는 배포 파이프라인에서 중요합니다.

거대 저장소의 clone/fetch를 빠르게 하려면요?

병목이 어디냐에 따라 처방이 다릅니다.

병목처방비고
서버의 객체 나열 도달 가능성 비트맵 (10편) 서버 측 설정. repack -adb
전송량 부분 클론 --filter=blob:none (23편) 히스토리는 유지, blob은 필요할 때
히스토리 깊이 shallow --depth=1 CI에 적합. 이후 작업에 제약
ref 광고 프로토콜 v2 + --single-branch Git 2.26부터 v2가 기본
CDN 활용 packfile-uris 서버가 "이 URL에서 받아라"를 알려 줌

packfile-uris가 흥미롭습니다. 응답의 한 섹션으로 "이 팩은 이 URL에서 직접 받아라"를 알려 주어, 대용량 데이터를 Git 서버가 아닌 CDN이나 오브젝트 스토리지가 서빙하게 합니다. 거대 저장소를 호스팅하는 서비스의 핵심 확장입니다.

bash — 상황별 clone 전략
# CI: 최신 커밋만 필요
$ git clone --depth=1 --single-branch --branch main <url>

# 개발: 히스토리는 필요하지만 옛날 파일 내용은 불필요
$ git clone --filter=blob:none <url>         # blob은 필요할 때 on-demand

# 모노레포에서 일부 디렉토리만
$ git clone --filter=blob:none --sparse <url>
$ cd repo && git sparse-checkout set services/payment

# 서버 측 준비 (호스팅을 직접 운영한다면)
$ git repack -adb                              # 비트맵
$ git multi-pack-index write --bitmap          # MIDX 비트맵
$ git config uploadpack.allowFilter true       # 부분 클론 허용
$ git config uploadpack.allowAnySHA1InWant true
bash — 전송 문제 진단 체크리스트
# 1) 어떤 프로토콜 버전을 쓰는가
$ GIT_TRACE_PACKET=1 git ls-remote <url> 2>&1 | head -3
packet:        git< version 2          # v2면 정상

# 2) 서버가 어떤 능력을 광고하는가
$ GIT_TRACE_PACKET=1 git ls-remote <url> 2>&1 | grep 'git<'

# 3) HTTP 레이어 문제인가 (프록시, 인증, TLS)
$ GIT_CURL_VERBOSE=1 git fetch 2>&1 | head -40

# 4) 큰 push가 실패한다면
$ git config http.postBuffer 524288000        # 500MB (HTTP만 해당)
# ↑ 다만 대개는 서버 측 제한이 원인. 커밋을 나눠 push하는 편이 낫다

$ git fetch --unshallow
$ git commit-graph write --reachable          # 세대 재계산 (14편)

면접 포인트: "clone이 느린데 원인을 어떻게 찾겠는가"라는 질문에는 계층을 나눠 답하는 것이 좋습니다. (1) 협상 — ref 광고량, 프로토콜 버전, (2) 객체 나열 — 서버의 비트맵 유무, (3) 전송 — 팩 크기, thin pack, CDN, (4) 수신 처리 — index-pack의 델타 복원과 fsck 검증. GIT_TRACE_PACKET과 진행률 표시가 어느 단계에서 멈추는지를 알려 줍니다.

📌 핵심 정리

  • 모든 Git 통신은 pkt-line 위에서 이루어진다. 길이를 16진수 ASCII 4자로 앞에 붙이며(자기 자신 포함), 0000=flush, 0001=delim, 0002=response-end가 구두점 역할을 한다. 페이로드 최대 65,516바이트.
  • 프로토콜 v2의 핵심은 "요청하지 않으면 ref를 광고하지 않는다"이다. ls-refs의 ref-prefix로 필요한 것만 받으며, 다만 이는 최적화일 뿐이라 클라이언트가 한 번 더 필터링해야 한다.
  • 네고시에이션은 want/have의 협상이다. 서버는 공통 객체에 ACK, 없으면 NAK를 보내고, 충분한 기반을 찾으면 ready 후 팩을 보낸다. 클라이언트가 done을 보내면 acknowledgments 섹션은 생략된다.
  • 보낼 객체 = "want 도달 가능 − have 도달 가능"이며, 비트맵이 이 차집합을 비트 연산으로 끝낸다. thin pack 덕분에 클라이언트가 이미 가진 객체를 base로 한 델타만 보낼 수 있다.
  • push는 <old> <new> <ref> 형태의 CAS 요청이며, 서버 훅(pre-receive/update/post-receive)이 여기서 실행된다. 전송 최적화는 비트맵·부분 클론·shallow·packfile-uris(CDN)로 계층별 병목에 맞춰 선택한다.
