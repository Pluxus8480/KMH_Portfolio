SHA-1은 깨졌는데 Git은 왜 안 무너졌을까?

해시 함수 전환 — SHAttered · 충돌 탐지 SHA-1 · SHA-256 선택 · objectFormat 확장

Part 1: 2017년 2월, SHAttered

SHA-1이 깨졌다는 게 정확히 무슨 뜻인가요?

Git 문서가 직접 기록합니다. "2017년 2월 23일 SHAttered 공격이 실용적인 SHA-1 해시 충돌을 시연했다"(https://shattered.io).

"깨졌다"는 표현을 정확히 이해해야 합니다. 암호학 해시에는 여러 속성이 있고, SHAttered가 깬 것은 그중 하나입니다.

속성의미SHA-1의 상태
충돌 저항성
(collision resistance)		 같은 해시를 갖는 서로 다른 두 입력을 만들기 어려움 깨짐. SHAttered가 실제 PDF 두 개를 제시
제2 역상 저항성
(2nd preimage)		 주어진 입력과 같은 해시를 갖는 다른 입력 찾기 아직 실용적 공격 없음
역상 저항성
(preimage)		 해시값만으로 원본 입력 복원 아직 실용적 공격 없음

Git에 중요한 차이가 여기 있습니다. 충돌 공격은 "공격자가 둘 다 만들어야" 성립합니다. "이미 저장소에 있는 특정 커밋과 같은 해시를 갖는 악성 커밋을 만드는 것"은 제2 역상 공격이고, 이는 아직 불가능합니다.

그래도 위험합니다. 공격자가 양성 파일과 악성 파일을 미리 짝지어 만들어 두고, 양성 쪽을 PR로 보내 머지시킨 뒤, 나중에 악성 쪽으로 바꿔치기하는 시나리오가 가능합니다. Git 문서도 "SHA-1은 여전히 약하다"고 못 박습니다.

🎯 비유로 이해하기

인감도장의 위조와 같습니다.

충돌은 "내가 두 장의 계약서를 만드는데, 같은 인영이 찍히도록 둘 다 미리 설계하는 것"입니다. 무해해 보이는 쪽을 상대에게 도장 받고, 나중에 악성 쪽으로 바꿔치기합니다.

제2 역상은 "이미 남이 도장 찍은 계약서와 같은 인영이 나오는 다른 계약서를 만드는 것"입니다. 훨씬 어렵고, 아직 아무도 못 했습니다.

SHAttered가 보여 준 것은 전자입니다. 그래도 "도장을 바꿔야 한다"는 결론은 같습니다.

그런데 왜 Git 저장소들이 실제로 무너지지 않았나요?

Git이 선제적으로 방어를 넣었기 때문입니다. Git 문서가 명시합니다. "Git v2.13.0 이후로는 기본적으로 강화된(hardened) SHA-1 구현으로 옮겨 갔으며, 이는 SHAttered 공격에 취약하지 않다."

이 구현이 sha1collisiondetection(sha1dc)입니다. Marc Stevens(SHAttered 공동 저자)와 Dan Shumow가 만든 라이브러리로, Git 소스 트리에 sha1dc/로 포함되어 있습니다.

동작 원리
일반 SHA-1: 입력 → 해시값

sha1dc:     입력 → 해시값
                 + 충돌 공격의 흔적을 탐지

SHA-1 충돌 공격은 특정한 형태의 "차분 경로(disturbance vector)"를
압축 함수 내부에 남긴다. sha1dc는 해시를 계산하면서
그 패턴이 나타나는지 동시에 검사한다.

탐지되면 → Git이 오류를 내고 작업을 거부한다.
탐지되지 않으면 → 일반 SHA-1과 완전히 동일한 값을 반환한다.

이 설계의 핵심은 하위 호환성입니다. 기존 저장소의 모든 OID가 그대로 유효합니다. 공격이 시도된 객체만 거부되고, 정상 객체는 아무 영향을 받지 않습니다. 저장소를 변환할 필요도, 다른 도구와 호환이 깨질 일도 없었습니다.

bash — 실제로 확인해 보기
# SHAttered의 충돌 PDF 두 개를 받아 add 해 보면
$ wget https://shattered.io/static/shattered-1.pdf
$ wget https://shattered.io/static/shattered-2.pdf
$ git add shattered-1.pdf
fatal: SHA-1 collision attack detected: shattered-1.pdf
# ↑ Git이 충돌 공격 시도를 탐지하고 거부한다

# 빌드 설정 확인 (Makefile)
$ grep -n "DC_SHA1" /path/to/git/Makefile | head -3
# DC_SHA1_EXTERNAL / DC_SHA1_SUBMODULE 등으로 구현을 고를 수 있다

그럼에도 Git 문서의 결론은 "신중하게, SHA-1의 어떤 변형에서도 벗어나는 것이 옳다"입니다. 이유도 명확합니다 — "미래에 SHA-1에 대한 새로운 공격이 발표되지 않으리라는 보장이 없고, 그 공격에는 실행 가능한 완화책이 없을 수 있다." sha1dc는 알려진 공격 패턴을 탐지하는 것이지, 근본적인 해결이 아닙니다.

Part 2: 왜 SHA-256인가

후속 해시는 어떻게 골랐나요?

Git 문서가 네 가지 선정 기준을 명시합니다.

  1. 256비트 길이 — 일반적인 보안 관행에 부합할 만큼 길되, 성능과 디스크 사용량을 해칠 만큼 과하지 않게
  2. 고품질 구현이 널리 존재 — OpenSSL, Apple CommonCrypto 등
  3. Git의 필요와 속성이 맞을 것 — 충돌 저항성과 제2 역상 저항성은 필요하지만, 길이 확장 공격 저항성은 필요 없음
  4. 타이브레이커: 계산이 빠를 것 — 다행히 후보 다수가 SHA-1보다 빠름

후보는 SHA-256, SHA-512/256, SHA-256x16, K12, BLAKE2bp-256이었고, 2018년 말 SHA-256으로 결정되었습니다.

3번이 흥미롭습니다. SHA-256은 길이 확장 공격에 취약한 Merkle–Damgård 구조입니다. 보통은 단점으로 꼽히지만, Git은 비밀 키를 해시에 넣는 MAC 용도로 쓰지 않으므로 그 취약점이 무의미합니다. "우리 용도에 필요 없는 속성"을 과감히 요구 사항에서 제외한 실용적 판단입니다.

"더 좋은 해시"가 아니라 "우리 문제에 충분하면서 생태계 지원이 가장 넓은 해시"를 고른 것입니다. BLAKE2bp-256이 더 빠를 수 있지만, SHA-256은 거의 모든 플랫폼에 하드웨어 가속(Intel SHA extensions, ARMv8 crypto)이 있고 모든 암호 라이브러리에 들어 있습니다.

SHA-256으로 바뀌면 무엇이 달라지나요?

OID가 20바이트/40자 → 32바이트/64자가 되고, 그 여파가 모든 포맷에 미칩니다. 지금까지 본 포맷들을 다시 훑어보면 전부 "해시 길이에 의존"하고 있었습니다.

포맷SHA-1SHA-256편
트리 엔트리의 OID20바이트 바이너리32바이트 바이너리04편
커밋 헤더의 OID40자 16진수64자 16진수05편
인덱스 엔트리62바이트 고정부74바이트 고정부06편
팩 트레일러 체크섬20바이트32바이트08편
.idx OID 테이블N×20바이트N×32바이트10편
REF_DELTA의 base 참조20바이트32바이트08편
ref 파일41바이트65바이트11편
빈 트리 OID4b825dc6...6ef19b41...03편

이 때문에 스크립트에 40이라는 숫자를 하드코딩하면 SHA-256 저장소에서 전부 깨집니다. grep -E '^[0-9a-f]{40}$' 같은 패턴이 대표적입니다. git rev-parse로 정규화하거나 길이를 가변으로 다루어야 합니다.

bash — 해시 비의존적으로 스크립트 짜기
# ❌ 깨지는 코드
$ git log --format=%H | grep -E '^[0-9a-f]{40}$'

# ✅ 길이에 의존하지 않음
$ git log --format=%H | while read oid; do
    git rev-parse --verify "$oid^{commit}" >/dev/null || echo "invalid: $oid"
  done

# 현재 저장소의 해시 알고리즘 확인
$ git rev-parse --show-object-format
sha1

# 빈 트리 OID를 하드코딩하지 말고 계산해서 쓰기
$ EMPTY_TREE=$(git hash-object -t tree /dev/null)
$ git diff "$EMPTY_TREE" HEAD --stat

Part 3: 전환 설계 — 목표와 비(非)목표

전 세계의 Git 저장소를 어떻게 한꺼번에 바꾸나요?

한꺼번에 바꾸지 않습니다. Git 문서의 첫 번째 목표가 그 점을 못 박습니다.

"SHA-256으로의 전환은 로컬 저장소 하나씩 수행할 수 있다. (a) 다른 어떤 당사자의 조치도 요구하지 않는다. (b) SHA-256 저장소가 SHA-1 Git 서버와 통신(push/fetch)할 수 있다. (c) 사용자는 SHA-1과 SHA-256 식별자를 교차해서 쓸 수 있다."

이를 가능하게 하는 것이 이중 저장(dual storage) 개념입니다. SHA-256 저장소가 SHA-1 OID와의 매핑 테이블을 함께 들고, 외부와 통신하거나 사용자가 옛 OID를 입력할 때 변환합니다.

.git/config — 관련 확장
[core]
	repositoryformatversion = 1        # 확장을 쓰려면 반드시 1
[extensions]
	objectFormat = sha256              # 이 저장소의 해시 알고리즘
	compatObjectFormat = sha1          # 호환용 보조 알고리즘
확장역할
extensions.objectFormat 이 저장소가 쓰는 해시. sha1 또는 sha256. 지정하지 않으면 sha1
extensions.compatObjectFormat 호환용 보조 해시. objectFormat과 달라야 한다. 이 알고리즘을 쓰는 저장소와 push/pull이 가능해지고, 그 형식의 OID로 객체를 지정할 수 있다

Git 문서가 compatObjectFormat에 대해 단호하게 경고합니다. "이 확장이 제공하는 기능은 불완전하며 변경될 수 있다. 현재는 기반 기능의 개발과 테스트를 위해서만 존재하며, 최종 사용자가 켜도록 설계되지 않았다." 즉 상호 운용은 아직 미완성입니다.

repositoryformatversion = 1이 중요한 장치입니다. 값이 0인 저장소만 알던 구버전 Git은 1을 보면 "모르는 형식"이라며 안전하게 거부합니다. 조용히 잘못 동작하는 대신 명확히 실패하게 만든 설계이며, 12편의 reftable 더미 파일과 같은 철학입니다.

비(非)목표로 명시된 것들도 있다고 들었습니다.

있습니다. 그리고 이것이 전환이 왜 이렇게 오래 걸리는지를 설명합니다.

비목표의미
Git 프로토콜에 SHA-256 지원 추가 "가치 있고 논리적인 다음 단계지만 이 초기 설계의 범위 밖". 즉 전송 계층은 별도 작업
기존 SHA-1 서명 객체의 보안을 투명하게 개선 이미 SHA-1으로 서명된 것은 소급해서 강해지지 않는다
한 저장소에서 여러 해시 객체를 섞기 저장소는 하나의 objectFormat을 갖는다. 혼재를 허용하지 않는다
이 기회에 다른 포맷 버그를 고치기 범위를 좁혀 위험을 줄인다

세 번째가 특히 중요한 설계 결정입니다. "한 저장소 안에 SHA-1 객체와 SHA-256 객체가 공존"하게 했다면 모든 코드 경로가 두 길이를 동시에 다뤄야 했을 것입니다. 대신 "저장소는 하나의 해시, 필요하면 매핑 테이블"로 단순화했습니다.

두 번째 목표도 명시되어 있습니다. "SHA-1으로부터 완전히 벗어날 수 있어야 한다 — SHA-1 호환용 로컬 메타데이터는 더 이상 필요 없으면 저장소에서 제거할 수 있다." 즉 매핑 테이블은 영구 부담이 아니라 과도기 장치입니다.

Part 4: 지금 무엇을 할 수 있는가

SHA-256 저장소를 지금 만들 수 있나요?

만들 수 있습니다. Git 2.29부터 실험적 기능이 아닌 정식 옵션이며, 로컬에서 완결되는 작업에는 문제없이 동작합니다.

bash — SHA-256 저장소
$ git init --object-format=sha256 repo256
$ cd repo256

$ git rev-parse --show-object-format
sha256

$ echo hello > a.txt && git add a.txt && git commit -q -m first
$ git log --format=%H
5f2e8a1c9b7d3f4e6a0c2b8d1e5f7a9c3b6d8e0f2a4c6b8d0e2f4a6c8b0d2e4f
  ↑ 64자

$ cat .git/config
[core]
	repositoryformatversion = 1
[extensions]
	objectFormat = sha256

# 빈 트리 OID도 달라진다
$ git hash-object -t tree /dev/null
6ef19b41225c5369f1c104d45d8d85efa9b057b53b14b4b9b939dd74decc5321

# 구버전 Git으로 열면?
$ git-2.20 status
fatal: unknown repository extension found: objectformat
# → 조용히 망가지지 않고 명확히 거부한다
실무에서는 지금 무엇을 해야 하나요?

현실적인 판단을 나누면 이렇습니다.

상황권장이유
기존 팀 저장소 SHA-1 유지 호스팅 서비스·CI·IDE·도구 생태계가 아직 SHA-256을 온전히 지원하지 않음
Git 버전 최신 유지 sha1dc 충돌 탐지가 기본 활성 (2.13+). 이것만으로 SHAttered는 막힌다
서버 운영 receive.fsckObjects = true 손상·악성 객체를 push 시점에 차단 (20편)
도구·스크립트 작성 해시 길이 비의존적으로 40 하드코딩 제거. 지금 고쳐 두면 전환 시 비용 0
새 실험/격리 프로젝트 SHA-256 시도 가능 로컬 작업은 완전히 동작. 상호 운용만 주의
무결성이 특히 중요한 경우 커밋/태그 서명 GPG/SSH 서명은 자체 해시(SHA-256/512)를 쓰므로 추가 보증이 된다
bash — 지금 할 수 있는 보안 강화
# 1) 커밋 서명 (SSH 키로, GPG보다 설정이 간단)
$ git config --global gpg.format ssh
$ git config --global user.signingkey ~/.ssh/id_ed25519.pub
$ git config --global commit.gpgsign true
$ git config --global tag.gpgsign true

# 2) 서명 검증
$ git log --show-signature -1
$ git verify-commit HEAD
$ git verify-tag v1.0

# 3) 서버 측 객체 검증
$ git config receive.fsckObjects true
$ git config transfer.fsckObjects true

# 4) 저장소 무결성 정기 점검
$ git fsck --full --strict

# 5) 스크립트의 해시 길이 의존성 점검
$ grep -rn '\[0-9a-f\]\{40\}\|{40}\|cut -c1-40' scripts/ .github/

면접 포인트: "SHA-1이 깨졌는데 Git을 계속 써도 되는가"라는 질문에는 세 층으로 답하는 것이 좋습니다. (1) SHAttered가 깬 것은 충돌 저항성이고, 기존 커밋을 위조하는 제2 역상 공격은 여전히 불가능하다. (2) Git 2.13+는 sha1dc로 충돌 공격을 탐지해 거부하므로 실질적 공격 경로가 막혀 있다. (3) 그럼에도 SHA-256 전환이 진행 중이며, 저장소 단위로 점진적 전환이 가능하도록 설계되었다. 다만 프로토콜 지원과 상호 운용은 아직 미완성이다.

이 전환 과정 자체가 좋은 공학 사례입니다. "근본 해결(SHA-256)은 오래 걸리니, 그동안 실용적 완화책(sha1dc)으로 위험을 막고, 전환은 점진적·호환 가능하게 설계한다." 하위 호환을 유지하며 기반 포맷을 바꾸는 일이 얼마나 큰 작업인지, 그리고 왜 repositoryformatversion 같은 장치를 미리 심어 두는지를 보여 줍니다.

📌 핵심 정리

  • 2017년 SHAttered가 깬 것은 SHA-1의 충돌 저항성이다. 공격자가 두 입력을 모두 설계해야 성립하며, 기존 커밋을 위조하는 제2 역상 공격은 여전히 불가능하다.
  • Git 2.13+는 sha1collisiondetection(sha1dc)을 기본으로 쓴다. 해시를 계산하며 충돌 공격의 차분 패턴을 탐지해 거부하고, 정상 입력에는 일반 SHA-1과 동일한 값을 반환해 기존 OID를 전부 보존한다.
  • 후속 해시로 SHA-256이 선택되었다(2018). 256비트 길이, 광범위한 고품질 구현, Git이 필요로 하는 속성 일치(길이 확장 저항성은 불필요), 계산 속도가 기준이었다.
  • 전환은 저장소 단위로, 다른 당사자의 조치 없이 가능하도록 설계되었다. extensions.objectFormat과 repositoryformatversion = 1이 그 장치이며, 구버전 Git은 조용히 오동작하는 대신 명확히 거부한다.
  • 프로토콜 지원과 compatObjectFormat 상호 운용은 아직 미완성이다. 실무에서는 Git 최신 유지 + receive.fsckObjects + 커밋 서명 + 스크립트의 40자 하드코딩 제거가 지금 할 수 있는 준비다.
