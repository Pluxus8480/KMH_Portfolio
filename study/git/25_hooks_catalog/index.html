Part 1: 커밋 계열 — 메시지를 고쳐 쓸 수 있는 훅들

커밋 하나를 만들 때 훅이 몇 번이나 불리나요?

평범한 git commit 한 번에 최대 네 개가 순서대로 불립니다. 순서가 곧 각 훅의 역할을 규정합니다.

1. pre-commit
메시지를 얻기 전. 인자 없음
→ 내용 검증 (린트·테스트·시크릿 탐지)
→
2. prepare-commit-msg
기본 메시지 준비 후, 에디터 실행 전
→ 메시지 초안 작성
→
3. commit-msg
사용자가 메시지를 다 쓴 뒤
→ 메시지 검증·정규화
→
4. post-commit
커밋 생성 후. 인자 없음
→ 알림만. 결과에 영향 없음

2번과 3번의 차이가 중요합니다. prepare-commit-msg는 "에디터가 뜨기 전"이므로 사용자가 볼 초안을 만드는 자리이고, commit-msg는 "사용자가 다 쓴 뒤"이므로 최종 검증 자리입니다. 이슈 번호 자동 삽입은 전자에, 컨벤션 검사는 후자에 넣어야 합니다.

각 훅의 정확한 스펙을 정리해 주세요.
훅인자stdin0이 아닌 종료 시--no-verify
pre-commit 없음 없음 커밋 중단 우회됨
prepare-commit-msg 1~3개
$1 메시지 파일
$2 출처
$3 커밋 OID		 없음 커밋 중단 우회 안 됨
commit-msg $1 메시지 파일 없음 커밋 중단 우회됨
post-commit 없음 없음 무시됨 —
pre-merge-commit 없음 없음 머지 중단 우회됨

prepare-commit-msg만 --no-verify로 우회되지 않습니다. 문서가 명시합니다 — "The purpose of the hook is to edit the message file in place, and it is not suppressed by the --no-verify option." 검증이 아니라 메시지 생성이 목적이므로 건너뛰면 커밋 자체가 이상해지기 때문입니다.

prepare-commit-msg의 $2(출처)가 특히 유용합니다. 값이 정해져 있습니다.

prepare-commit-msg의 $2 값
message   : -m 또는 -F 옵션이 주어졌다
template  : -t 옵션 또는 commit.template 설정이 있다
merge     : 머지 커밋이거나 .git/MERGE_MSG가 존재한다
squash    : .git/SQUASH_MSG가 존재한다
commit    : -c / -C / --amend 가 주어졌다  → $3에 커밋 OID가 따라온다
(없음)    : 평범한 git commit (에디터가 뜬다)
bash — 브랜치명에서 이슈 번호 자동 삽입
#!/bin/sh
# .githooks/prepare-commit-msg
msg_file="$1"
source="$2"

# -m 으로 직접 쓴 경우와 머지/스쿼시는 건드리지 않는다
case "$source" in
    merge|squash|commit) exit 0 ;;
esac

branch=$(git symbolic-ref --short HEAD 2>/dev/null) || exit 0
issue=$(printf '%s' "$branch" | grep -oE '[A-Z]{2,}-[0-9]+') || exit 0

# 이미 들어 있으면 중복 삽입하지 않는다
grep -q "$issue" "$msg_file" && exit 0

# 첫 줄 앞에 붙인다
printf '[%s] %s' "$issue" "$(cat "$msg_file")" > "$msg_file.tmp"
mv "$msg_file.tmp" "$msg_file"

Git이 기본 제공하는 샘플 훅들도 참고할 만합니다. 문서에 따르면 기본 pre-commit은 비ASCII 파일명과 줄 끝 공백을 막고(hooks.allownonascii로 조절), 기본 commit-msg는 중복 Signed-off-by 트레일러를 잡아냅니다.

git am 계열 훅도 있던데요?

메일로 패치를 주고받는 워크플로(Linux 커널 방식)를 위한 세 개입니다. 커밋 계열과 대응 관계가 있습니다.

훅인자시점기본 동작
applypatch-msg $1 메시지 파일 패치 적용 전 기본 훅은 commit-msg를 대신 실행
pre-applypatch 없음 패치 적용 후, 커밋 전 기본 훅은 pre-commit을 대신 실행
post-applypatch 없음 커밋 후 알림 전용. 결과에 영향 없음

pre-applypatch의 시점이 재미있습니다. "패치는 이미 워킹 트리에 적용됐지만 커밋은 아직"인 상태라, 워킹 트리를 검사해 커밋을 거부할 수 있습니다. 그래서 기본 훅이 pre-commit을 재활용합니다 — 같은 검증 로직을 두 워크플로에서 공유하는 구조입니다.

Part 2: 워크플로 계열 — 체크아웃 · 머지 · 재작성

브랜치를 오갈 때 불리는 훅들을 정리해 주세요.
훅인자중단 가능?비고
post-checkout $1 이전 HEAD
$2 새 HEAD
$3 플래그(1=브랜치, 0=파일)		 불가
(단 종료 코드가 명령의 종료 코드가 됨)		 clone, worktree add에서도 실행. 이때 $1은 null-ref, $3은 항상 1
post-merge $1 squash 여부(0/1) 불가 충돌로 실패한 머지에서는 실행 안 됨
pre-rebase $1 upstream
$2 대상 브랜치(현재 브랜치 rebase 시 없음)		 가능 공유 브랜치 rebase 차단에 사용
post-rewrite $1 amend 또는 rebase 불가 stdin으로 <old> <new> 목록
pre-auto-gc 없음 가능 (gc --auto 중단) 20편의 자동 GC 억제용
post-index-change $1 워킹 디렉토리 갱신 여부
$2 skip-worktree 변경 가능성		 불가 인덱스가 쓰일 때마다(06편)

post-checkout의 $3 플래그를 반드시 확인해야 합니다. git checkout -- file.txt(파일 복원)에서도 이 훅이 불리는데, 이때 $3이 0입니다. 브랜치 전환에만 반응하고 싶다면 [ "$3" = "1" ] 검사가 필수입니다. 이걸 빠뜨리면 파일 하나 복원할 때마다 npm install이 도는 참사가 납니다.

bash — 브랜치 전환 시 의존성 자동 갱신
#!/bin/sh
# .githooks/post-checkout
prev="$1"; new="$2"; is_branch="$3"

[ "$is_branch" = "1" ] || exit 0          # 파일 체크아웃이면 무시

# lock 파일이 바뀌었을 때만 설치 (13편의 경로 제한 diff)
if ! git diff --quiet "$prev" "$new" -- package-lock.json 2>/dev/null; then
    echo "package-lock.json 변경 감지 → npm ci"
    npm ci
fi

post-rewrite는 19편과 직결됩니다. rebase나 --amend로 커밋 OID가 바뀐 매핑(<old> <new>)을 통째로 받으므로, 외부 시스템(이슈 트래커, 리뷰 도구)에 기록된 옛 OID를 새 OID로 갱신할 수 있습니다.

문서가 rebase에 대해 짚는 세부 사항이 중요합니다. "squash와 fixup 연산에서는 뭉쳐진 모든 커밋이 그 스쿼시 결과 커밋으로 재작성된 것으로 나열된다" — 즉 같은 new-oid를 갖는 줄이 여러 개 나옵니다. 또 "커밋은 rebase가 처리한 순서대로 나열됨이 보장된다"고 명시합니다.

함정: 문서가 "git fast-import나 git-filter-repo 같은 전체 히스토리 재작성 도구는 보통 이 훅을 부르지 않는다"고 경고합니다. 대규모 재작성에서는 post-rewrite에 의존할 수 없습니다.

나머지 특수 훅들은요?

fsmonitor-watchman이 가장 이질적입니다. 검증이 아니라 데이터를 반환하는 훅입니다.

fsmonitor-watchman 프로토콜
입력 (v2):  $1 = 2 (버전),  $2 = 토큰 (watchman의 clock id)
출력:       새 토큰 + NUL + "변경됐을 수 있는 파일 목록" (NUL 구분)

규칙:
  - 경로는 워킹 트리 루트 기준 상대 경로
  - 실제로 안 바뀐 파일을 포함해도 된다 (보수적으로 넓게)
  - 생성·삭제·rename(양쪽 이름 모두) 전부 포함해야 한다
  - "전부 바뀌었다"를 최적화해 알리려면 파일명 "/" 하나를 반환
  - 오류로 종료하면 Git은 전체 검사로 후퇴한다

07편과 직접 연결됩니다. Git은 lstat 비교로 변경을 판정하는데, 파일 수십만 개에서는 그 lstat 자체가 비쌉니다. fsmonitor는 "파일 시스템 감시 데몬이 알려 준 후보만 검사"하게 해 git status를 극적으로 줄입니다. "포함해도 된다(false positive 허용)"는 규칙이 14편의 Bloom filter와 같은 설계 철학입니다.

sendemail-validate는 git send-email용입니다. $1은 메일 본문 파일, $2는 SMTP 헤더 파일이며, 실제 메일은 $2의 내용 뒤에 $1의 내용이 붙은 형태입니다. GIT_SENDEMAIL_FILE_COUNTER/_TOTAL로 "패치 시리즈 전체가 다 왔는지"를 판단할 수 있습니다.

p4-* 네 개(p4-changelist, p4-prepare-changelist, p4-post-changelist, p4-pre-submit)는 git-p4 submit 전용입니다. 커밋 계열과 구조가 그대로 대응합니다 — prepare(초안 작성, --no-verify 우회 불가) → changelist(검증) → post(알림). Perforce 연동을 쓰지 않으면 무시해도 됩니다.

Part 3: 서버 계열 — 진짜 강제력이 있는 자리

push 한 번에 서버에서 훅이 어떤 순서로 불리나요?

receive-pack이 다음 순서로 실행합니다. 거부 가능한 지점이 두 군데라는 점이 핵심입니다.

1. pre-receive
전체에 1회. stdin으로 모든 ref
→ 0이 아니면 전부 거부
→
2. update
ref마다 1회씩. 인자 3개
→ 0이 아니면 그 ref만 거부
→
3. (ref 갱신)
11편의 ref 트랜잭션 수행
4. post-receive
전체에 1회. stdin으로 성공한 ref 목록
→ 결과에 영향 없음
→
5. post-update
인자로 갱신된 ref 이름만
→ 기본 훅은 update-server-info 실행
훅실행 횟수데이터거부 범위
pre-receive 1회 stdin: <old> <new> <ref> 전부 push 전체
update ref 수만큼 인자: $1=ref, $2=old, $3=new 해당 ref 하나
post-receive 1회 (최소 1개 성공 시) stdin: 성공한 ref만 없음
post-update 1회 인자: ref 이름들 (old/new 없음) 없음

문서가 post-update보다 post-receive를 쓰라고 권합니다 — "post-update는 어떤 head가 push됐는지는 알지만 원래 값과 갱신된 값을 모르므로 old..new 로그를 찍기에 나쁜 자리다." post-update는 post-receive가 없던 시절의 유산이고, 지금은 사실상 update-server-info 전용입니다.

update 훅의 용도도 문서가 짚습니다. "특정 ref에 대한 forced update를 막는 데 쓸 수 있다 — 새 객체가 옛 객체의 자손인지 확인해 fast-forward만 허용하는 정책"입니다. 15편의 조상 판정이 그대로 쓰입니다.

bash — fast-forward 전용 정책 (update 훅)
#!/bin/sh
# hooks/update   $1=ref  $2=old  $3=new
ref="$1"; old="$2"; new="$3"
zero=$(git hash-object --stdin -t tree </dev/null | tr '[0-9a-f]' '0')

case "$ref" in
    refs/heads/main|refs/heads/release/*) ;;
    *) exit 0 ;;                                 # 보호 대상만 검사
esac

[ "$new" = "$zero" ] && { echo "보호된 브랜치는 삭제할 수 없습니다." >&2; exit 1; }
[ "$old" = "$zero" ] && exit 0                   # 새로 생성은 허용

# old가 new의 조상이 아니면 = 되감기(force) 시도 (15편)
if ! git merge-base --is-ancestor "$old" "$new"; then
    echo "non-fast-forward push는 $ref 에서 금지됩니다." >&2
    exit 1
fi
서버 훅이 실행될 때 객체는 이미 저장된 상태인가요?

중요한 질문입니다. 답은 "격리(quarantine) 영역에 있다"입니다. git-receive-pack 문서의 "QUARANTINE ENVIRONMENT" 절이 이를 규정합니다.

"receive-pack이 객체를 받으면 $GIT_DIR/objects 안의 임시 '격리' 디렉토리에 두고, pre-receive 훅이 완료된 뒤에야 메인 객체 저장소로 옮긴다. 그 전에 push가 실패하면 임시 디렉토리는 통째로 제거된다."

팩 수신
객체가 격리 디렉토리에 기록됨
→
pre-receive 실행
훅은 격리 객체를 읽을 수 있음
→
성공 → 이관
메인 객체 저장소로 migrate
/
실패 → 폐기
디렉토리째 삭제. 디스크에 아무것도 안 남음

이 설계가 20편의 GC 문제를 우아하게 피합니다. 격리가 없다면 거부된 push의 객체가 도달 불가능한 쓰레기로 계속 쌓이고, 2주 유예 동안 디스크를 차지합니다. 문서의 표현대로 "반복 실패한 push가 디스크를 채우는 것을 막아 주지만, 디버깅은 더 어려워집니다."

훅 작성자가 주의할 점: pre-receive 훅이 만든 객체도 격리 디렉토리에 생성되며, 성공해야만 이관됩니다. 훅에서 객체를 만들어 두고 나중에 쓰려 한다면 이 동작을 반드시 고려해야 합니다.

push-to-checkout은 어떤 상황의 훅인가요?

bare가 아닌 저장소로 push할 때의 문제를 다룹니다. 01편에서 본 receive.denyCurrentBranch가 배경입니다.

체크아웃된 브랜치로 push하면 ref는 바뀌는데 워킹 트리와 인덱스는 그대로라 불일치가 생깁니다. 그래서 Git은 기본적으로 거부합니다. receive.denyCurrentBranch = updateInstead로 설정하면 "워킹 트리까지 같이 갱신"을 시도하는데, 이때 워킹 트리나 인덱스에 차이가 있으면 여전히 거부합니다.

push-to-checkout 훅이 그 기본 동작을 덮어씁니다. 인자로 새 커밋 OID를 받고, 두 가지 중 하나를 해야 합니다.

  • 거부한다 — 0이 아닌 코드로 종료. 단 인덱스와 워킹 트리를 수정하면 안 됩니다.
  • 수용한다 — 워킹 트리와 인덱스를 원하는 상태로 만들고 0으로 종료
문서가 제시하는 구현 예
#!/bin/sh
# hooks/push-to-checkout   $1 = 새 커밋 OID
exec git read-tree -u -m HEAD "$1"

# 2-tree 형태의 read-tree -u -m 은 본질적으로
# "로컬 변경을 유지한 채 브랜치를 전환하는" git switch와 같다.
# 즉 push 방향으로 뒤집힌 git fetch를 흉내 내는 것.

배포 서버에 직접 push해서 즉시 반영하는 워크플로(간단한 정적 사이트 등)에서 쓰입니다. 다만 요즘은 CI/CD로 처리하는 것이 일반적이라, 실무에서 만나기는 드뭅니다.

Part 4: 고급 — proc-receive와 reference-transaction

proc-receive가 특별한 이유가 뭔가요?

다른 훅은 "허가/거부"만 하지만, proc-receive는 ref 갱신을 대신 수행합니다. 문서의 표현입니다.

"서버가 receive.procReceiveRefs를 설정했고 receive-pack에 온 명령의 ref 이름이 매칭되면, 그 명령들은 내부 execute_commands() 함수 대신 이 훅이 실행한다. 이 훅이 관련 ref를 갱신하고 결과를 receive-pack에 보고할 책임을 진다."

Gerrit이나 Gitea에서 git push origin HEAD:refs/for/main 하면 브랜치가 아니라 리뷰가 생성되는 동작이 정확히 이것입니다. refs/for/main은 실제 ref가 아니라 의사 ref(pseudo-reference)이고, 훅이 이를 가로채 전혀 다른 일을 합니다.

다른 훅과 달리 pkt-line 프로토콜(21편)로 양방향 대화합니다.

proc-receive 프로토콜 (S=receive-pack, H=훅)
# 1) 버전·기능 협상
S: PKT-LINE(version=1\0push-options atomic...)
S: flush-pkt
H: PKT-LINE(version=1\0push-options...)
H: flush-pkt

# 2) 서버 → 훅: 처리할 명령들
S: PKT-LINE(<old-oid> <new-oid> <ref>)
S: ... ...
S: flush-pkt
S: PKT-LINE(push-option)          # push-options 기능이 켜진 경우만
S: flush-pkt

# 3) 훅 → 서버: 결과 보고
H: PKT-LINE(ok <ref>)                     # 성공
H: PKT-LINE(ng <ref> <reason>)            # 거부
H: PKT-LINE(ok <ref>)                     # 내가 처리 안 함 —
H: PKT-LINE(option fall-through)          #   receive-pack이 알아서 하라
H: PKT-LINE(ok <ref>)                     # 성공했는데 실제로는
H: PKT-LINE(option refname <refname>)     #   다른 ref를 갱신했다
H: PKT-LINE(option old-oid <old-oid>)
H: PKT-LINE(option new-oid <new-oid>)
H: PKT-LINE(option forced-update)
H: flush-pkt

option refname이 핵심 장치입니다. 클라이언트는 refs/for/main으로 push했지만, 훅은 실제로 refs/changes/34/1234/1 같은 ref를 만들 수 있고, 그 사실을 클라이언트에게 되돌려 보고합니다. 그래서 push 결과 화면에 리뷰 URL이 뜨는 것입니다.

문서가 짚는 세부 규칙 두 가지입니다. "이 훅으로 오는 각 명령은 의사 ref를 가리킬 수 있고 항상 zero-old를 old-oid로 갖지만, 훅은 이미 존재하는(non-zero old-oid) 다른 ref를 갱신할 수 있다." 그리고 "보고 순서는 입력과 같아야 한다."

종료 코드의 의미도 다릅니다 — "훅의 종료 상태는 자신에게 전달된 명령 그룹의 성공/실패만 결정한다(atomic push를 쓰는 경우 제외)." 다른 ref들의 운명에는 영향을 주지 않습니다.

reference-transaction은 얼마나 자주 불리나요?

ref를 바꾸는 모든 명령에서, 그것도 여러 번 불립니다. 11편에서 본 ref 트랜잭션의 각 단계마다 호출되기 때문입니다.

$1 상태시점종료 코드
preparing 모든 갱신이 큐에 들어갔지만 아직 락 전 0이 아니면 트랜잭션 중단
prepared 큐에 들어갔고 디스크에 락까지 획득 0이 아니면 트랜잭션 중단
committed 커밋 완료. 모든 ref가 새 값 무시됨
aborted 중단됨. 변경 없고 락 해제됨 무시됨

문서가 명시하는 규칙입니다 — "종료 상태는 preparing과 prepared를 제외한 모든 상태에서 무시된다. 이 두 상태에서 0이 아닌 종료는 트랜잭션을 중단시킨다. 그 경우 훅은 aborted 상태로 호출되지 않는다."

stdin 포맷은 익숙한 삼종 세트이지만, symbolic ref를 위한 확장이 있습니다.

reference-transaction의 stdin
<old-value> SP <new-value> SP <ref-name> LF

특수 규칙:
  - 강제 갱신이거나 새로 생성이면 <old-value>는 all-zeroes
    → 둘을 구분하려면 git rev-parse로 현재 값을 직접 확인해야 한다
  - symbolic ref 갱신이면 값이 객체가 아니라 ref일 수 있고,
    "ref:" 접두사가 붙는다  (예: ref:refs/heads/main)
  - "preparing" 상태에서는 symbolic ref가 해석되지 않는다
    → <ref-name>은 가리키는 대상이 아니라 symbolic ref 자신
bash — 완전한 ref 감사 로그
#!/bin/sh
# hooks/reference-transaction
[ "$1" = "committed" ] || exit 0          # 실제로 반영된 것만 기록

ts=$(date -Is)
who=$(git config user.email 2>/dev/null || echo unknown)
cmd="${GIT_REFLOG_ACTION:-unknown}"       # 어떤 작업이었는지 힌트

while read old new ref; do
    printf '%s\t%s\t%s\t%s\t%s -> %s\n' \
        "$ts" "$who" "$cmd" "$ref" "$old" "$new" >> /var/log/git-refs.log
done

성능 주의가 필요합니다. commit, merge, rebase, fetch, reset, gc까지 거의 모든 명령에서, 그것도 상태마다 불립니다. 대량 fetch에서는 수천 번 호출될 수 있으므로 무거운 작업(네트워크 호출 등)을 넣으면 체감 성능이 즉시 무너집니다. 파일에 append하는 정도로 끝내고, 집계는 별도 프로세스가 하도록 설계해야 합니다.

이 훅의 진가는 규제 대응입니다. reflog(11편)는 로컬에만 있고 만료되며 bare 저장소에는 기본적으로 없지만, reference-transaction은 서버에서 모든 ref 변경을 빠짐없이 외부 로그로 뽑아낼 수 있습니다. "누가 언제 어떤 브랜치를 되감았는가"를 증명해야 하는 환경에서 유일한 수단에 가깝습니다.

📌 핵심 정리

  • 커밋 하나에 최대 4개(pre-commit → prepare-commit-msg → commit-msg → post-commit)가 순서대로 불린다. 메시지 초안은 prepare-commit-msg(--no-verify로 우회 안 됨), 검증은 commit-msg에 넣는다.
  • post-checkout은 파일 복원($3=0)에서도 불리므로 $3 검사가 필수이고, 종료 코드가 명령의 종료 코드가 된다. post-rewrite는 rebase/amend의 old→new 매핑을 주지만 filter-repo 같은 도구는 호출하지 않는다.
  • 서버 훅은 pre-receive(전체 1회, 전부 거부) → update(ref마다, 해당 ref만 거부) → post-receive(성공 ref만) → post-update(이름만) 순이다. old/new가 필요하면 post-update가 아니라 post-receive를 쓴다.
  • 수신 객체는 격리(quarantine) 디렉토리에 들어갔다가 pre-receive 성공 후에야 이관된다. 실패한 push는 디스크에 아무것도 남기지 않으며, 훅이 만든 객체도 같은 규칙을 따른다.
  • proc-receive는 pkt-line 프로토콜로 ref 갱신을 대신 수행해 refs/for/* 같은 의사 ref를 리뷰 생성으로 바꾸고, reference-transaction은 모든 ref 변경을 4단계로 관측해 완전한 감사 로그를 만든다. 후자는 호출 빈도가 매우 높아 가벼워야 한다.
