git log는 어떤 순서로 커밋을 뱉을까?

리비전 워크 해부 — 우선순위 큐 · UNINTERESTING 전파 · TREESAME과 히스토리 단순화

Part 1: DAG를 "목록"으로 펴는 문제

커밋 그래프는 DAG인데 git log는 일렬로 출력합니다. 순서는 누가 정하나요?

리비전 워크(revision walk)라는 Git의 핵심 엔진이 정합니다. revision.c가 그 구현이고, log, rev-list, bisect, blame, pack-objects, fetch의 네고시에이션까지 전부 이 엔진 위에 얹혀 있습니다.

문제의 본질은 이렇습니다. DAG에는 "올바른 순서"가 유일하지 않습니다. 두 브랜치가 갈라진 구간의 커밋들은 서로 조상 관계가 없으므로 어느 쪽을 먼저 보여 줘도 위상적으로 정당합니다.

A
←
B
←
C1, C2 (브랜치 1)
←
M
 
 
 
 
D1, D2 (브랜치 2)
←
 

C1, C2, D1, D2를 어떤 순서로 보여 줄지는 정책의 문제입니다. Git은 기본적으로 커밋 날짜 내림차순을 택하고, --topo-order, --author-date-order, --reverse로 바꿀 수 있게 열어 두었습니다.

🎯 비유로 이해하기

여러 지류가 합쳐지는 강을 하구에서 거슬러 오르는 상황입니다.

갈림길을 만나면 두 지류 중 어디로 갈지 골라야 합니다. Git의 기본 전략은 "지금 눈앞의 후보들 중 가장 최근에 비가 온 지류부터"(커밋 날짜순)입니다. --topo-order는 "한 지류를 끝까지 따라간 뒤 다른 지류로"로 정책을 바꿉니다.

실제 알고리즘은 어떻게 되나요?

우선순위 큐를 쓰는 BFS 변형입니다. 소스의 자료구조가 그대로 드러납니다.

revision.c — 우선순위 큐
struct prio_queue queue = { .compare = compare_commits_by_commit_date };

기본 흐름은 네 단계입니다.

1. 시드 투입
시작 ref들(HEAD, 지정한 리비전)을 큐에 넣는다
→
2. 최우선 꺼내기
커밋 날짜가 가장 최근인 것을 큐에서 뺀다
→
3. 출력 + 부모 투입
조건을 만족하면 출력하고, 부모들을 큐에 넣는다(SEEN 표시)
→
4. 반복
큐가 비거나 중단 조건까지 2~3 반복

여기서 중요한 함정이 있습니다. 커밋 날짜는 신뢰할 수 없습니다. 05편에서 봤듯 rebase·cherry-pick은 committer date를 바꾸고, 시계가 틀린 머신에서 만든 커밋은 부모보다 이른 날짜를 가질 수 있습니다. 그래서 날짜순 워크는 위상 순서를 보장하지 못합니다 — 자식이 부모보다 먼저 출력되는 일이 드물게 발생합니다.

--topo-order는 이를 해결하지만 대가가 있습니다. "이 커밋의 모든 자식을 출력했는가"를 알아야 하므로, 출력 전에 그래프를 미리 훑어야 합니다. 그래서 첫 출력까지의 지연이 커집니다.

Git은 이 비용을 commit-graph의 generation number로 줄입니다. 소스에서 topo-order의 탐색 큐는 compare_commits_by_gen_then_commit_date를 씁니다 — 날짜가 아니라 세대 번호를 1순위로 삼는 것입니다(14편).

Part 2: UNINTERESTING — 범위 표기의 실체

main..feature는 내부적으로 어떻게 계산되나요?

플래그 전파로 계산합니다. revision.h의 비트 플래그가 워크의 상태 기계를 이룹니다.

revision.h — 워크 플래그
#define SEEN            (1u<<0)   /* 큐에 이미 들어갔음 */
#define UNINTERESTING   (1u<<1)   /* 이 커밋과 그 조상은 제외 */
#define TREESAME        (1u<<2)   /* 부모와 (관심 경로의) 트리가 동일 */
#define SHOWN           (1u<<3)   /* 이미 출력했음 */
#define ADDED           (1u<<7)   /* 부모를 이미 파싱해 큐에 넣었음 */
#define BOTTOM          (1u<<10)  /* 워크의 바닥 경계 */

main..feature는 ^main feature와 같습니다. ^가 붙은 것이 UNINTERESTING 시드입니다.

1. 시드 표시
feature는 관심(interesting), main은 UNINTERESTING
→
2. 전파
UNINTERESTING 커밋의 부모도 전부 UNINTERESTING
→
3. 출력 필터
플래그가 없는 커밋만 출력
→
4. 조기 종료
큐에 남은 것이 전부 UNINTERESTING이면 그만둔다

4번이 성능의 핵심입니다. main..feature에 커밋 5개만 있다면, Git은 저장소 전체 히스토리를 훑지 않고 공통 조상 언저리에서 멈춥니다. 커밋 100만 개짜리 저장소에서도 이 질의는 즉시 끝납니다.

bash — 범위 표기의 등가 형태
# 이 셋은 전부 같다
$ git log main..feature
$ git log ^main feature
$ git rev-list feature --not main

# 대칭 차집합: 양쪽에 각자 있는 것
$ git log main...feature          # = (A∪B) - (A∩B)
$ git log --left-right main...feature
< abc1234 main에만 있음           # < = 왼쪽(main)
> def5678 feature에만 있음        # > = 오른쪽(feature)

# 여러 개도 가능
$ git log ^main ^develop feature  # main과 develop 어디에도 없는 feature의 커밋

# 실전: "아직 푸시 안 한 내 커밋"
$ git log @{u}..HEAD              # @{u} = upstream
# 실전: "원격에 있는데 아직 안 받은 커밋"
$ git log HEAD..@{u}
이 메커니즘이 다른 곳에도 쓰이나요?

Git의 거의 모든 핵심 연산이 이 위에 있습니다.

연산리비전 워크를 어떻게 쓰나
git push "원격이 가진 것"을 UNINTERESTING으로 두고 워크 → 보낼 객체 확정
git fetch 네고시에이션으로 얻은 공통 커밋을 UNINTERESTING으로 두고 받을 범위 계산 (21편)
git gc 모든 ref + reflog를 시드로 워크 → 도달 가능한 객체 집합 확정 (20편)
git bisect good..bad 범위를 워크해 후보 집합을 만들고 그 안에서 이분 탐색
git merge-base 양방향 플래그 전파의 특수 형태 (15편)

git rev-list가 이 엔진의 날것 그대로의 인터페이스입니다. git log는 여기에 포매팅을 씌운 것이고, 스크립트를 짤 때는 rev-list를 직접 쓰는 것이 훨씬 빠르고 안정적입니다.

bash — rev-list 활용
# 커밋 개수만 (로그 포매팅 비용 없음)
$ git rev-list --count main..feature
17

# 도달 가능한 모든 객체 (경로까지)
$ git rev-list --objects --all | head
c0ffee1...
a1b2c3d... src
d4e5f6a... src/main.c

# 릴리스 노트용: main 줄기의 머지 커밋만
$ git rev-list --first-parent --merges v1.0..v2.0 --format='%s'

# 특정 파일을 건드린 커밋
$ git rev-list HEAD -- src/auth.c

Part 3: 경로 필터와 히스토리 단순화

git log -- src/auth.c를 하면 머지 커밋이 안 보입니다. 버그인가요?

버그가 아니라 기본 동작인 "히스토리 단순화(history simplification)"입니다. 이 동작을 모르면 "커밋이 사라졌다"는 오해를 하게 됩니다.

경로를 지정하면 Git은 각 커밋마다 "이 경로의 트리가 부모와 같은가"를 검사해 TREESAME 플래그를 답니다. 그리고 기본 규칙은 이렇습니다.

단순화 규칙
일반 커밋 (부모 1개):
  TREESAME  → 출력하지 않음. 부모로 대체해 계속 진행
  다름      → 출력

머지 커밋 (부모 여러 개):
  어느 한 부모와라도 TREESAME이면
      → 그 부모 쪽만 따라가고, 나머지 부모 방향은 통째로 버린다
  모든 부모와 다르면
      → 출력하고 모든 부모를 따라간다

머지 규칙이 강력한 부작용을 냅니다. feature 브랜치에서 src/auth.c를 고쳤고 main에서는 안 고쳤다면, 머지 커밋은 main 쪽 부모와 TREESAME이 아니고 feature 쪽 결과와 같습니다. 그런데 머지가 "feature 쪽 내용을 그대로 취한" 경우라면 feature 부모와 TREESAME이 되어, Git은 feature 방향만 따라가고 main 방향을 잘라냅니다. 반대 상황에서는 feature 쪽 커밋들이 통째로 보이지 않게 됩니다.

bash — 단순화 제어
# 기본 (단순화 적용) — 커밋이 "사라져" 보일 수 있다
$ git log --oneline -- src/auth.c

# 모든 커밋을 보고 싶다 (단순화 끄기)
$ git log --full-history --oneline -- src/auth.c

# 머지의 어느 쪽에서 왔는지 그래프로 확인
$ git log --full-history --graph --oneline -- src/auth.c

# 파일이 삭제된 시점 찾기 (자주 쓰는 패턴)
$ git log --full-history --diff-filter=D --oneline -- src/auth.c

# rename을 따라 끝까지 추적
$ git log --follow --oneline -- src/auth.c

실무 규칙: "파일 하나의 진짜 이력을 조사할 때는 --full-history를 붙이십시오." 기본 단순화는 "이 파일이 지금 모습이 된 대표 경로"를 보여 주는 것이지, 완전한 이력이 아닙니다. 장애 조사에서 결정적 커밋을 놓치는 흔한 원인입니다.

--follow는 왜 파일 하나에만 쓸 수 있나요?

rename 감지가 조회 시점 추론이기 때문입니다(17편). Git은 "이 파일이 저 파일에서 이름이 바뀌었다"를 저장하지 않습니다. 커밋마다 두 트리를 비교해 유사도로 추측할 뿐입니다.

--follow는 워크 도중 "경로가 사라진 커밋"을 만나면 그 커밋의 diff에서 rename을 찾아 추적 대상 경로를 바꿔치기합니다. 경로가 여러 개면 각각을 독립적으로 바꿔치기해야 하는데, 워크 상태가 경로 집합 전체에 걸려 있어 구현이 복잡해집니다. 그래서 Git은 경로 하나로 제한합니다.

--follow는 근사입니다. 파일 내용이 rename과 동시에 크게 바뀌면(유사도 50% 미만) 추적이 끊깁니다. 정확한 추적이 필요하면 git log --find-renames=30% --full-history처럼 임계값을 낮추거나, git log -S'함수이름'으로 내용 기반으로 찾는 편이 낫습니다.

bash — 내용 기반 탐색 (pickaxe)
# -S: 이 문자열의 "등장 횟수가 바뀐" 커밋을 찾는다 (추가/삭제 시점)
$ git log -S'ValidateToken' --oneline
a1b2c3d refactor: 인증 로직 분리
f7d3c0e feat: 토큰 검증 추가

# -G: 이 정규식에 매치되는 줄이 diff에 등장한 커밋 (수정 시점까지 포함)
$ git log -G'ValidateToken\s*\(' --oneline

# 경로 제한 없이 저장소 전체에서 찾으므로 rename에 영향받지 않는다
# 장애 조사에서 --follow보다 신뢰할 만한 경우가 많다

Part 4: 정렬 옵션과 성능 튜닝

정렬 옵션들은 정확히 뭐가 다른가요?
옵션순서 기준특징
(기본) committer date 내림차순 빠름. 첫 결과가 즉시 나옴. 위상 순서 보장 안 됨
--date-order 날짜순이되 부모를 자식보다 먼저 보이지 않게 기본과 위상 정렬의 절충
--author-date-order author date 기준 rebase가 많은 저장소에서 "실제 작성 순서"에 가까움
--topo-order 순수 위상 정렬. 한 갈래를 끝낸 뒤 다음 갈래 브랜치가 섞이지 않아 읽기 좋음. 선행 탐색 비용
--reverse 결과를 뒤집음 전체를 다 계산한 뒤 뒤집으므로 -n과 조합 시 주의
--first-parent 머지의 첫 부모만 따라감 PR 단위 히스토리. 릴리스 노트에 최적

--reverse -n 10은 함정입니다. "가장 오래된 10개"가 아니라 "최신 10개를 뒤집은 것"입니다. Git이 -n을 먼저 적용하고 --reverse를 나중에 하기 때문입니다. 가장 오래된 10개를 원하면 git log --reverse | head -10처럼 파이프를 쓰거나 git rev-list --max-parents=0 계열을 씁니다.

bash — 정렬 차이 확인
# 브랜치가 섞여 읽기 어려운 기본 출력
$ git log --oneline --graph -15

# 갈래별로 모여 읽기 좋은 위상 정렬
$ git log --oneline --graph --topo-order -15

# main 줄기만 (머지 내부 무시) - 릴리스 노트용
$ git log --oneline --first-parent v1.0..v2.0

# 루트 커밋 찾기
$ git rev-list --max-parents=0 HEAD

# 머지 커밋만 / 머지 아닌 것만
$ git log --merges --oneline
$ git log --no-merges --oneline
대형 저장소에서 git log가 느릴 때는 어떻게 하나요?

느려지는 원인이 세 가지로 나뉘고, 처방이 각각 다릅니다.

증상원인처방
git log 자체가 느림 커밋 객체를 하나씩 압축 해제하며 파싱 commit-graph (14편). 파싱 없이 이진 데이터에서 부모/날짜를 읽음
--topo-order가 느림 선행 탐색 범위가 넓음 commit-graph의 generation number가 탐색을 조기 종료시킴
log -- path/가 느림 커밋마다 트리를 비교해 TREESAME 판정 changed-path Bloom filter. "이 커밋이 이 경로를 건드렸을 리 없다"를 즉시 배제
bash — 세 가지를 한 번에 해결
# commit-graph + Bloom filter 생성
$ git commit-graph write --reachable --changed-paths

# 효과 측정 (모노레포 실측 예)
$ time git log --oneline -- services/payment/ | wc -l
# 전: 18.4s  →  후: 0.6s

# 자동 유지: fetch 후 자동 갱신
$ git config fetch.writeCommitGraph true
$ git maintenance start        # commit-graph, MIDX, prune 등을 주기적으로 갱신

# 진단: 어디서 시간을 쓰는지
$ GIT_TRACE2_PERF=1 git log --oneline -- services/payment/ 2>&1 | head -30

정리하면 리비전 워크의 성능은 "그래프 탐색 비용"과 "커밋 파싱 비용"의 합입니다. commit-graph가 후자를 없애고 generation number가 전자를 줄이며, Bloom filter가 경로 필터의 트리 비교를 건너뜁니다. 이 셋이 대형 저장소 성능 개선의 표준 패키지이고, 다음 편의 주제입니다.

📌 핵심 정리

  • 리비전 워크는 우선순위 큐 기반 그래프 순회다. 기본 키는 committer date 내림차순인데, 날짜는 rebase나 시계 오차로 신뢰할 수 없어 위상 순서를 보장하지 않는다.
  • A..B는 ^A B이고, ^는 UNINTERESTING 플래그를 부모로 전파한다. 큐가 전부 UNINTERESTING이 되면 조기 종료하므로 거대 저장소에서도 범위 질의가 즉시 끝난다.
  • push·fetch·gc·bisect·merge-base가 모두 이 엔진 위에 있다. git rev-list가 날것의 인터페이스이며, 스크립트에는 log보다 rev-list가 적합하다.
  • 경로를 주면 기본으로 히스토리 단순화가 걸린다. 머지 커밋이 어느 한 부모와 TREESAME이면 나머지 부모 방향을 통째로 버리므로, 진짜 이력 조사에는 --full-history가 필요하다.
  • 성능은 commit-graph(파싱 제거) + generation number(탐색 조기 종료) + changed-path Bloom filter(트리 비교 생략)로 해결한다. git commit-graph write --reachable --changed-paths가 표준 처방이다.
