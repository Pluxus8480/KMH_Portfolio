공통 조상은 하나가 아닐 수 있다

merge-base 계산 해부 — PARENT1/PARENT2 페인팅 · STALE 전파 · criss-cross 머지

Part 1: 왜 공통 조상이 필요한가

머지할 때 "공통 조상"을 찾는다고 하는데, 왜 필요한가요?

3-way merge의 기준점이기 때문입니다. 두 버전만 놓고는 "누가 무엇을 바꿨는지" 알 수 없습니다.

2-way vs 3-way
[2-way — 판단 불가]
  ours   : int timeout = 30;
  theirs : int timeout = 60;
  → 어느 쪽이 "바꾼" 쪽인가? 알 수 없다. 무조건 충돌.

[3-way — 판단 가능]
  base   : int timeout = 30;
  ours   : int timeout = 30;    ← base와 같음 = 안 건드림
  theirs : int timeout = 60;    ← base와 다름 = theirs가 변경함
  → theirs를 채택. 충돌 없음.

즉 base는 "누가 변경의 주체인가"를 판정하는 기준입니다. 이것이 Git 머지가 SVN 초기 버전보다 압도적으로 강했던 이유이고, 브랜치를 자유롭게 쓸 수 있게 만든 토대입니다.

🎯 비유로 이해하기

두 사람이 같은 계약서를 각자 수정해 왔습니다. 두 사본만 비교하면 어느 조항이 누구의 수정인지 알 수 없어 전부 다툼거리가 됩니다.

여기에 원본을 한 부 놓으면 상황이 달라집니다. "3조는 A만 고쳤네, A안 채택", "7조는 B만 고쳤네, B안 채택", "12조는 둘 다 다르게 고쳤네 — 이것만 상의합시다". 논의할 항목이 극적으로 줄어듭니다.

공통 조상이 여러 개일 수 있다는 게 무슨 뜻인가요?

merge-base의 정의를 정확히 보면 답이 나옵니다. Git 문서의 정의입니다.

"merge base는 공통 조상 중에서, 다른 공통 조상의 조상이 아닌 것이다."

조상은 루트까지 내려가면 무수히 많지만, 그중 "가장 가까운" 것들만 의미가 있습니다. 그런데 "가장 가까운"이 유일하지 않을 수 있습니다.

전형적인 사례가 criss-cross 머지입니다.

criss-cross 구조
        A ------ C ------ E   (branch1)
       / \      /
      O   X----/
       \ / \
        B ------ D ------ F   (branch2)

O에서 A와 B가 갈라진 뒤
  C는 A와 B를 머지 (부모 = A, B)
  D도 A와 B를 머지 (부모 = B, A)

E와 F의 공통 조상은?
  A도 공통 조상, B도 공통 조상.
  그런데 A는 B의 조상이 아니고, B도 A의 조상이 아니다.
  ⇒ merge base가 두 개

현실에서 criss-cross는 생각보다 자주 생깁니다. 두 개발자가 서로의 브랜치를 상호 머지하거나, hotfix를 여러 릴리스 브랜치에 각각 머지했다가 다시 합칠 때 발생합니다.

bash — 여러 merge base 확인
$ git merge-base branch1 branch2
a1b2c3d...                    # 기본은 하나만 출력

$ git merge-base --all branch1 branch2
a1b2c3d...
e5f6a7b...                    # ← 두 개!

# 조상 여부만 묻기 (종료 코드로 답함)
$ git merge-base --is-ancestor v1.0 HEAD && echo "v1.0은 HEAD의 조상"

# 브랜치가 갈라진 지점 (fork point) — reflog까지 참조
$ git merge-base --fork-point main feature

merge base가 여러 개일 때 Git의 기본 전략(recursive, 지금은 ort)은 "merge base들을 서로 머지해서 가상의 단일 base를 만드는" 방식입니다. 재귀적으로 이루어지므로 이름이 "recursive"였습니다. 자세한 내용은 18편에서 다룹니다.

Part 2: paint_down_to_common — 두 색으로 칠하기

실제 알고리즘은 어떻게 동작하나요?

commit-reach.c의 paint_down_to_common()이 담당합니다. 이름 그대로 "공통 지점까지 내려가며 색칠한다"입니다.

두 가지 색(플래그)
PARENT1 : 커밋 one 에서 도달 가능
PARENT2 : 커밋 twos[] 중 하나에서 도달 가능
STALE   : 이 커밋은 (또는 그 조상은) 이미 "더 나은" 후보에 가려졌다
1. 시드 색칠
one에 PARENT1, twos[]에 PARENT2를 칠해 우선순위 큐에 투입
→
2. 최우선 꺼내기
세대 번호 내림차순, 동률이면 커밋 날짜순으로 가장 앞선 것
→
3. 색 전파
자신의 플래그를 부모에게 물려주고, 새 플래그를 얻은 부모를 큐에 넣음
→
4. 양쪽 색을 다 받으면
merge base 후보로 등록하고 STALE을 붙여 그 조상들도 낡은 것으로 전파

4번의 STALE 전파가 정의를 직접 구현합니다. "더 깊은 공통 조상은 필연적으로 불필요(redundant)하다"는 것이 merge base의 정의이므로, 후보를 찾는 즉시 그 조상 전체를 낡은 것으로 표시하면 자동으로 걸러집니다.

🎯 비유로 이해하기

강의 두 지류를 각각 빨간 염료와 파란 염료로 물들이며 하류에서 상류로 거슬러 오릅니다.

어느 지점에서 보라색이 되면 그곳이 두 물길이 만나는 합류점(공통 조상)입니다. 그 위쪽은 당연히 전부 보라색일 테니 더 볼 필요가 없다고 표시(STALE)하고 탐색을 접습니다.

큐의 우선순위를 세대 번호로 하는 이유는요?

14편의 성질을 그대로 활용하기 위해서입니다. 세대가 큰 것부터 처리하면 "자식이 부모보다 먼저" 처리되는 것이 보장됩니다.

Git 문서는 커밋을 두 영역으로 나눠 설명합니다.

영역세대 값큐 순서성질
정렬된 영역
(ordered)		 유한하고 포화되지 않음 위상 순서 보장 자식의 세대가 부모보다 엄격히 큼. 꺼낸 커밋의 색은 최종 확정
비정렬 영역
(unordered)		 INFINITY 또는 V1_MAX 커밋 날짜 휴리스틱 부모·자식이 같은 세대일 수 있음. 꺼낸 커밋이 나중에 색을 더 얻을 수 있음

비정렬 영역의 세대 값이 정렬된 영역보다 크므로, 탐색은 비정렬 → 정렬 방향으로만 이동하고 그 반대는 없습니다. commit-graph가 아예 없으면 모든 커밋이 INFINITY라 전 구간이 비정렬 영역이 되고, 날짜 휴리스틱만으로 동작합니다 — 느리지만 여전히 정확합니다.

중요한 안전 장치: 플래그는 추가만 되고 제거되지 않습니다. 이 단조성이 "한 커밋이 큐에 다시 들어가는 횟수"에 상한을 두어 알고리즘의 종료를 보장합니다.

Part 3: 언제 멈추는가 — 다섯 가지 종료 조건

탐색을 끝내는 조건은 뭔가요?

Git 문서가 다섯 가지를 명시합니다. 각각이 서로 다른 최적화 기회를 잡습니다.

조건내용왜 안전한가
1. 큐가 빔 더 볼 것이 없음 자명
2. 전부 STALE 큐에 남은 것이 모두 낡음 새 후보가 나오려면 양쪽에서 낡지 않은 커밋이 만나야 하는데 불가능. 기존 후보 간의 중복 제거는 remove_redundant()가 사후에 처리
3. 세대 컷오프 꺼낸 커밋의 세대가 min_generation 미만 호출자(주로 remove_redundant())가 "입력들 사이의 도달 가능성만" 알면 되는 경우, 그보다 깊이 갈 필요 없음
4. 단일 결과 base 하나만 필요한데 하나 찾았고, 정렬된 영역에 진입함 세대 정렬이 자식을 먼저 방문시키므로, 첫 후보가 곧 가장 세대가 높은 공통 조상. 남은 것이 이 후보의 자손일 수 없음
5. 한쪽 소진 순수 PARENT1이나 순수 PARENT2가 남지 않고, 대기 중 후보도 없으며, 정렬된 영역임 새 후보는 양쪽이 만나야 생기는데 한쪽이 없음

4번과 5번이 "정렬된 영역"을 조건으로 다는 이유가 핵심입니다. 비정렬 영역에서는 뒤늦게 색이 전파되어 소진된 줄 알았던 쪽이 되살아날 수 있습니다. 그래서 이 최적화들은 세대 정렬이 보장되는 구간에서만 활성화됩니다.

문서는 포화 경계도 짚습니다. 조기 종료 게이트는 v1 그래프면 GENERATION_NUMBER_V1_MAX, v2면 GENERATION_NUMBER_INFINITY와 비교해, 포화된 커밋을 "비정렬"로 취급합니다. 세대 값이 상한에 붙어 버리면 부등식이 더 이상 정보를 주지 못하기 때문입니다.

두 가지 용도가 같은 알고리즘을 쓴다고 하던데요?

Git 문서가 명시적으로 구분합니다.

용도질문호출하는 곳
1. 모든 merge base 찾기 "공통 조상 중 다른 것의 조상이 아닌 것들은?" merge-base --all, merge-tree, merge, rebase
2. 조상 판정 "A가 B의 조상인가?" in_merge_bases, merge-base --is-ancestor, branch -d, fetch

2번이 1번으로 환원되는 논리가 우아합니다. 문서의 설명입니다. "공통 조상 중 하나가 입력 중 하나와 같다면, 그 입력이 필연적으로 유일한 merge base다. 다른 어떤 공통 조상도 그만큼 최신이면서 그것의 조상이 아닐 수는 없기 때문이다."

그래서 git branch -d feature가 "머지되지 않았다"며 거부하는 판정이 바로 이 알고리즘입니다. merge-base(feature, HEAD) == feature이면 feature는 이미 HEAD에 포함된 것이므로 안전하게 지울 수 있습니다.

bash — 조상 판정 활용
# 이 브랜치가 main에 머지되었나?
$ git merge-base --is-ancestor feature main && echo "머지됨"

# 머지된 브랜치 일괄 정리
$ git branch --merged main | grep -v -E '^\*|main' | xargs -r git branch -d

# 태그가 특정 커밋을 포함하나? (이 수정이 어느 릴리스에 들어갔나)
$ git tag --contains a1b2c3d
v2.3.0
v2.4.0

# 반대로: 이 커밋이 어느 브랜치들에 들어 있나
$ git branch -a --contains a1b2c3d

--merged/--contains는 squash merge나 rebase로 합쳐진 브랜치를 잡아내지 못합니다. 커밋 OID가 바뀌므로 조상 관계가 성립하지 않기 때문입니다. squash 기반 워크플로에서는 git cherry나 patch-id 비교(19편)를 써야 합니다.

Part 4: 실전 — criss-cross와 fork-point

merge base가 여러 개면 머지 결과가 이상해질 수 있나요?

그럴 수 있습니다. 여러 base를 하나로 합치는 과정에서 가상 base 자체가 충돌을 포함할 수 있기 때문입니다.

bash — criss-cross 상황 진단
$ git merge feature
Auto-merging src/config.c
CONFLICT (content): Merge conflict in src/config.c

# base가 몇 개인지 확인
$ git merge-base --all HEAD MERGE_HEAD
a1b2c3d...
e5f6a7b...                    # ← 2개. criss-cross다

# 가상 base 때문에 충돌 마커가 이상해 보일 수 있다.
# 각 base 기준으로 개별 비교해 보면 상황이 명확해진다
$ git diff a1b2c3d HEAD -- src/config.c
$ git diff e5f6a7b HEAD -- src/config.c

# diff3 스타일로 base 내용까지 보이게 하면 훨씬 판단하기 쉽다
$ git config merge.conflictStyle zdiff3
$ git checkout --conflict=zdiff3 src/config.c

merge.conflictStyle = zdiff3은 실무에서 반드시 켜 둘 만한 설정입니다. 기본 merge 스타일은 ours/theirs만 보여 주지만, zdiff3은 base 내용까지 함께 보여 줍니다. "누가 무엇을 바꿨는가"를 사람이 직접 판단할 수 있게 되어, 충돌 해결 품질이 크게 올라갑니다.

충돌 마커 비교
[merge 스타일 — 기본]
<<<<<<< HEAD
int timeout = 30;
=======
int timeout = 60;
>>>>>>> feature

[zdiff3 스타일 — base가 보임]
<<<<<<< HEAD
int timeout = 30;
||||||| base
int timeout = 45;          ← 원래 45였다! 둘 다 바꾼 것이다
=======
int timeout = 60;
>>>>>>> feature
--fork-point는 일반 merge-base와 뭐가 다른가요?

reflog까지 참조한다는 점이 결정적으로 다릅니다.

상황을 그려 보겠습니다. main에서 feature를 땄는데, 그 사이 누군가 main을 강제로 되감았습니다(force push나 reset). 이제 feature가 갈라져 나온 그 커밋은 현재 main의 조상이 아닙니다. 순수 merge-base는 훨씬 아래의 엉뚱한 지점을 답합니다.

--fork-point는 main의 reflog에 기록된 과거 위치들을 후보에 넣어, "feature가 실제로 갈라져 나온 시점"을 찾아냅니다.

bash — fork-point가 필요한 상황
# main이 되감긴 뒤
$ git merge-base main feature
0000aaa...                    # 너무 오래된 지점 — rebase하면 남의 커밋까지 끌려온다

$ git merge-base --fork-point main feature
f7d3c0e...                    # main의 reflog에서 찾은 "실제로 갈라진 지점"

# rebase가 내부적으로 쓰는 것이 이것이다
$ git rebase main feature              # --fork-point가 기본 동작(인자 형태에 따라 다름)
$ git rebase --no-fork-point main feature   # 끄고 싶다면

한계가 명확합니다. reflog에 의존하므로 다른 머신에서는 동작하지 않고, reflog가 만료되면(기본 90일) 정보가 사라집니다. 또 11편에서 봤듯 bare 저장소에는 reflog가 기본적으로 없습니다. CI에서 --fork-point가 로컬과 다르게 동작하는 원인이 여기 있습니다.

실무 권장: CI 스크립트에서는 --fork-point에 의존하지 말고, 비교 대상 base를 명시적으로 지정하십시오. git rebase --onto <base> <upstream>처럼 셋을 직접 주면 reflog 상태와 무관하게 재현 가능합니다.

bash — 재현 가능한 CI 패턴
# ❌ 환경에 따라 결과가 달라짐
$ git rebase main

# ✅ base를 명시 — 어디서 돌려도 같은 결과
$ BASE=$(git merge-base origin/main HEAD)
$ git rebase --onto origin/main "$BASE" HEAD

# PR의 변경분만 정확히 보기 (3점 표기 + merge-base)
$ git diff origin/main...HEAD          # = git diff $(git merge-base origin/main HEAD) HEAD

git diff A...B(점 세 개)가 git diff $(git merge-base A B) B의 축약이라는 점은 특히 유용합니다. PR 리뷰에서 "내가 바꾼 것만" 보고 싶을 때, 점 두 개(A..B)를 쓰면 그 사이 main에 들어온 남의 변경까지 섞여 보입니다. 점 세 개를 쓰십시오.

📌 핵심 정리

  • merge base는 "공통 조상 중 다른 공통 조상의 조상이 아닌 것"이며, 여러 개일 수 있다. criss-cross 머지에서 흔히 발생하고, ort 전략은 base들을 서로 머지해 가상 base를 만든다.
  • paint_down_to_common()은 PARENT1/PARENT2 두 색을 부모로 전파하고, 양쪽 색을 모두 받은 커밋을 후보로 등록한 뒤 STALE을 전파한다. "더 깊은 공통 조상은 불필요"라는 정의를 그대로 구현한 것이다.
  • 큐는 세대 번호 내림차순(동률이면 날짜)이다. 세대가 유효한 "정렬된 영역"에서는 색이 방문 시점에 확정되지만, INFINITY/V1_MAX인 "비정렬 영역"에서는 뒤늦게 색이 더해질 수 있어 조기 종료 최적화가 비활성화된다.
  • 종료 조건은 다섯 가지다. 큐 비움 · 전부 STALE · 세대 컷오프 · 단일 결과(정렬 영역) · 한쪽 소진(정렬 영역). 뒤 둘은 정렬된 영역에서만 안전하다.
  • 조상 판정(branch -d, --contains)도 같은 알고리즘이다. 다만 squash/rebase로 합쳐진 브랜치는 OID가 달라 잡히지 않으며, --fork-point는 reflog에 의존하므로 CI에서는 base를 명시하는 편이 안전하다.
