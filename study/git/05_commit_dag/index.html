커밋은 변경사항이 아니다

커밋 객체의 텍스트 구조 · author와 committer의 차이 · 태그 · DAG 표기법

Part 1: 커밋 객체는 그냥 텍스트다

커밋 객체 안에는 diff가 들어 있나요?

들어 있지 않습니다. 이것이 Git에 대한 가장 흔한 오해입니다. 커밋 객체에는 diff가 없고, 그 시점의 루트 트리 OID 하나와 부모 커밋 OID들, 그리고 메타데이터만 있습니다.

git show가 보여 주는 diff는 저장된 것이 아니라 조회할 때마다 부모 트리와 현재 트리를 비교해 즉석에서 계산한 결과입니다. 그래서 같은 커밋이라도 -w(공백 무시), -M(rename 감지) 같은 옵션에 따라 다르게 보입니다.

커밋 객체의 실제 내용 (전부 ASCII 텍스트)
$ git cat-file commit HEAD | cat -A
tree ec1aab2675f729695e07f143e4fc5650da77baa2$
author Pluxus <me@example.com> 1790062531 +0900$
committer Pluxus <me@example.com> 1790062531 +0900$
$
t$

# $ 는 개행(LF). 즉 실제 바이트는:
# "tree <40자 16진수>\n"
# "parent <40자 16진수>\n"      (부모 수만큼 0~N줄)
# "author <이름> <<이메일>> <유닉스시각> <타임존>\n"
# "committer ... \n"
# "\n"                          ← 빈 줄이 헤더와 본문의 경계
# "<커밋 메시지>"

주목할 점: 트리 객체와 달리 커밋 객체의 OID는 40자 16진수 "문자열"로 적힙니다. 트리는 20바이트 바이너리였습니다. 커밋은 사람이 읽을 수 있는 텍스트 포맷이고, 트리는 기계가 빠르게 읽는 바이너리 포맷이라는 설계 차이입니다.

🎯 비유로 이해하기

커밋은 "사진 뒷면에 적은 메모"입니다. "2026년 3월 10일, 촬영자 김씨, 이전 사진은 #9a1b, 이 사진의 필름 번호는 #ec1a".

메모 어디에도 "이전 사진과 비교해 나무가 하나 늘었다" 같은 내용은 없습니다. 그건 두 사진을 나란히 놓고 볼 때 계산해서 알아내는 것입니다.

헤더 줄의 순서나 형식이 고정되어 있나요?

고정되어 있습니다. 순서가 바뀌면 다른 OID가 되므로 정규형이 중요합니다.

줄 개수 설명
tree <oid> 정확히 1개 이 커밋이 나타내는 스냅샷의 루트 트리
parent <oid> 0 ~ N개 0=루트 커밋, 1=일반, 2=머지, 3+=옥토퍼스 머지
author 1개 원본 변경을 만든 사람 + 시각
committer 1개 이 커밋 객체를 만든 사람 + 시각
gpgsig 0 또는 1개 서명 커밋일 때. 여러 줄이며 이어지는 줄은 공백으로 시작
(빈 줄) 1개 헤더와 본문의 경계
메시지 나머지 전부 첫 줄이 제목, 빈 줄 뒤가 본문이라는 것은 관례일 뿐

시각은 1790062531 +0900 형태입니다. 앞은 UTC 기준 유닉스 타임스탬프, 뒤는 커밋한 사람의 로컬 타임존 오프셋입니다. 절대 시각은 앞 숫자로만 결정되며, 오프셋은 "이 사람이 몇 시에 커밋했다고 느꼈는가"를 보존하기 위한 표시용 정보입니다.

Part 2: author와 committer는 왜 둘 다 필요한가

두 줄이 거의 항상 같던데, 왜 나눠 놓았나요?

평소에는 같지만, 히스토리를 다시 쓰는 순간 갈라집니다. 그리고 그 갈라짐이 Git 워크플로의 핵심 정보를 담습니다.

상황 author committer
평범한 git commit 나 나 (동일)
git rebase 원 작성자 유지 (시각도 유지) rebase를 실행한 나, 지금 시각
git cherry-pick 원 작성자 유지 cherry-pick한 나
git am (메일 패치 적용) 패치를 보낸 기여자 패치를 적용한 메인테이너
git commit --amend 원래 author 유지 amend한 나, 지금 시각

Linux 커널 개발 모델이 이 구분의 뿌리입니다. 기여자가 메일로 패치를 보내면 메인테이너가 적용합니다. "누가 코드를 썼는가(author)"와 "누가 이 히스토리에 넣었는가(committer)"는 다른 책임이므로 둘 다 기록합니다.

bash — 두 값이 갈라지는 순간 관찰
# rebase 전
$ git log -1 --format='A: %an %ad%nC: %cn %cd'
A: Alice  Mon Mar 2 10:00:00 2026 +0900
C: Alice  Mon Mar 2 10:00:00 2026 +0900

$ git rebase main

# rebase 후 - author는 그대로, committer만 바뀐다
$ git log -1 --format='A: %an %ad%nC: %cn %cd'
A: Alice  Mon Mar 2 10:00:00 2026 +0900     # ← 원본 유지
C: Bob    Tue Mar 10 15:22:41 2026 +0900    # ← 지금 이 순간

그래서 git log가 기본으로 보여 주는 날짜는 author date인데, --since/--until 같은 필터와 기본 정렬은 commit date를 씁니다. rebase가 많은 저장소에서 "로그 날짜가 뒤죽박죽"으로 보이는 원인이 바로 이 불일치입니다. --date-order, --author-date-order로 명시할 수 있습니다.

커밋 OID에는 무엇이 영향을 주나요? 같은 변경인데 해시가 달라지는 이유는?

커밋 객체의 모든 바이트가 영향을 줍니다. 따라서 다음이 하나라도 다르면 OID가 달라집니다.

  • 트리 OID (내용이 같으면 동일)
  • 부모 OID 목록과 순서
  • author 이름/이메일/시각/타임존
  • committer 이름/이메일/시각/타임존
  • 커밋 메시지의 한 글자, 공백, 개행

그래서 같은 변경을 같은 사람이 두 번 커밋해도 OID가 다릅니다(committer 시각이 다르므로). 반대로 GIT_AUTHOR_DATE와 GIT_COMMITTER_DATE를 고정하면 재현 가능한(deterministic) 커밋 해시를 만들 수 있고, 이는 재현 가능한 빌드 검증에 쓰입니다.

bash — 결정적 커밋 만들기
$ export GIT_AUTHOR_DATE="2026-01-01T00:00:00+0000"
$ export GIT_COMMITTER_DATE="2026-01-01T00:00:00+0000"
$ export GIT_AUTHOR_NAME="bot" GIT_AUTHOR_EMAIL="bot@x"
$ export GIT_COMMITTER_NAME="bot" GIT_COMMITTER_EMAIL="bot@x"

$ git commit -q -m "fixed" && git rev-parse HEAD
a7c4f21e9b0d3c8f5e2a1b6d4c7e9f0a3b5c8d1e

# 같은 조건으로 다른 머신에서 다시 만들어도 정확히 같은 해시가 나온다

반대로 "머지 커밋의 부모 순서"가 OID에 영향을 준다는 점도 실무에서 중요합니다. parent 1은 머지를 받은 쪽(ours, 보통 main), parent 2는 머지해 온 쪽(theirs, 보통 feature)입니다. HEAD^1, HEAD^2가 이 순서를 가리키며, git log --first-parent가 main의 줄기만 따라갈 수 있는 근거이기도 합니다.

Part 3: 태그 객체 — 경량 태그와 주석 태그

git tag v1.0과 git tag -a v1.0은 뭐가 다른가요?

완전히 다른 물건이 만들어집니다. 전자는 객체를 만들지 않고, 후자는 tag 객체를 만듭니다.

구분 경량 태그 (lightweight) 주석 태그 (annotated)
명령 git tag v1.0 git tag -a v1.0 -m "..."
디스크에 남는 것 refs/tags/v1.0 파일에 커밋 OID 한 줄 tag 객체 1개 + ref 파일이 그 태그 객체를 가리킴
담는 정보 없음 (그냥 북마크) 태거, 시각, 메시지, (선택) GPG 서명
GPG 서명 불가 가능 (-s)
용도 개인용 임시 북마크 릴리스 등 공식 표식
bash — 두 태그의 실체 비교
$ git tag light                    # 경량
$ git tag -a heavy -m "release"    # 주석

$ cat .git/refs/tags/light
c0ffee1234...                      # ← 커밋 OID를 직접 가리킴
$ git cat-file -t light
commit                             # ← 태그 객체가 아니라 커밋!

$ cat .git/refs/tags/heavy
deadbeef99...                      # ← tag 객체 OID
$ git cat-file -t heavy
tag
$ git cat-file -p heavy
object c0ffee1234567890abcdef1234567890abcdef12
type commit
tag heavy
tagger Pluxus <me@example.com> 1790062531 +0900

release

tag 객체는 커밋을 한 겹 더 감싼 봉투입니다. object가 가리키는 대상은 아무 타입이나 될 수 있어서, 이론적으로는 blob이나 tree에도 태그를 달 수 있습니다(실제로 Git 저장소에는 공개 키 blob을 가리키는 태그가 있습니다).

"커밋 OID를 얻는다"고 할 때 주석 태그는 한 번 더 벗겨야(peel) 합니다. git rev-parse v1.0은 tag 객체 OID를, git rev-parse v1.0^{commit}(또는 v1.0^{})은 커밋 OID를 줍니다. CI 스크립트에서 자주 터지는 함정입니다.

Part 4: DAG와 리비전 표기법

커밋 그래프는 왜 트리가 아니라 DAG인가요?

머지 때문입니다. 머지 커밋은 부모가 둘 이상이므로 "한 노드가 여러 부모를 갖는" 구조가 되고, 이는 트리가 아니라 방향 비순환 그래프(DAG)입니다.

"비순환"인 것은 해시 때문에 구조적으로 보장됩니다. 커밋 OID는 부모 OID를 포함해 계산되므로, 자기 자신을 (간접적으로라도) 부모로 삼으려면 OID를 미리 알아야 하는 모순이 생깁니다. 사이클을 만들 방법이 없습니다.

A
←
B
←
C
←
M (머지)
 
 
B
←
D
←
M의 두 번째 부모

화살표 방향에 주의하십시오. 커밋은 부모를 가리키지, 자식을 가리키지 않습니다. 따라서 "이 커밋의 자식이 누구인가"는 저장소 전체를 훑어야만 알 수 있습니다. git log가 과거로만 거슬러 갈 수 있고, "이 커밋 이후의 커밋"을 찾으려면 git rev-list --ancestry-path 같은 비싼 연산이 필요한 이유입니다.

HEAD~3과 HEAD^3은 어떻게 다른가요? 늘 헷갈립니다.

한 문장으로 구분됩니다. ^는 "몇 번째 부모", ~는 "몇 세대 위"입니다.

표기 의미 풀어 쓰면
HEAD^ = HEAD^1 첫 번째 부모 머지라면 "머지를 받은 쪽(main)"
HEAD^2 두 번째 부모 머지라면 "머지해 온 쪽(feature)". 머지가 아니면 오류
HEAD~ = HEAD~1 첫 부모를 1번 따라감 HEAD^와 동일
HEAD~3 첫 부모를 3번 따라감 HEAD^^^와 동일
HEAD^2~1 두 번째 부모로 간 뒤 한 세대 더 조합 가능
A..B B에서 도달 가능 − A에서 도달 가능 ^A B와 동일. "A 이후 B에 추가된 것"
A...B 대칭 차집합 (양쪽에만 있는 것) "두 브랜치가 갈라진 뒤 각자 한 일"
bash — 표기법 검증
# 머지 커밋에서 두 부모 확인
$ git log -1 --format='%H %P' HEAD
M_oid  P1_oid P2_oid          # %P = 부모 OID들 (공백 구분)

$ git rev-parse HEAD^1        # = P1 (main 쪽)
$ git rev-parse HEAD^2        # = P2 (feature 쪽)
$ git rev-parse HEAD~1        # = P1 (^1과 동일)

# ~ 와 ^ 의 차이가 드러나는 지점
$ git rev-parse HEAD~2        # P1의 P1
$ git rev-parse HEAD^^        # 동일
$ git rev-parse HEAD^2^       # P2의 P1 - 전혀 다른 커밋!

# 범위 표기
$ git log --oneline main..feature     # feature에만 있는 커밋
$ git log --oneline main...feature    # 양쪽에 각자 있는 커밋
$ git log --oneline --first-parent main   # main의 줄기만 (머지 내부 무시)
🎯 비유로 이해하기

가족 관계도에서 ^는 "아버지냐 어머니냐"를 고르는 것이고, ~는 "몇 대(代)를 거슬러 올라가느냐"입니다.

HEAD^2는 "두 번째 부모", 즉 어머니 쪽입니다. HEAD~2는 "아버지의 아버지", 즉 친조부입니다. 한쪽은 선택이고 한쪽은 반복입니다.

실무 팁: git log --first-parent main은 머지 커밋 내부의 개별 커밋을 건너뛰고 main의 줄기만 보여 줍니다. PR 단위로 관리되는 저장소에서 "릴리스 노트용 커밋 목록"을 뽑을 때 가장 유용한 옵션입니다.

📌 핵심 정리

  • 커밋 객체에 diff는 없다. 루트 트리 OID 1개, 부모 OID 0~N개, author/committer, 메시지가 전부인 순수 ASCII 텍스트다. git show의 diff는 조회 시 계산된다.
  • author는 "누가 썼는가", committer는 "누가 히스토리에 넣었는가"다. rebase·cherry-pick·am에서 갈라지며, 이 불일치가 로그 정렬 혼란의 원인이 된다.
  • 커밋 OID는 모든 바이트에 의존한다. 시각까지 포함하므로 같은 변경도 매번 다른 해시가 되고, 날짜를 고정하면 결정적 해시를 만들 수 있다.
  • 경량 태그는 ref 파일 한 줄, 주석 태그는 진짜 tag 객체다. 주석 태그는 ^{commit}으로 한 겹 벗겨야 커밋 OID가 나온다.
  • 커밋 그래프는 부모 방향으로만 연결된 DAG다. 해시 체인 때문에 사이클이 구조적으로 불가능하고, 자식을 찾으려면 전체를 훑어야 한다. ^=부모 선택, ~=세대 반복.
