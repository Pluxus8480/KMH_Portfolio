지운 커밋은 언제 진짜로 사라질까?

GC 해부 — 도달 가능성 · prune 2주의 유예 · cruft pack · fsck로 복구하기

Part 1: 도달 가능성 — Git의 생사 판정 기준

브랜치를 지우면 그 커밋들은 어떻게 되나요?

즉시 지워지지 않습니다. "도달 불가능(unreachable)" 상태가 될 뿐이며, 그 자체로는 아무 일도 일어나지 않습니다.

Git의 GC는 mark-and-sweep 방식입니다. 프로그래밍 언어의 가비지 컬렉터와 원리가 같습니다.

1. 루트 수집
모든 ref(브랜치·태그·원격 추적) + reflog 항목 + 인덱스 + 진행 중 상태(MERGE_HEAD 등)
→
2. 마킹
루트에서 커밋 → 트리 → 하위 트리 → blob으로 전부 순회하며 표시 (13편의 리비전 워크)
→
3. 스윕
표시되지 않은 객체 중 충분히 오래된 것만 삭제

3번의 "충분히 오래된"이 Git GC의 결정적 안전장치입니다. 일반적인 GC와 달리 Git은 도달 불가능해진 즉시 지우지 않습니다.

🎯 비유로 이해하기

사무실의 문서 폐기 규정과 같습니다.

어떤 문서를 참조하는 색인 카드가 모두 없어지면 그 문서는 "버려도 되는 후보"가 됩니다. 하지만 즉시 파쇄하지 않고 2주간 폐기함에 둡니다. 누가 실수로 카드를 버렸을 수도 있고, 마침 지금 새 카드를 만드는 중일 수도 있기 때문입니다.

Git의 2주 유예가 정확히 이 폐기함입니다.

왜 즉시 지우지 않나요?

두 가지 이유가 있고, 둘 다 실용적입니다.

1) 사용자의 실수 복구. reset --hard, 브랜치 삭제, rebase 사고로 잃은 커밋을 되살릴 시간을 줍니다.

2) 경쟁 상태 방지 — 이쪽이 더 중요합니다. 다른 프로세스가 지금 막 객체를 쓰고 있는데 ref를 아직 만들지 않았다면, 그 객체는 순간적으로 도달 불가능합니다. 즉시 지우면 진행 중인 작업이 파괴됩니다.

위험한 시나리오
프로세스 A (git commit 진행 중)
  t1: blob 기록
  t2: tree 기록
  t3: commit 객체 기록       ← 아직 ref가 없다! 도달 불가능 상태
  t4: refs/heads/main 갱신

프로세스 B (git gc)
  t3.5: "도달 불가능한 커밋 발견" → 즉시 삭제했다면?
        → A의 t4에서 만들어진 ref가 없는 객체를 가리키게 됨 = 저장소 손상

02편에서 본 "이미 있으면 mtime만 갱신(freshen)"이 여기서 의미를 갖습니다. Git은 객체를 쓸 때 이미 존재하면 mtime을 갱신하는데, 이는 "이 객체는 방금 쓰이려 했으니 아직 지우지 마라"는 신호입니다. 도달 가능성과 mtime, 두 가지를 함께 보는 이유입니다.

Part 2: gc가 실제로 하는 일들

git gc는 무엇을 하나요?

이름은 "가비지 컬렉션"이지만 실제로는 유지보수 작업의 묶음입니다.

작업내용관련 설정
repack느슨한 객체를 팩으로, 여러 팩을 하나로gc.autoPackLimit (기본 50)
prune오래되고 도달 불가능한 객체 삭제gc.pruneExpire (기본 2.weeks.ago)
reflog expire오래된 reflog 항목 삭제gc.reflogExpire 90일 / gc.reflogExpireUnreachable 30일
pack-refsloose ref를 packed-refs로—
commit-graph write커밋 그래프 갱신gc.writeCommitGraph
worktree prune사라진 worktree 정리gc.worktreePruneExpire
builtin/gc.c — 기본 유예 기간
.prune_expire = xstrdup("2.weeks.ago"),

reflog expire가 prune보다 먼저 실행된다는 순서가 중요합니다. reflog 항목이 사라져야 그 커밋이 비로소 도달 불가능해지고, 그 뒤에야 prune의 대상이 됩니다. 즉 실제 삭제까지는 "reflog 만료(30~90일) + prune 유예(2주)"가 걸립니다.

bash — 삭제 시점 체험
$ git log --oneline -1
a1b2c3d 실수로 만든 커밋

$ git reset --hard HEAD~1              # 커밋을 "버렸다"

# 여전히 살아 있다 — reflog가 가리키고 있기 때문
$ git cat-file -t a1b2c3d
commit
$ git fsck --unreachable                # 아무것도 안 나옴 (reflog가 루트니까)

# reflog까지 지워야 비로소 도달 불가능
$ git reflog expire --expire=now --all
$ git fsck --unreachable
unreachable commit a1b2c3d...

# 그래도 2주 유예 때문에 gc로는 안 지워진다
$ git gc
$ git cat-file -t a1b2c3d
commit                                  # 아직 살아 있다!

# 유예까지 무시하고 즉시 삭제
$ git gc --prune=now
$ git cat-file -t a1b2c3d
fatal: git cat-file: could not get object info    # 이제 정말 사라졌다

--prune=now는 진행 중인 다른 Git 프로세스를 파괴할 수 있습니다. 저장소를 아무도 안 쓰는 것이 확실할 때만 사용하십시오. 서버에서는 특히 위험합니다.

자동 GC는 언제 돌아가나요?

commit, merge, rebase, am 같은 명령이 끝날 때 git gc --auto를 호출합니다. 임계를 넘지 않으면 아무것도 하지 않고 돌아갑니다.

설정기본값의미
gc.auto6700느슨한 객체가 이보다 많으면 팩으로 묶는다. 0이면 자동 GC 전체 비활성
gc.autoPackLimit50.keep이 없는 팩이 이보다 많으면 하나로 합친다
gc.autoDetachtrue백그라운드에서 돌리고 즉시 반환
gc.bigPackThreshold—이보다 큰 팩은 재패킹 대상에서 제외

gc.auto가 6700이라는 어중간한 숫자인 데는 이유가 있습니다. 객체 앞 2자로 256개 디렉토리에 흩어지므로(03편), Git은 objects/17/ 디렉토리 하나만 세어 보고 ×256으로 추정합니다. 전체를 스캔하지 않고 표본으로 어림하는 것이며, 6700은 그 추정 기준에 맞춘 값입니다.

bash — GC 제어
# 지금 GC가 필요한 상태인지
$ git count-objects -v
count: 8234                # gc.auto(6700) 초과 → 다음 명령에서 자동 GC

# 자동 GC 임시 비활성 (대량 스크립트 작업 중)
$ git -c gc.auto=0 fast-import < data

# 백그라운드 GC가 성가시다면 (CI 등)
$ git config gc.autoDetach false

# 현대적 대안: maintenance (2.31+)
$ git config --global maintenance.auto false   # 자동 gc 끄고
$ git maintenance register                      # 스케줄러에 등록
$ git maintenance start
# → gc 대신 incremental-repack, commit-graph, prefetch를 주기적으로 수행

git maintenance가 현대적 권장안입니다. gc가 "가끔 크게 한 번"이라면, maintenance는 "자주 조금씩"입니다. 대형 저장소에서 작업 중 갑자기 수 분간 멈추는 일을 방지합니다.

Part 3: cruft pack — "느슨한 객체 폭발" 문제

GC를 돌렸는데 오히려 파일 수가 늘어난 적이 있습니다. 왜 그런가요?

Git의 오래된 골칫거리였습니다. 원인은 mtime과 팩의 충돌입니다.

문제
prune은 객체별 mtime으로 만료를 판정한다
→
그런데
팩 안의 객체는 개별 mtime이 없다. 팩 파일 하나의 mtime만 존재
→
옛 해법
repack 시 도달 불가능한 객체를 느슨한 객체로 풀어냄(unpack-unreachable) → 파일 수 폭발
→
현대 해법
cruft pack — 별도 팩 + .mtimes 파일에 객체별 mtime 기록

10편에서 본 .mtimes 파일이 이 문제의 해답입니다. 4바이트 × 객체 수의 테이블에 각 객체의 mtime을 담아, 팩 안에 있으면서도 개별 만료 판정이 가능해집니다.

bash — cruft pack 사용
# 도달 불가능한 객체를 cruft pack으로 모으기
$ git gc --cruft
$ ls .git/objects/pack/
pack-aaa.pack  pack-aaa.idx                    # 도달 가능한 객체
pack-bbb.pack  pack-bbb.idx  pack-bbb.mtimes   # ← cruft pack

# 만료 기간을 지정해 repack
$ git repack --cruft --cruft-expiration=30.days -d

# 기본값으로 켜기 (대형 저장소 권장)
$ git config gc.cruftPacks true

# 확인: .mtimes가 있는 팩이 cruft pack
$ ls .git/objects/pack/*.mtimes

GitHub 같은 호스팅 서비스에는 이 기능이 존재 이유 그 자체였습니다. 거대 저장소에서 GC를 돌릴 때마다 inode가 수백만 개 생기는 문제를 겪었고, cruft pack이 그것을 해결했습니다.

.keep 파일은 뭔가요?

팩 파일 옆에 같은 이름의 .keep 파일을 두면 그 팩은 repack 대상에서 제외됩니다.

bash — .keep 활용
# 거대한 팩(예: 최초 clone으로 받은 것)을 재패킹에서 제외
$ touch .git/objects/pack/pack-aaa.keep

# 이후 gc는 이 팩을 건드리지 않는다
$ git gc
# → pack-aaa는 그대로, 새로 생긴 객체만 다른 팩으로

# 효과: 20GB짜리 팩을 매번 다시 쓰는 비용을 없앤다
# gc.autoPackLimit의 팩 개수 계산에서도 제외된다

Git이 스스로 .keep을 만드는 경우도 있습니다. fetch로 팩을 받는 도중에는 임시 .keep을 두어, 인덱싱이 끝나기 전에 다른 프로세스가 그 팩을 지우지 못하게 합니다.

Part 4: fsck — 진단과 복구

reflog도 없이 커밋을 잃었습니다. 복구할 방법이 있나요?

GC가 아직 돌지 않았다면 가능성이 높습니다. git fsck가 "아무도 안 가리키는 객체"를 찾아 줍니다.

bash — 미아 객체 찾기
# reflog를 루트에서 제외하고 진짜 미아를 찾는다
$ git fsck --lost-found --no-reflogs
Checking object directories: 100% (256/256), done.
dangling commit a1b2c3d4e5f6...
dangling commit f7d3c0e9b8a7...
dangling blob   9f8e7d6c5b4a...

# 각각이 뭔지 확인
$ git show a1b2c3d4e5f6
commit a1b2c3d4e5f6
Author: me
Date:   ...
    fix: 잃어버린 그 커밋!

# 파일로도 떨어진다
$ ls .git/lost-found/commit/
a1b2c3d4e5f6...
$ ls .git/lost-found/other/          # blob 등

# 되살리기 — 이름을 붙여 주면 된다
$ git branch recovered a1b2c3d4e5f6
$ git log recovered

블롭만 남은 경우(git add는 했지만 커밋 전에 잃은 파일)도 건질 수 있습니다. dangling blob의 내용을 git cat-file -p로 꺼내 확인하고, 맞는 것을 파일로 저장하면 됩니다.

bash — 스테이징만 하고 잃은 파일 찾기
# dangling blob들을 훑어 내용 확인
$ for b in $(git fsck --lost-found --no-reflogs | awk '/dangling blob/{print $3}'); do
    echo "=== $b ($(git cat-file -s $b) bytes) ==="
    git cat-file -p "$b" | head -5
  done

# 찾았으면 복원
$ git cat-file -p 9f8e7d6c5b4a > recovered.c

시간이 관건입니다. git gc --prune=now나 자동 GC가 돌기 전에 해야 합니다. 사고를 인지한 즉시 저장소 디렉토리 전체를 cp -a로 복사해 두는 것이 가장 안전한 첫 조치입니다.

fsck는 복구 말고 무엇에 쓰나요?

이름 그대로 파일 시스템 검사(file system check)입니다. 저장소의 무결성을 전수 검증합니다.

검사 항목내용
해시 일치객체 내용을 다시 해시해 이름과 비교 (03편)
연결 무결성커밋이 가리키는 트리, 트리가 가리키는 blob이 실제로 존재하는가
포맷 검증트리 엔트리 정렬(04편), 커밋 헤더 순서, 모드 값의 유효성
미아 객체도달 불가능한 객체 목록
손상된 ref없는 객체를 가리키는 ref
bash — fsck 실전
# 전체 검사 (대형 저장소에서는 수 분 소요)
$ git fsck --full --strict

# 흔한 출력과 의미
warning in tree 4d5e6f7: contains zero-padded file modes   # 옛 Git이 만든 040000
warning in commit a1b2c3d: invalid author/committer line   # 이메일 형식 문제
error: refs/heads/broken does not point to a valid object  # ref 손상
missing blob 9f8e7d6c                                      # 객체 유실 (심각)

# 수신 데이터 검증 강화 (서버 권장)
$ git config transfer.fsckObjects true
$ git config receive.fsckObjects true      # push 받을 때 검증
$ git config fetch.fsckObjects true        # fetch 할 때 검증

# 특정 경고 무시 (옛 저장소 마이그레이션 시)
$ git config fsck.zeroPaddedFilemode warn

receive.fsckObjects = true는 서버에서 반드시 켜야 할 설정입니다. 악의적이거나 손상된 객체가 저장소에 들어오는 것을 push 시점에 막습니다. 켜지 않으면 손상된 객체가 조용히 저장되었다가, 나중에 다른 사용자의 clone을 깨뜨립니다. 검증 비용이 있어 기본값이 아니지만, 공용 서버라면 켜는 것이 옳습니다.

bash — 저장소 용량 분석 (GC와 함께 자주 쓰는 패턴)
# 1) 큰 blob Top 10과 그 경로
$ git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1=="blob"' | sort -k3 -n -r | head -10
blob 3f4a5b6c 104857600 Assets/Textures/intro.png

# 2) 도달 불가능한 객체가 차지하는 용량
$ git count-objects -vH
size-pack: 1.32 GiB
$ git gc --prune=now --quiet && git count-objects -vH
size-pack: 842 MiB                  # 490MB가 쓰레기였다

# 3) 브랜치별 기여도 (어느 브랜치가 용량을 먹는가)
$ for b in $(git branch -r --format='%(refname)'); do
    echo "$(git rev-list --count $b) $b"
  done | sort -rn | head

면접 포인트: "Git에서 파일을 완전히 삭제하려면?"이라는 질문의 정답은 여러 단계입니다. (1) 히스토리 재작성(filter-repo)으로 도달 불가능하게 만들고, (2) 모든 클론에서 강제 push + 재클론, (3) reflog 만료 + gc --prune=now, (4) 호스팅 서비스에 서버 측 GC를 요청. 그리고 유출된 비밀은 어차피 폐기(rotate)해야 한다는 점을 함께 말하는 것이 실무적인 답입니다.

📌 핵심 정리

  • Git GC는 mark-and-sweep이며, 루트에는 ref뿐 아니라 reflog·인덱스·진행 중 상태가 포함된다. 브랜치를 지워도 reflog가 가리키는 동안은 도달 가능이다.
  • 도달 불가능해져도 즉시 지우지 않고 gc.pruneExpire(기본 2주) 유예를 둔다. 사용자 실수 복구뿐 아니라, "객체는 썼지만 ref는 아직" 상태의 다른 프로세스를 파괴하지 않기 위한 경쟁 상태 방어다.
  • 실제 삭제까지는 reflog 만료(도달 불가 항목 30일, 그 외 90일) + prune 유예 2주가 걸린다. --prune=now는 진행 중인 프로세스를 깨뜨릴 수 있어 서버에서 특히 위험하다.
  • cruft pack + .mtimes가 "GC 후 느슨한 객체 폭발" 문제를 해결했다. 팩 안의 객체에도 개별 mtime을 부여해 만료 판정이 가능해졌다. .keep 파일은 거대 팩을 재패킹에서 제외한다.
  • git fsck --lost-found --no-reflogs가 reflog 없이도 미아 커밋·blob을 찾아 준다. 단 GC 전에 해야 하며, 사고 직후에는 저장소 디렉토리를 통째로 복사해 두는 것이 최선의 첫 조치다. 서버에서는 receive.fsckObjects를 켜 두는 것이 좋다.
