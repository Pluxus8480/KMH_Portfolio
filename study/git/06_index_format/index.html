스테이징 영역은 대체 어디에 있는가?

.git/index 바이너리 해부 — DIRC 헤더 · 62바이트 엔트리 · stage 번호 · cache-tree

Part 1: 인덱스는 "스테이징 영역"만이 아니다

인덱스는 git add한 것들을 담아 두는 임시 공간 아닌가요?

그것도 맞지만, 인덱스의 역할은 세 가지입니다. 하나만 알면 Git의 절반을 오해하게 됩니다.

역할 내용 관련 명령
1. 다음 커밋의 초안 "다음에 커밋할 트리"를 경로+OID 목록으로 들고 있음 add, rm, commit
2. stat 캐시 파일마다 lstat(2) 결과를 기억해, 내용을 안 읽고 "수정됨" 판정 status, diff
3. 머지 충돌 작업대 같은 경로를 stage 1/2/3으로 세 벌 보관 merge, rebase

두 번째 역할이 성능의 핵심입니다. git status가 파일 10만 개짜리 저장소에서 1초 안에 끝나는 이유는 파일 내용을 읽지 않고 lstat 결과만 비교하기 때문입니다. 내용을 전부 해시해야 한다면 수십 초가 걸립니다.

🎯 비유로 이해하기

인덱스는 출판사 편집자의 책상입니다.

책상 위에는 (1) 다음 판본에 들어갈 원고 목록이 있고, (2) 각 원고를 마지막으로 확인한 시각과 분량을 적은 메모가 붙어 있어 "이거 바뀌었나?"를 빠르게 판단할 수 있으며, (3) 두 저자가 같은 장을 고쳐 와 다툴 때는 원본·저자A안·저자B안 세 부를 나란히 펼쳐 놓습니다.

텍스트 파일이 아니라 바이너리인 이유가 있나요?

크기와 파싱 속도 때문입니다. 인덱스는 git status, git diff가 돌 때마다 전체를 읽고, 때로는 전체를 다시 씁니다. Linux 커널 저장소처럼 파일 8만 개인 곳에서는 인덱스가 수 MB이므로, 파싱 비용이 곧 체감 성능입니다.

고정 길이 필드의 바이너리 포맷이면 mmap 후 포인터 산술만으로 엔트리를 순회할 수 있습니다. 실제로 Git은 인덱스를 mmap해서 읽습니다.

Part 2: 바이트 단위 해부

실제 .git/index의 바이트를 읽어 볼 수 있을까요?

파일 3개가 담긴 인덱스의 앞부분입니다. 모든 정수는 네트워크 바이트 순서(빅엔디언)입니다.

xxd .git/index — 헤더 + 첫 엔트리
00000000: 4449 5243 0000 0002 0000 0003 6ab2 2f56  DIRC........j./V
00000010: 3987 6bec 6ab2 2f56 3987 6bec 0000 0000  9.k.j./V9.k.....
00000020: 0000 0000 0000 81a4 0000 0000 0000 0000  ................
00000030: 0000 0006 ce01 3625 030b a8db a906 f756  ......6%.......V
00000040: 967f 9e9c a394 464a 0005 612e 7478 7400  ......FJ..a.txt.
00000050: 0000 0000 6ab2 2fc3 ...                  ....j./.

한 바이트씩 해석하면 이렇습니다.

오프셋 바이트 의미
0x0044 49 52 43시그니처 "DIRC" (DIRectory Cache — 인덱스의 옛 이름)
0x0400 00 00 02버전 = 2 (2, 3, 4 지원)
0x0800 00 00 03엔트리 개수 = 3
0x0C6a b2 2f 56ctime 초
0x1039 87 6b ecctime 나노초
0x146a b2 2f 56mtime 초
0x1839 87 6b ecmtime 나노초
0x1C00 00 00 00dev (Windows에서는 0)
0x2000 00 00 00ino (Windows에서는 0)
0x2400 00 81 a4mode. 0x81a4 = 8진수 100644
0x2800 00 00 00uid
0x2C00 00 00 00gid
0x3000 00 00 06파일 크기 = 6바이트
0x34ce 01 36 ... 46 4aOID 20바이트 (raw 바이너리)
0x4800 05flags. 하위 12비트 = 이름 길이 5
0x4A61 2e 74 78 74 00"a.txt" + NUL
0x5000 00 00 008의 배수 정렬을 위한 패딩

엔트리 하나는 62바이트 고정부 + 이름 + NUL이고, 전체 길이가 8의 배수가 되도록 패딩합니다. 첫 엔트리는 12(헤더) + 62 + 5 + 1 = 80바이트 → 패딩으로 84바이트(0x54)에서 다음 엔트리가 시작합니다. 위 덤프에서 0x54부터 두 번째 엔트리가 시작하는 것이 확인됩니다.

8바이트 정렬은 mmap된 메모리에서 구조체를 그대로 읽기 위한 장치입니다. 다만 버전 4에서는 이 패딩이 사라집니다(뒤에 설명).

mode 필드에 0x81a4가 들어 있는데, 트리에서 본 100644와 같은 건가요?

같은 값입니다. 0x81a4를 8진수로 바꾸면 0100644입니다. 인덱스는 이 32비트를 다음처럼 나눠 씁니다.

32비트 mode 필드의 구성
비트 31..16 : 사용 안 함 (0이어야 함)
비트 15..12 : 객체 타입
              1000 = 일반 파일, 1010 = 심볼릭 링크, 1110 = gitlink
비트 11..9  : 사용 안 함 (0)
비트  8..0  : Unix 권한 9비트
              일반 파일은 0755 또는 0644만 유효
              심링크/gitlink는 0

0x81a4 = 1000 0001 1010 0100
         \타입 1000(일반파일)  \권한 110100100 = 0644

인덱스는 원본 st_mode를 그대로 저장하지 않고 위 규칙으로 정규화합니다. 04편에서 본 "Git은 다섯 가지 모드만 안다"가 인덱스 레벨에서 강제되는 지점입니다.

Part 3: stage 번호 — 충돌은 인덱스에 산다

flags 필드의 "2비트 stage"는 뭔가요?

머지 충돌을 담는 자리입니다. 평상시 모든 엔트리는 stage 0이고, 충돌이 나면 같은 경로에 stage 1/2/3 세 엔트리가 동시에 존재합니다.

stage 의미 머지에서
0정상 (충돌 없음)머지 완료 상태
1base공통 조상의 버전
2ours현재 브랜치(HEAD)의 버전
3theirs머지해 오는 쪽의 버전

인덱스 엔트리는 "이름 → stage" 순으로 정렬되므로, 같은 경로의 1/2/3이 나란히 놓입니다.

bash — 충돌 중인 인덱스 관찰
$ git merge feature
CONFLICT (content): Merge conflict in app.c

$ git ls-files --stage
100644 ce013625...  0	README.md        # ← 충돌 없는 파일은 stage 0
100644 aaaa1111...  1	app.c            # base
100644 bbbb2222...  2	app.c            # ours  (HEAD)
100644 cccc3333...  3	app.c            # theirs

# 각 버전을 개별로 꺼낼 수 있다
$ git show :1:app.c > app.base.c
$ git show :2:app.c > app.ours.c
$ git show :3:app.c > app.theirs.c

# 해결 후 git add 를 하면 1/2/3이 사라지고 stage 0 하나만 남는다
$ git add app.c
$ git ls-files --stage | grep app.c
100644 dddd4444...  0	app.c

"충돌 해결"의 정체는 단순합니다. stage 1/2/3 엔트리를 지우고 stage 0 엔트리 하나를 넣는 것입니다. git add가 하는 일이 정확히 그것이고, git commit은 stage 0이 아닌 엔트리가 하나라도 있으면 거부합니다("Unmerged paths").

워킹 트리의 <<<<<<< 충돌 마커는 사람이 보라고 써 준 힌트일 뿐이며, Git이 참조하는 진실은 인덱스의 stage 1/2/3입니다. 마커를 다 지워도 git add하지 않으면 충돌 상태가 유지되고, 반대로 마커를 그대로 둔 채 git add하면 마커째로 커밋됩니다.

flags의 나머지 비트들은요?

16비트 flags와 (버전 3 이상의) 확장 16비트가 다음처럼 쓰입니다.

flags 비트 배치
[기본 16비트]
 비트 15    : assume-valid   (git update-index --assume-unchanged)
 비트 14    : extended       (v2에서는 반드시 0)
 비트 13-12 : stage          (0~3)
 비트 11-0  : 이름 길이 (0xFFF 미만일 때. 그 이상이면 0xFFF 고정)

[확장 16비트 - extended 비트가 1일 때만 존재, v3+]
 비트 15    : 예약
 비트 14    : skip-worktree  (희소 체크아웃)
 비트 13    : intent-to-add  (git add -N)
 비트 12-0  : 사용 안 함

여기서 실무와 직결되는 두 비트가 있습니다.

assume-valid: "이 파일은 안 바뀐 걸로 치고 lstat조차 건너뛰라"는 표시입니다. 느린 네트워크 파일 시스템에서 성능을 짜낼 때 쓰지만, 실제로 파일이 바뀌어도 Git이 무시하므로 "로컬 설정 파일 변경 감추기" 용도로 쓰면 반드시 사고가 납니다.

skip-worktree: 희소 체크아웃에서 "이 경로는 워킹 트리에 없어도 정상"이라는 표시입니다(23편). assume-valid와 달리 Git이 의도적으로 관리하는 상태입니다.

이 두 비트를 혼동해 "변경 감추기"에 --assume-unchanged를 쓰는 사례가 흔합니다. 브랜치 전환이나 머지에서 조용히 덮어써지거나 충돌이 나므로, 그 목적이라면 .gitignore나 .git/info/exclude, 혹은 템플릿 파일 패턴을 써야 합니다.

Part 4: 버전 2/3/4와 확장 — 그리고 cache-tree

인덱스 버전 4는 뭐가 좋아지나요?

버전 4의 핵심은 경로 접두사 압축입니다. 인덱스는 경로순으로 정렬되어 있으므로, src/foo/a.c 다음에 src/foo/b.c가 오면 앞부분이 거의 같습니다. 이를 "이전 경로에서 뒤 N바이트를 지우고 이 문자열을 붙여라"로 표현합니다.

v4 경로 인코딩
이전 경로: src/foo/alpha.c
이번 경로: src/foo/beta.c

저장되는 것: N=7, S="beta.c"
  → "src/foo/alpha.c"에서 뒤 7바이트("alpha.c") 제거 → "src/foo/"
  → 거기에 "beta.c"를 붙임 → "src/foo/beta.c"

N은 가변 길이 정수(팩 파일의 offset 인코딩과 같은 방식)로 저장되고,
S는 NUL로 끝나는 문자열이다. v4에서는 8바이트 패딩도 없앤다.
버전추가된 것언제 쓰이나
2기본 포맷기본값. 대부분의 저장소
3확장 flags 16비트 (skip-worktree, intent-to-add)해당 비트가 필요한 엔트리가 생기면 자동 승격
4경로 접두사 압축 + 패딩 제거git update-index --index-version 4로 명시. 거대 모노레포에서 인덱스 30~50% 감소

버전 3은 사용자가 고르는 것이 아니라 필요할 때 Git이 알아서 올립니다. 희소 체크아웃을 켜면 인덱스 버전이 3으로 바뀌는 것을 git update-index --show-index-version으로 확인할 수 있습니다.

인덱스 끝에 붙는 "확장(extension)"은 뭔가요?

엔트리 목록 뒤에 오는 선택적 캐시 블록들입니다. 각 확장은 4바이트 시그니처 + 4바이트 크기 + 데이터로 이루어지며, 시그니처 첫 바이트가 대문자면 "몰라도 무시해도 되는" 선택적 확장이라는 규칙이 있습니다. 덕분에 구버전 Git도 새 확장이 붙은 인덱스를 안전하게 읽습니다.

시그니처이름하는 일
TREEcache-tree디렉토리 구간별로 이미 아는 tree OID를 캐싱. 커밋 속도의 핵심
REUCresolve-undo충돌을 해결한 뒤에도 1/2/3 원본을 기억해 checkout -m으로 되돌릴 수 있게 함
UNTRuntracked cache디렉토리별 untracked 파일 목록 캐시. status 가속
FSMNfsmonitor파일 감시 데몬과 연동해 "바뀐 파일만" 검사
linksplit index인덱스를 공유 베이스 + 델타로 분리해 쓰기 비용 절감
EOIE/IEOT오프셋 테이블인덱스를 멀티스레드로 병렬 파싱하기 위한 구간 표시

가장 중요한 것은 TREE(cache-tree)입니다. 인덱스는 평평한 경로 목록인데, 커밋하려면 계층적 트리로 접어야 합니다. cache-tree는 "이 구간(=이 디렉토리)은 이미 tree OID가 X임을 안다"를 저장합니다.

어떤 경로를 git add하면 그 경로의 모든 상위 디렉토리 노드가 무효화됩니다. 무효는 "엔트리 개수 = −1"로 표시합니다. 커밋 시에는 무효 노드만 다시 계산하므로, 파일 10만 개 중 하나를 고쳐도 새로 만드는 트리는 보통 서너 개뿐입니다.

bash — cache-tree 직접 보기
$ git ls-files --debug | head -6      # stat 캐시까지 전부 출력
a.txt
  ctime: 1790062422:965726700
  mtime: 1790062422:965726700
  dev: 0	ino: 0
  uid: 0	gid: 0
  size: 6	flags: 0

# cache-tree 상태 확인 (Git 2.20+)
$ test-tool read-cache --table     # (테스트 도구. 배포판엔 없을 수 있음)

# 무효화 여부를 간접 확인: add 직후 commit이 빠른지 재 보면 된다
$ git add big-dir/one-file.txt
$ time git commit -q -m "one line"   # 트리 전체가 아니라 조상만 재계산됨
real	0m0.09s

인덱스가 손상되면(드물지만 강제 종료 시 발생) rm -f .git/index && git reset으로 HEAD에서 재생성할 수 있습니다. 인덱스는 캐시이자 초안이지 원본 데이터가 아니므로, 스테이징하지 않은 상태라면 잃을 것이 없습니다.

📌 핵심 정리

  • 인덱스의 역할은 셋이다. 다음 커밋의 초안, lstat 결과를 담은 stat 캐시, 머지 충돌 작업대. 두 번째가 git status 속도의 비밀이다.
  • 포맷은 "DIRC" + 버전 + 엔트리 수 + (62바이트 고정부 + 이름) 반복 + 확장 + 체크섬이며 전부 빅엔디언이다. 엔트리는 8바이트 배수로 패딩된다(v4 제외).
  • 충돌은 워킹 트리의 마커가 아니라 인덱스의 stage 1/2/3에 산다. "해결"이란 1/2/3을 지우고 stage 0 하나를 넣는 일이고, 그것이 git add가 하는 전부다.
  • 버전 3은 확장 flags(skip-worktree, intent-to-add)가 필요할 때 자동 승격되고, 버전 4는 경로 접두사 압축으로 인덱스를 크게 줄인다.
  • cache-tree(TREE 확장)가 커밋을 빠르게 만든다. 수정된 경로의 조상 노드만 무효화(-1)되므로 커밋마다 새로 만드는 트리는 몇 개뿐이다.
