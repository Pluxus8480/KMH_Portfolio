commit-graph 해부 — 청크 포맷 · generation number v1/v2 · changed-path Bloom filter

Part 1: 커밋 하나 읽는 데 드는 진짜 비용

13편에서 "커밋 파싱 비용"이라는 말이 나왔습니다. 커밋은 작은 텍스트인데 왜 비싼가요?

커밋 하나를 읽으려면 실제로 이 과정을 전부 거쳐야 합니다.

1. 위치 찾기
모든 팩의 .idx에 이진 탐색
2. 읽기
mmap/seek델타 체인이면 base까지 따라가 복원
3. 압축 해제
zlib inflate
4. 파싱
"tree ", "parent ", "committer " 줄 파싱16진수 40자 → 바이너리 변환

커밋 하나는 수십 µs면 되지만, git log --topo-order나 git gc는 커밋 수십만 개를 전부 이 과정으로 읽습니다. Linux 커널 저장소(커밋 120만 개)에서는 이것만으로 수십 초가 날아갑니다.

그런데 그래프 탐색이 실제로 필요로 하는 정보는 부모 목록, 커밋 날짜, 루트 트리 OID뿐입니다. 메시지도, author도, 서명도 필요 없습니다. "필요한 것만 고정 길이 이진 배열로 뽑아 두면 압축 해제도 파싱도 필요 없다"는 것이 commit-graph의 아이디어입니다.

🎯 비유로 이해하기

도서관에서 "이 책의 참고 문헌은 무엇인가"를 조사한다고 합시다.

책을 한 권씩 꺼내 포장을 풀고 목차를 넘겨 참고 문헌 페이지를 찾는 것이 커밋 객체 파싱입니다. commit-graph는 "책 번호 → 참고 문헌 번호 목록"만 적은 별도의 카드 색인을 미리 만들어 두는 것입니다. 카드는 규격이 같아서 원하는 번호의 카드로 계산만으로 바로 점프할 수 있습니다.

commit-graph 파일은 어떤 구조인가요?

MIDX와 같은 청크 기반 포맷입니다. 헤더에 "어떤 청크가 어디 있는지" 목록을 두고, 실제 데이터는 청크로 나뉩니다.

청크 ID이름크기내용
OIDFOID Fanout256 × 4B.idx와 같은 누적 fanout
OIDLOID LookupN × 20B정렬된 커밋 OID 목록
CDATCommit DataN × (20+16)B핵심. 루트 트리 + 부모 위치 + 세대 + 날짜
GDA2Generation DataN × 4Bgeneration number v2 (수정 커밋 날짜)
GDO2Generation OverflowM × 8B31비트를 넘는 값
EDGEExtra Edge List가변부모가 3개 이상인 옥토퍼스 머지의 나머지 부모
BIDXBloom Filter IndexN × 4B각 커밋의 Bloom filter 끝 오프셋(누적)
BDATBloom Filter Data가변changed-path Bloom filter 본체
BASEBase Graphs ListB × 20B분할 commit-graph 체인의 하위 레이어들

CDAT의 36바이트가 특히 흥미롭습니다. 비트를 한 톨도 낭비하지 않습니다.

CDAT 엔트리 (20 + 16 = 36바이트)
[0..19]   루트 트리 OID (20바이트)

[20..23]  첫 번째 부모의 그래프 위치 (4바이트)
          0x70000000 = "부모 없음"
[24..27]  두 번째 부모의 그래프 위치 (4바이트)
          MSB가 1이면 → 나머지 비트는 EDGE 청크의 인덱스 (옥토퍼스 머지)

[28..31]  상위 30비트 = topological level (generation number v1)
          하위  2비트 = 커밋 시각의 33~34번째 비트
[32..35]  커밋 시각의 하위 32비트

⇒ 커밋 시각을 34비트로 저장 (2106년 이후도 표현 가능)

부모를 OID가 아니라 "그래프 위치(배열 인덱스)"로 저장하는 것이 결정적입니다. 부모를 따라가려면 OID 탐색 없이 배열 인덱싱 한 번이면 됩니다. 그래프 순회가 포인터 추적 수준으로 빨라집니다.

Part 2: generation number — "탐색을 언제 멈출지" 아는 법

generation number는 왜 필요한가요? 부모 포인터만 있으면 되지 않나요?

탐색을 언제 멈출지 알기 위해서입니다. "A가 B의 조상인가?"를 묻는다고 합시다. 부모 포인터만 있으면 B의 조상 전체를 훑어야 "아니오"라고 답할 수 있습니다. 루트까지 내려가야 끝납니다.

generation number는 각 커밋에 부분 순서를 부여하는 숫자입니다. Git 문서의 정의가 명확합니다.

topological level (generation number v1)
부모가 없는 커밋(루트)의 topological level = 1
부모가 있는 커밋의 topological level = 부모들 중 최댓값 + 1

⇒ 커밋 A의 topological level은
  "A에서 루트까지 가는 가장 긴 경로의 길이 + 1"

여기서 결정적인 성질이 나옵니다. Git 문서의 표현을 그대로 옮깁니다.

"A와 B의 generation number가 각각 N과 M이고 N ≤ M이면, A는 B에 도달할 수 없다." 즉 탐색하지 않고도 "B는 A의 조상이 아니다"를 알 수 있습니다. B가 루트에서 더 멀기 때문입니다.

질문
"A가 B의 조상인가?" (A의 세대 = N)
→
탐색 중단 조건
B에서 거슬러 오르다가 경계의 모든 커밋의 세대가 N 이하가 되면 즉시 "아니오"
→
구현
세대 내림차순 우선순위 큐를 쓰면 이 조건을 자연스럽게 감지

13편에서 본 compare_commits_by_gen_then_commit_date가 바로 이 큐입니다. 세대가 큰 것부터 꺼내므로, 큐의 맨 앞이 N 이하가 되는 순간 나머지도 전부 N 이하입니다.

v2(corrected committer date)는 뭐가 다른가요?

v1의 약점을 고친 것입니다. v1은 커밋 날짜 정보를 전혀 쓰지 않습니다. 순수한 그래프 깊이만 보므로, 실제로는 훨씬 오래된 커밋인데 세대만 높은 경우가 생겨 탐색을 충분히 잘라내지 못합니다.

corrected committer date (generation number v2)
루트 커밋의 수정 커밋 날짜 = 자신의 커밋 날짜
부모가 있는 커밋의 수정 커밋 날짜
    = max(자신의 커밋 날짜, 부모들의 수정 커밋 날짜 중 최댓값 + 1)

특수 케이스: 타임스탬프가 0인 루트 커밋은 1로 둔다
    (0 = "아직 계산 안 됨"을 뜻하는 GENERATION_NUMBER_ZERO와 구분하기 위해)

핵심 아이디어: "커밋 날짜를 쓰되, 부모보다 항상 크도록 보정한다." 시계가 틀려 부모보다 이른 날짜를 가진 커밋이 있어도 +1 규칙이 단조성을 강제하므로, 날짜의 정보량을 활용하면서도 v1의 수학적 보장을 유지합니다.

날짜 기반이므로 실제 히스토리의 시간 분포를 반영해 탐색 경계가 훨씬 타이트해집니다. 대형 저장소에서 merge-base 계산이 v1 대비 수 배 빨라집니다.

구분v1 (topological level)v2 (corrected committer date)
저장 위치CDAT의 상위 30비트별도 GDA2 청크 (4바이트)
기반그래프 깊이만커밋 날짜 + 단조성 보정
포화값GENERATION_NUMBER_V1_MAX = 0x3FFFFFFF31비트 초과 시 GDO2 오버플로 청크
탐색 절단력보통훨씬 좋음

두 버전이 섞일 수 있어서 규칙이 하나 더 있습니다. 분할 commit-graph 체인에서 일부 레이어에만 GDA2가 있는 경우, Git은 안전을 위해 전체를 v1(topological level)로 취급합니다. 서로 다른 척도의 숫자를 섞어 비교하면 부등식이 깨지기 때문입니다.

특수값 두 개도 알아 둘 만합니다. GENERATION_NUMBER_ZERO = 0은 "commit-graph를 지원하지 않던 구버전이 만든, 세대를 모르는 커밋"이고, GENERATION_NUMBER_INFINITY는 "commit-graph에 아예 없는 커밋"입니다. 이런 커밋을 만나면 세대 기반 최적화를 포기하고 날짜 휴리스틱으로 후퇴합니다.

Part 3: changed-path Bloom filter — 경로 필터 가속

13편의 "git log -- path/가 느린 문제"는 어떻게 푸나요?

문제를 정확히 보면 이렇습니다. 경로 필터가 걸리면 Git은 커밋마다 "이 커밋이 그 경로를 건드렸는가"를 알아야 하고, 이를 위해 부모 트리와 현재 트리를 비교해야 합니다. 커밋 50만 개면 트리 비교 50만 번입니다.

그런데 실제로는 대부분의 커밋이 그 경로를 건드리지 않았습니다. 모노레포에서 services/payment/를 건드린 커밋은 전체의 2%일 수 있습니다. 나머지 98%에 대해 "확실히 아니다"를 싸게 판정할 수 있다면 트리 비교를 건너뛸 수 있습니다.

이것이 정확히 Bloom filter가 잘하는 일입니다. Bloom filter는 "확실히 없다"는 100% 정확하게, "있을 수도 있다"는 거짓 양성을 허용하며 답합니다. 거짓 양성이 나오면 원래대로 트리를 비교하면 되므로 정확성은 전혀 손상되지 않고 속도만 얻습니다.

🎯 비유로 이해하기

창고 100개에서 특정 부품을 찾는 상황입니다. 창고를 하나씩 열어 뒤지면(트리 비교) 하루가 걸립니다.

대신 각 창고 문에 "이 창고에 들어온 적 있는 부품 종류"를 압축해 적은 태그를 붙여 둡니다. 태그에 없으면 절대 그 안에 없으므로 문을 열 필요가 없습니다. 태그에 있다고 나오면 그때만 열어 확인합니다. 가끔 헛걸음(거짓 양성)을 하지만, 98개의 창고를 열지 않아도 됩니다.

Git의 Bloom filter는 구체적으로 어떻게 구성되나요?

Git 소스의 기본 설정값이 명시적입니다.

bloom.h — 기본 설정
#define DEFAULT_BLOOM_MAX_CHANGES 512
#define DEFAULT_BLOOM_FILTER_SETTINGS { 1, 7, 10, DEFAULT_BLOOM_MAX_CHANGES }
                                          |  |   |   \- 최대 변경 경로 수
                                          |  |   \----- 엔트리당 최소 비트 수 b = 10
                                          |  \--------- 해시 횟수 k = 7
                                          \------------ 버전

포맷 문서가 설명하는 동작은 이렇습니다.

  • 해시는 murmur3 32비트를 쓰고, 시드 0x293ae76f와 0x7e646e2로 이중 해싱(double hashing)해서 7개의 비트 위치를 만듭니다. 서로 다른 해시 함수 7개를 구현하는 대신 2개로 7개를 합성하는 표준 기법입니다.
  • 필터 크기는 n × 10비트를 담는 최소한의 64비트 워드 개수입니다.
  • 필터에 넣는 것은 변경된 파일의 경로와 그 상위 디렉토리들입니다. 그래서 services/payment/처럼 디렉토리로 질의해도 매치됩니다.

두 가지 예외 처리가 중요합니다. 문서의 표현대로, 변경이 없거나 512개를 초과하는 커밋은 길이 1짜리 필터를 갖습니다. 전자는 모든 비트가 0(=무조건 "없음"), 후자는 모든 비트가 1(=무조건 "있을 수도")입니다. 거대 머지나 대량 리팩터링 커밋에서 필터가 비대해지는 것을 막는 장치입니다.

버전 1에는 알려진 버그가 있습니다. char가 signed인 플랫폼에서 경로에 0x80 이상 바이트(한글 등 비ASCII 파일명)가 있으면 해시가 달라집니다. 버전 2가 이를 고쳤고, Git은 읽기 호환을 유지하되 v1 쓰기는 장래에 제거할 예정이라고 명시합니다. 한글 파일명이 있는 저장소라면 commit-graph를 최신 Git으로 다시 생성하는 것이 좋습니다.

Part 4: 실전 — 생성 · 유지 · 함정

어떻게 만들고 얼마나 효과가 있나요?
bash — commit-graph 생성과 측정
# 생성 (Bloom filter 포함)
$ git commit-graph write --reachable --changed-paths
Expanding reachable commits in commit graph: 512043, done.
Writing out commit graph in 4 passes: 100% (2048172/2048172), done.

$ ls -lh .git/objects/info/commit-graph
-r--r--r-- 1 me me 42M ... commit-graph

# 효과 측정 (대형 저장소)
$ time git log --oneline --topo-order | wc -l
# 전: 11.8s → 후: 1.4s

$ time git log --oneline -- services/payment/ | wc -l
# 전: 18.4s → 후: 0.6s

$ time git merge-base --is-ancestor v1.0 HEAD
# 전: 2.1s → 후: 0.02s

# 검증
$ git commit-graph verify

주목할 점은 commit-graph가 순수한 캐시라는 것입니다. 지워도 저장소는 멀쩡하고, 내용이 낡아도 Git은 없는 커밋에 대해 일반 경로로 후퇴합니다. 있으면 빠르고 없으면 정확한, 안전한 최적화입니다.

자동으로 유지하려면요?
bash — 자동 유지 설정
# fetch 후 자동으로 commit-graph 갱신
$ git config fetch.writeCommitGraph true

# 경로 필터까지 자동으로
$ git config commitGraph.changedPathsVersion 2

# 백그라운드 유지보수 (commit-graph + MIDX + prune + gc)
$ git maintenance start
$ git maintenance register        # 여러 저장소를 한 스케줄에 등록

# 분할 체인 방식으로 증분 갱신 (전체 재작성 없이)
$ git commit-graph write --reachable --split --changed-paths
$ ls .git/objects/info/commit-graphs/
commit-graph-chain
graph-{hash1}.graph               # 베이스 레이어
graph-{hash2}.graph               # 증분 레이어

분할 commit-graph(--split)가 대형 저장소에서 실용적입니다. 커밋 10개가 추가될 때마다 50만 커밋짜리 파일을 통째로 다시 쓰는 대신, 작은 레이어를 위에 쌓고 가끔 병합합니다. BASE 청크가 하위 레이어를 참조하며, 12편의 reftable 스택과 같은 LSM 패턴입니다.

주의할 점이나 함정은 없나요?

네 가지가 있습니다.

1) 히스토리를 다시 쓰면 낡은 항목이 남습니다. rebase, filter-repo로 커밋 OID가 대거 바뀌면 commit-graph에 도달 불가능한 커밋 정보가 쌓입니다. 정확성 문제는 없지만 파일이 부풀므로, 대규모 재작성 후에는 git commit-graph write --reachable로 다시 만드는 것이 좋습니다.

2) shallow clone에서는 세대가 틀어집니다. 문서가 명시하듯, 잘린 경계 커밋은 부모가 없는 것처럼 보여 세대 1로 계산됩니다. 나중에 --unshallow로 복원해도 그 세대 값은 자동으로 고쳐지지 않습니다. unshallow 후에는 commit-graph를 재생성해야 합니다.

3) replace ref와 grafts가 있으면 비활성화됩니다. git replace나 .git/info/grafts로 부모 관계를 조작하면 그래프 구조가 파일과 달라지므로, Git은 commit-graph 사용을 포기합니다.

4) 한글·비ASCII 파일명 + Bloom filter v1 조합은 오동작할 수 있습니다. v2로 재생성하십시오.

bash — 문제 진단
# commit-graph가 실제로 쓰이고 있는지 확인
$ GIT_TRACE2_PERF=1 git log --topo-order -1 2>&1 | grep -i 'commit.graph'

# 일시적으로 끄고 비교 (원인 격리)
$ git -c core.commitGraph=false log --topo-order -1

# 무결성 검사 (그래프와 실제 객체가 일치하는지)
$ git commit-graph verify --progress

# 문제가 있으면 삭제 후 재생성 (안전 — 순수 캐시다)
$ rm -rf .git/objects/info/commit-graph .git/objects/info/commit-graphs
$ git commit-graph write --reachable --changed-paths

면접 포인트: "Git이 대형 저장소에서 느린데 어떻게 개선하겠는가"라는 질문에는 commit-graph(그래프 탐색), MIDX(객체 조회), 비트맵(clone/fetch), 희소 인덱스(워킹 트리) 네 가지를 층위별로 나눠 답하는 것이 좋습니다. 각각이 병목이 다른 계층을 공략합니다.

📌 핵심 정리

  • commit-graph는 그래프 탐색에 필요한 정보(부모·날짜·루트 트리)만 고정 길이 이진 배열로 뽑아 둔 캐시다. 압축 해제와 텍스트 파싱이 사라지고, 부모를 OID가 아니라 배열 인덱스로 가리켜 순회가 포인터 추적 수준이 된다.
  • generation number는 "탐색을 언제 멈출지"를 알려 주는 부분 순서다. N ≤ M이면 A는 B에 도달할 수 없다는 성질 덕분에, 조상 판정에서 그래프 전체를 훑지 않아도 된다.
  • v1은 topological level(그래프 깊이), v2는 corrected committer date(날짜 + 단조성 보정)다. v2가 실제 시간 분포를 반영해 탐색 경계가 훨씬 타이트하며, 레이어에 섞여 있으면 안전하게 v1로 후퇴한다.
  • changed-path Bloom filter가 경로 필터를 가속한다. murmur3 이중 해싱으로 7비트를 세우고, "확실히 없음"은 정확히, "있을 수도"는 거짓 양성을 허용한다. 변경 0개 또는 512개 초과 커밋은 길이 1 필터로 특수 처리한다.
  • commit-graph는 순수 캐시이므로 지워도 안전하다. 다만 shallow clone, replace/grafts, 대규모 히스토리 재작성, 비ASCII 경로 + Bloom v1에서는 재생성이 필요하다.
