훅으로 정책을 강제할 수 있을까?

훅 실전 — 우회 가능성 · 2중 방어 · 프레임워크와 배포 · 성능과 디버깅

Part 1: 클라이언트 훅은 강제가 아니다

커밋 컨벤션을 훅으로 강제하면 되는 거 아닌가요?

여기서 많은 팀이 잘못된 보안 모델을 갖습니다. 클라이언트 훅은 우회가 한 플래그면 됩니다.

우회 방법들 — 전부 합법적인 Git 기능
$ git commit --no-verify -m "아무거나"     # pre-commit, commit-msg 건너뜀
$ git push --no-verify                      # pre-push 건너뜀
$ git config --unset core.hooksPath         # 훅 경로 자체를 해제
$ chmod -x .githooks/*                      # 실행 비트를 떼면 조용히 무시됨(24편)
$ rm .git/hooks/pre-commit                  # 그냥 지운다

따라서 클라이언트 훅의 정체는 "정책 집행 수단"이 아니라 "실수를 줄여 주는 편의 장치"입니다. 악의를 막지 못하고, 실수만 막습니다. 그리고 그것만으로도 충분히 가치가 있습니다 — 대부분의 문제는 악의가 아니라 실수니까요.

🎯 비유로 이해하기

클라이언트 훅은 자동차의 안전벨트 경고음입니다.

띵띵거려서 대부분의 사람이 벨트를 매게 되지만, 버클만 꽂아 두면 그만입니다. 정말로 못 지나가게 하려면 톨게이트의 차단봉이 필요하고, 그것이 서버 훅입니다.

그렇다고 경고음이 쓸모없는 건 아닙니다. 톨게이트까지 가서야 제지당하는 것보다, 출발 전에 알려 주는 편이 훨씬 빠르고 친절합니다.

그럼 진짜로 막으려면 어떻게 해야 하나요?

2중 방어가 정석입니다. 같은 규칙을 두 층에 두되 역할을 나눕니다.

1층: 클라이언트 훅
커밋/푸시 직전에 즉각 피드백
우회 가능하지만 빠르다
→
2층: 서버 훅 / CI
push 시점에 실제로 차단
우회 불가. 느리지만 확실
환경2층에 무엇을 두나
자체 Git 서버 (Gitea, GitLab self-hosted, bare 저장소) pre-receive / update 훅 — 가장 강력. 25편 참고
GitHub / GitLab SaaS 서버 훅을 직접 못 넣음 → 브랜치 보호 규칙 + 필수 상태 검사(CI)
GitHub Enterprise pre-receive hook 기능 제공 (관리자 설정)
Gerrit proc-receive 기반 리뷰 강제 (25편)

SaaS를 쓰는 대부분의 팀에게는 "서버 훅을 쓸 수 없다"가 현실입니다. 이때 브랜치 보호 규칙(force push 금지, 리뷰 필수, 상태 검사 통과 필수)이 서버 훅의 역할을 대신합니다. 훅으로 해결하려 하지 말고 그쪽을 설정해야 합니다.

그리고 중요한 원칙: 같은 검증 로직을 두 번 작성하지 마십시오. 스크립트 하나를 만들어 클라이언트 훅과 CI가 같은 파일을 호출하게 해야 규칙이 어긋나지 않습니다.

검증 로직 단일화
# scripts/validate-commit-msg.sh  ← 진실은 여기 하나뿐
#!/bin/sh
grep -qE '^(feat|fix|docs|refactor|test|chore)(\(.+\))?: .{1,72}$' "$1"

# .githooks/commit-msg
#!/bin/sh
exec ./scripts/validate-commit-msg.sh "$1"

# .github/workflows/ci.yml
- run: |
    git log --format=%B -n1 ${{ github.event.pull_request.head.sha }} > /tmp/msg
    ./scripts/validate-commit-msg.sh /tmp/msg

Part 2: 서버 훅으로 실제 정책 만들기

실무에서 자주 쓰는 서버 정책을 예제로 보여 주세요.

가장 많이 요구되는 네 가지를 pre-receive 하나에 담으면 이렇습니다. 25편의 stdin 포맷과 24편의 all-zeroes 규칙이 그대로 쓰입니다.

hooks/pre-receive — 통합 정책 훅 sh 
#!/bin/sh
# 서버(bare) 저장소의 hooks/pre-receive
# stdin: <old-oid> SP <new-oid> SP <ref-name> LF  (25편)

zero=$(git hash-object --stdin -t tree </dev/null | tr '[0-9a-f]' '0')
fail=0

# push option으로 긴급 우회를 허용 (감사 로그는 남긴다)
i=0
emergency=0
while [ "$i" -lt "${GIT_PUSH_OPTION_COUNT:-0}" ]; do
    eval "opt=\$GIT_PUSH_OPTION_$i"
    [ "$opt" = "emergency" ] && emergency=1
    i=$((i + 1))
done

while read old new ref; do

    # -- 정책 1: 보호 브랜치 삭제 금지 ------------------
    if [ "$new" = "$zero" ]; then
        case "$ref" in
            refs/heads/main|refs/heads/release/*)
                echo "거부: $ref 는 삭제할 수 없습니다." >&2
                fail=1 ;;
        esac
        continue                       # 삭제는 더 검사할 게 없다
    fi

    # -- 정책 2: non-fast-forward 금지 (15편의 조상 판정) --
    if [ "$old" != "$zero" ]; then
        case "$ref" in
            refs/heads/main|refs/heads/release/*)
                if ! git merge-base --is-ancestor "$old" "$new"; then
                    echo "거부: $ref 에 force push 할 수 없습니다." >&2
                    fail=1; continue
                fi ;;
        esac
    fi

    # 검사할 커밋 범위 결정 (24편의 all-zeroes 처리)
    if [ "$old" = "$zero" ]; then
        # 새 브랜치: 기존 브랜치들에 없는 커밋만 (13편의 --not --all)
        range=$(git rev-list "$new" --not --all)
    else
        range=$(git rev-list "$old".."$new")
    fi

    for c in $range; do
        subject=$(git log -1 --format=%s "$c")

        # -- 정책 3: 커밋 메시지 컨벤션 ------------------
        if ! printf '%s' "$subject" | grep -qE '^(feat|fix|docs|refactor|test|chore)(\(.+\))?: .+'; then
            echo "거부: $c 메시지가 컨벤션에 맞지 않습니다: $subject" >&2
            fail=1
        fi

        # -- 정책 4: 대용량 파일 차단 (09편 — 델타가 안 먹힌다) --
        git diff-tree -r --no-commit-id --name-only "$c" | while read path; do
            blob=$(git rev-parse "$c:$path" 2>/dev/null) || continue
            size=$(git cat-file -s "$blob" 2>/dev/null) || continue
            if [ "$size" -gt 10485760 ]; then
                echo "거부: $path 가 10MB를 초과합니다 ($size). LFS를 사용하세요." >&2
                exit 1
            fi
        done || fail=1
    done
done

if [ "$fail" -ne 0 ]; then
    if [ "$emergency" -eq 1 ]; then
        echo "경고: --push-option=emergency 로 정책을 우회했습니다." >&2
        logger -t git-hook "EMERGENCY BYPASS by $(whoami)"
        exit 0
    fi
    echo "" >&2
    echo "정책 위반으로 push가 거부되었습니다." >&2
    echo "긴급 시: git push --push-option=emergency" >&2
    exit 1
fi
exit 0

여기서 눈여겨볼 설계가 둘 있습니다.

1) 새 브랜치에는 git rev-list "$new" --not --all을 씁니다. old가 all-zeroes라 범위를 만들 수 없는데, 그렇다고 $new 전체를 검사하면 이미 main에 있는 옛 커밋까지 전부 재검사하게 됩니다. --not --all이 13편의 UNINTERESTING 전파를 이용해 "이 저장소에 아직 없는 커밋만" 골라 줍니다.

2) 우회 경로를 의도적으로 남겼습니다. 장애 상황에서 정책 때문에 핫픽스를 못 올리는 일은 실제로 벌어집니다. --push-option(24편)으로 명시적 우회를 허용하되 반드시 로그를 남기는 것이 현실적인 타협입니다.

셸 스크립트의 함정 하나: while read ... done이 파이프 뒤에 오면 서브셸에서 실행되어 변수 변경이 밖으로 전파되지 않습니다. 위 코드의 git diff-tree | while read 블록에서 fail=1을 직접 설정하지 않고 exit 1 + || fail=1로 처리한 이유입니다.

서버 훅 성능은 신경 안 써도 되나요?

신경 써야 합니다. push할 때마다 사용자가 기다리는 시간입니다.

안티패턴문제대안
커밋마다 git 명령 수십 번 1,000커밋 push에 수만 번의 프로세스 생성 git log --format=...로 한 번에 뽑아 파싱
훅에서 전체 테스트 실행 push가 수 분 블로킹 훅은 빠른 검증만, 테스트는 CI로
post-receive에서 동기 배포 배포 끝날 때까지 push 안 끝남 큐에 넣고 즉시 반환
reference-transaction에서 네트워크 호출 모든 ref 연산이 느려짐(25편) 파일에 append만, 집계는 별도 프로세스
sh — 프로세스 생성 줄이기
# ❌ 커밋당 git 프로세스 1개
for c in $(git rev-list "$old".."$new"); do
    subject=$(git log -1 --format=%s "$c")
    check "$subject"
done

# ✅ 한 번의 호출로 전부 수집
git rev-list "$old".."$new" --format='%H%x09%s' --no-commit-header \
  | while IFS="$(printf '\t')" read -r sha subject; do
        check "$subject"
    done

post-receive에서 배포를 트리거할 때는 반드시 비동기여야 합니다. nohup ... &로 떼어 내거나 메시지 큐에 넣고 즉시 반환하십시오. 동기로 두면 개발자가 git push 앞에서 배포가 끝나길 기다리게 되고, push가 타임아웃되면 ref는 갱신됐는데 배포는 실패한 어중간한 상태가 됩니다.

Part 3: 프레임워크와 팀 배포

훅 프레임워크는 뭘 해결해 주나요?

직접 짤 때 부딪히는 세 가지 문제를 해결합니다.

  1. 설치 강제 — .git/hooks는 클론되지 않고, core.hooksPath 설정은 각자 해야 합니다(24편).
  2. 한 이벤트에 여러 도구 — 전통적 훅은 이벤트당 파일 하나뿐이라, 린터와 시크릿 탐지기를 함께 돌리려면 디스패처를 직접 만들어야 합니다.
  3. 변경된 파일만 검사 — 전체 검사는 느려서 아무도 안 씁니다.
도구생태계설치 방식특징
Husky Node.js npm install의 prepare 스크립트 core.hooksPath를 .husky로 설정. lint-staged와 조합
pre-commit Python (언어 무관) pre-commit install 도구를 격리 환경에 자동 설치. YAML 선언형. CI 연동 강력
Lefthook Go 단일 바이너리 lefthook install 런타임 의존성 없음. 병렬 실행 내장
Overcommit Ruby overcommit --install 서명 검증으로 훅 변조 감지
.pre-commit-config.yaml — 선언형 예시
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-merge-conflict      # 충돌 마커(18편)가 남았는지
      - id: check-added-large-files
        args: ['--maxkb=10240']       # 09편 — 큰 바이너리 차단

  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.18.0
    hooks:
      - id: gitleaks                  # 시크릿 탐지

pre-commit이 특히 강력한 이유는 도구를 격리 환경에 자동 설치한다는 점입니다. 팀원이 파이썬 린터를 안 깔았어도 알아서 가상환경을 만들어 동일 버전으로 실행합니다. "내 로컬에선 통과했는데 CI에선 실패"를 구조적으로 없앱니다.

그리고 24편에서 본 config 기반 훅(hook.<name>.command)이 장기적으로 2번 문제를 Git 자체에서 해결합니다. 다만 아주 최신 기능이라, 당분간은 프레임워크가 현실적인 선택입니다.

팀에 배포할 때 실제 세팅은 어떻게 하나요?

"클론 후 한 번의 명령"으로 끝나게 만드는 것이 목표입니다. 프레임워크 없이 순수 Git으로 한다면 이렇습니다.

bash — 순수 Git 팀 배포 구성
# 저장소 구조
.githooks/
  pre-commit
  commit-msg
  pre-push
scripts/
  setup-hooks.sh
  validate-commit-msg.sh

# scripts/setup-hooks.sh
#!/bin/sh
set -e
git config core.hooksPath .githooks
echo "훅이 설치되었습니다: $(git rev-parse --git-path hooks)"

# 실행 비트를 인덱스에 박아 둔다 (24편 — Windows 대응 필수)
$ git update-index --chmod=+x .githooks/*

# 팀원 안내 (README)
$ ./scripts/setup-hooks.sh

여기서 "설치를 잊는 사람" 문제가 남습니다. 몇 가지 현실적 대응이 있습니다.

방법동작한계
빌드 도구에 끼워 넣기 npm prepare, make, Gradle 태스크에서 자동 설정 빌드를 한 번은 돌려야 함
init.templateDir 전사 표준 온보딩 시 개인 환경에 1회 설정(24편) 개인 설정이라 강제 불가
서버/CI에서 검증 설치 여부와 무관하게 push/PR에서 차단 이것이 정답. 클라이언트 훅은 보조

결국 Part 1의 결론으로 돌아옵니다. "모두가 훅을 설치하게 만드는 완벽한 방법은 없습니다." 설치를 쉽게 만들되, 정책은 서버나 CI에서 검증하는 것이 유일하게 확실한 구조입니다.

Part 4: 디버깅과 함정

훅이 이상하게 동작할 때 어떻게 디버깅하나요?
bash — 훅 디버깅 체크리스트
# 1) Git이 보는 훅 경로 확인 (24편)
$ git rev-parse --git-path hooks
$ git config --get core.hooksPath

# 2) 훅을 Git과 동일한 방식으로 직접 실행
$ git hook run pre-commit
$ git hook run commit-msg -- /tmp/testmsg      # 인자 전달

# 3) 훅에 추적 코드를 심는다
#!/bin/sh
exec 2>>/tmp/hook-debug.log                    # stderr를 파일로
set -x                                          # 실행되는 명령을 전부 출력
echo "=== $(date) args: $@ ==="
cat >>/tmp/hook-stdin.log                       # stdin을 통째로 보존
# ↑ stdin을 소비했으므로 실제 로직에서 다시 읽을 수 없음에 주의

# 4) 환경 확인 — 훅의 PATH는 셸과 다를 수 있다
#!/bin/sh
env | sort > /tmp/hook-env.txt
which node npm python3 >> /tmp/hook-env.txt

# 5) 훅을 빼고 재현 — 훅이 원인인지 격리
$ git commit --no-verify -m test
$ git -c core.hooksPath=/dev/null commit -m test

# 6) Git 내부 추적
$ GIT_TRACE=1 git commit -m test 2>&1 | grep -i hook

4번 PATH 문제가 압도적으로 흔합니다. GUI 클라이언트(SourceTree, VS Code, Fork, IntelliJ)는 로그인 셸을 거치지 않고 Git을 실행하므로, .bashrc/.zshrc에서 설정한 PATH가 없습니다. nvm으로 설치한 node, pyenv의 python이 터미널에서는 되는데 GUI에서는 "command not found"가 되는 이유입니다.

sh — PATH 문제 방어
#!/bin/sh
# 흔한 위치를 명시적으로 추가
export PATH="$HOME/.local/bin:/usr/local/bin:$PATH"

# nvm 환경 로드 (GUI 클라이언트 대응)
[ -s "$HOME/.nvm/nvm.sh" ] && . "$HOME/.nvm/nvm.sh"

# 도구가 없으면 "조용히 통과"시킬지 "실패"시킬지 명시적으로 결정
if ! command -v npx >/dev/null 2>&1; then
    echo "경고: npx를 찾을 수 없어 린트를 건너뜁니다." >&2
    exit 0            # ← 팀 정책에 따라 exit 1 일 수도 있다
fi
그 밖에 자주 밟는 함정들을 정리해 주세요.
함정증상해결
실행 비트 누락 아무 일도 안 일어남(24편) chmod +x + git update-index --chmod=+x
셔뱅 없음/CRLF Windows에서 bad interpreter #!/bin/sh 명시 + .gitattributes에 .githooks/* text eol=lf
워킹 트리를 검사 스테이징 안 한 변경까지 린트에 걸림 git diff --cached로 인덱스를 본다(06편)
부분 스테이징 무시 git add -p로 일부만 올렸는데 파일 전체를 검사 git stash -k로 워킹 트리를 인덱스와 일치시킨 뒤 검사

GIT_DIR 오염 다른 저장소 명령이 엉뚱한 곳을 봄 unset $(git rev-parse --local-env-vars)(24편)

부분 스테이징 문제가 특히 교묘합니다. git add -p로 파일의 일부 hunk만 올렸는데 훅이 워킹 트리 파일을 린트하면, 커밋되지 않을 코드를 검사하게 됩니다. 반대로 통과했는데 실제 커밋 내용은 깨져 있을 수도 있습니다. lint-staged 같은 도구가 존재하는 이유가 정확히 이것입니다.

sh — 인덱스 내용만 정확히 검사하기
#!/bin/sh
# 인덱스 상태를 임시 디렉토리에 펼쳐서 검사 (워킹 트리를 건드리지 않음)
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT

# 인덱스의 내용을 그대로 꺼낸다 (04편의 tree, 06편의 인덱스)
git checkout-index --prefix="$tmp/" -af

# 스테이징된 파일만 골라 검사
git diff --cached --name-only --diff-filter=ACM -z \
  | while IFS= read -r -d '' f; do
        case "$f" in *.js|*.ts) npx eslint "$tmp/$f" || exit 1 ;; esac
    done

git checkout-index --prefix=가 우아한 해법입니다. 인덱스의 내용을 워킹 트리와 무관한 위치에 펼쳐서 검사하므로, 부분 스테이징이든 워킹 트리에 수정이 남아 있든 "실제로 커밋될 내용"만 정확히 검증합니다. stash를 쓰는 방식보다 안전합니다 — 훅이 중간에 죽어도 사용자의 작업이 stash에 갇히지 않습니다.

면접 포인트: "훅으로 코드 품질을 강제하겠다"는 답은 절반짜리입니다. 클라이언트 훅은 우회 가능하므로 빠른 피드백 역할이고, 실제 강제는 서버 훅 또는 브랜치 보호 + CI에서 이루어지며, 두 층이 같은 검증 스크립트를 공유해야 규칙이 어긋나지 않는다 — 여기까지 말해야 설계를 이해한 답이 됩니다.

📌 핵심 정리

  • 클라이언트 훅은 --no-verify 한 번이면 우회된다. 정책 집행 수단이 아니라 실수를 줄이는 빠른 피드백 장치이며, 실제 강제는 서버 훅(pre-receive/update)이나 브랜치 보호 + CI에서만 가능하다.
  • 두 층이 같은 검증 스크립트를 호출하게 만들어야 한다. 로직을 두 번 작성하면 반드시 어긋나고, 클라이언트는 통과하는데 CI는 막는 상황이 생긴다.
  • 서버 훅에서 새 브랜치는 git rev-list "$new" --not --all로 "아직 없는 커밋"만 검사한다. 긴급 우회는 --push-option으로 명시적으로 열어 두되 반드시 로그를 남긴다.
  • 훅 성능은 곧 사용자 대기 시간이다. 커밋마다 git 프로세스를 띄우지 말고 한 번에 수집하며, post-receive의 배포는 반드시 비동기로 떼어 낸다.
  • 가장 흔한 사고는 실행 비트 누락과 GUI 클라이언트의 PATH 문제다. 그리고 워킹 트리가 아니라 인덱스를 검사해야 하며, git checkout-index --prefix=로 펼쳐 검사하면 부분 스테이징까지 정확히 다룰 수 있다.
