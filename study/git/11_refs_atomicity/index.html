브랜치는 41바이트짜리 파일이다

files 백엔드 해부 — loose ref · packed-refs · symref · reflog 줄 포맷 · 트랜잭션과 원자성

Part 1: ref는 포인터일 뿐이다

"브랜치를 만드는 게 가볍다"는 말은 어느 정도로 가벼운 건가요?

파일 하나를 쓰는 만큼입니다. 정확히는 OID 40자 + 개행 = 41바이트짜리 텍스트 파일입니다.

bash — 브랜치의 실체
$ git branch feature/login
$ cat .git/refs/heads/feature/login
c0ffee1234567890abcdef1234567890abcdef12

$ wc -c .git/refs/heads/feature/login
41 .git/refs/heads/feature/login      # 40자 + LF

# 브랜치 이름의 슬래시는 그냥 디렉토리다
$ find .git/refs -type f
.git/refs/heads/main
.git/refs/heads/feature/login         # ← feature/ 디렉토리가 실제로 생김
.git/refs/tags/v1.0

SVN에서 브랜치가 "디렉토리 전체 복사"였던 것과 비교하면 차이가 극명합니다. Git에서 브랜치 생성은 파일 쓰기 한 번이고, 브랜치 삭제는 파일 삭제 한 번입니다. 그래서 "브랜치를 아낌없이 쓰라"는 조언이 가능합니다.

🎯 비유로 이해하기

객체 DB가 거대한 도서관의 서고라면, ref는 책상 위에 붙여 둔 포스트잇입니다.

"main: 3층 C열 12번 책", "feature/login: 5층 A열 7번 책". 포스트잇을 떼도 책은 서고에 그대로 있고, 새로 붙이는 데는 1초도 걸리지 않습니다. 다만 포스트잇이 하나도 없는 책은 사서가 폐기 대상으로 분류합니다(GC, 20편).

ref의 종류와 네임스페이스는 어떻게 되나요?

refs/ 아래의 계층은 규약이며, Git 명령들이 이 규약에 의존합니다.

네임스페이스용도비고
refs/heads/*로컬 브랜치git branch가 다루는 것
refs/tags/*태그커밋 또는 tag 객체를 가리킴
refs/remotes/<remote>/*원격 추적 브랜치직접 커밋할 수 없음. fetch가 갱신
refs/stash스태시특수한 머지 커밋 구조
refs/notes/*git notes커밋에 사후 메모를 붙이는 기능
refs/pull/*, refs/merge-requests/*호스팅 서비스의 PR refGitHub/GitLab이 서버에 만들어 둠
HEAD, ORIG_HEAD, MERGE_HEAD최상위 특수 refrefs/ 밖. .git/ 바로 아래

이름을 짧게 쓰면 Git이 정해진 순서로 찾아 줍니다. git rev-parse main은 .git/main → refs/main → refs/tags/main → refs/heads/main → refs/remotes/main → refs/remotes/main/HEAD 순으로 시도합니다.

그래서 브랜치와 태그에 같은 이름을 쓰면 태그가 이깁니다. git checkout v1.0이 브랜치가 아닌 태그로 가서 detached HEAD가 되는 사고가 여기서 나옵니다. 모호하면 refs/heads/v1.0처럼 완전한 이름을 쓰십시오.

symref(symbolic ref)는 뭔가요?

"다른 ref를 가리키는 ref"입니다. 파일 내용이 OID가 아니라 ref: <경로> 형태입니다.

bash — symref 다루기
$ cat .git/HEAD
ref: refs/heads/main

$ git symbolic-ref HEAD
refs/heads/main

# 원격의 기본 브랜치도 symref다
$ cat .git/refs/remotes/origin/HEAD
ref: refs/remotes/origin/main

# 직접 만들 수도 있다
$ git symbolic-ref refs/heads/latest refs/heads/release/2.4
$ git log latest -1            # release/2.4를 따라간다

symref의 존재 이유는 "현재 위치"라는 개념을 간접 참조로 표현하기 위해서입니다. HEAD가 OID를 직접 담는다면 커밋할 때마다 브랜치와 HEAD 둘 다 갱신해야 하고, 그 사이에 프로세스가 죽으면 불일치가 생깁니다. symref면 브랜치 파일 하나만 갱신하면 됩니다.

detached HEAD는 이 간접 참조가 사라진 상태입니다. HEAD에 OID가 직접 들어가고, 커밋하면 HEAD 자신이 갱신됩니다.

Part 2: packed-refs — 파일 수십만 개를 피하는 법

태그가 수천 개인 저장소는 refs/tags/에 파일이 수천 개인가요?

그대로 두면 그렇습니다. 그래서 Git은 ref들을 한 파일로 모읍니다. .git/packed-refs입니다.

.git/packed-refs 포맷
# pack-refs with: peeled fully-peeled sorted
c0ffee1234567890abcdef1234567890abcdef12 refs/heads/main
a1b2c3d4e5f6789012345678901234567890abcd refs/remotes/origin/main
deadbeef99887766554433221100ffeeddccbbaa refs/tags/v1.0
^c0ffee1234567890abcdef1234567890abcdef12
                                          ↑ '^'로 시작하는 줄 = "peeled" 값
                                            (주석 태그가 최종적으로 가리키는 커밋)

첫 줄의 주석이 능력 선언입니다. Git 소스의 상수를 그대로 보면 이렇습니다.

refs/packed-backend.c
static const char PACKED_REFS_HEADER[] =
        "# pack-refs with: peeled fully-peeled sorted \n";
능력의미
peeled일부 태그에 ^ 줄이 있음
fully-peeled모든 주석 태그에 ^ 줄이 있음 — 태그를 벗기려고 객체를 열 필요가 없음
sortedref 이름순 정렬됨 — 이진 탐색 가능

fully-peeled가 실전에서 큰 차이를 만듭니다. 태그 5,000개짜리 저장소에서 "모든 태그가 가리키는 커밋"을 알려면, 이 줄이 없으면 tag 객체 5,000개를 전부 열어 압축을 풀어야 합니다. 있으면 파일 하나 읽기로 끝납니다.

loose ref와 packed-refs가 같은 ref를 동시에 가지면 어떻게 되나요?

loose ref가 항상 이깁니다. 이 규칙이 전체 설계의 열쇠입니다.

읽기
.git/refs/heads/main이 있으면 그것을 사용. 없으면 packed-refs를 본다
→
쓰기
항상 loose ref로 쓴다. packed-refs는 건드리지 않는다
→
정리
git pack-refs(또는 gc)가 loose를 packed로 흡수하고 loose 파일을 삭제

이 구조 덕분에 ref 갱신은 언제나 "작은 파일 하나 쓰기"로 끝납니다. packed-refs 전체를 다시 쓰는 비싼 작업은 gc 때만 일어납니다. 02편에서 본 "느슨한 객체 vs 팩 파일"과 정확히 같은 패턴입니다.

함정이 하나 있습니다. ref 삭제입니다. loose 파일만 지우면 packed-refs에 남은 옛 값이 되살아납니다. 그래서 Git은 삭제 시 packed-refs도 함께 다시 씁니다. rm .git/refs/heads/foo를 직접 하면 브랜치가 좀비처럼 돌아오는 일이 생기며, 반드시 git update-ref -d를 써야 합니다.

Part 3: reflog — ref가 움직인 이력

reflog는 어디에 어떤 형식으로 저장되나요?

.git/logs/ 아래에 ref와 같은 경로 구조로 저장되는 순수 텍스트 파일입니다. 한 줄이 한 번의 이동입니다.

reflog 줄 포맷 (refs/files-backend.c의 log_ref_write_fd)
<이전 OID> <새 OID> <커미터 이름> <<이메일>> <타임스탬프> <타임존>\t<메시지>\n

$ cat .git/logs/HEAD
0000000000000000000000000000000000000000 f7d3c0e... Pluxus <me@x> 1790062531 +0900	commit (initial): first
f7d3c0e... a1b2c3d... Pluxus <me@x> 1790062600 +0900	commit: add login
a1b2c3d... f7d3c0e... Pluxus <me@x> 1790062700 +0900	reset: moving to HEAD~1
   ↑ 이전값    ↑ 새값                                    ↑ 탭 구분자 후 메시지

소스 코드가 이 포맷을 그대로 만듭니다.

refs/files-backend.c
strbuf_addf(&sb, "%s %s %s", oid_to_hex(old_oid), oid_to_hex(new_oid), committer);
if (msg && *msg) {
        strbuf_addch(&sb, '\t');       /* 탭이 메시지 구분자 */
        strbuf_addstr(&sb, msg);
}
strbuf_addch(&sb, '\n');

모든 줄의 "새 OID"가 다음 줄의 "이전 OID"와 일치하므로, reflog는 그 ref의 완전한 이동 궤적입니다. 첫 줄의 이전 OID가 0으로 가득 찬 것은 "존재하지 않던 상태에서 생성됨"을 뜻합니다.

HEAD@{2} 같은 표기는 어떻게 동작하나요?

<ref>@{N}은 그 ref의 reflog에서 N번 전의 값입니다. 시간 표기도 가능합니다.

bash — reflog 활용
$ git reflog
f7d3c0e (HEAD -> main) HEAD@{0}: reset: moving to HEAD~1
a1b2c3d HEAD@{1}: commit: add login
f7d3c0e HEAD@{2}: commit (initial): first

# N번 전의 상태로 되돌리기
$ git reset --hard HEAD@{1}

# 시간 기반 (reflog의 타임스탬프를 사용)
$ git show main@{yesterday}
$ git diff main@{1.week.ago} main

# 브랜치별 reflog도 따로 있다
$ cat .git/logs/refs/heads/main
$ git reflog show main

중요한 구분: HEAD~1은 "커밋의 부모"이고 HEAD@{1}은 "HEAD가 이전에 가리키던 값"입니다. 완전히 다른 개념입니다. rebase로 커밋 10개를 날린 뒤 HEAD~10을 찾으면 새 히스토리를 따라가지만, HEAD@{1}은 rebase 직전의 상태를 줍니다.

reflog가 Git의 안전망인 이유가 여기 있습니다. reset --hard, rebase, amend, 브랜치 삭제로 "사라진" 커밋은 도달 불가능해질 뿐이고, reflog가 그 OID를 기억하는 동안은 도달 가능한 것으로 취급되어 GC 대상이 아닙니다.

설정기본값의미
core.logAllRefUpdatestrue (비-bare)reflog 기록 여부. bare 저장소는 기본 꺼져 있음
gc.reflogExpire90일도달 가능한 reflog 항목의 보존 기간
gc.reflogExpireUnreachable30일도달 불가능해진 항목의 보존 기간. amend/rebase 잔해가 여기 해당

서버(bare) 저장소에는 reflog가 기본적으로 없습니다. "force push로 날아간 커밋을 서버에서 복구"가 잘 안 되는 이유입니다. 중요한 서버라면 core.logAllRefUpdates = true를 명시적으로 켜 두는 것이 좋습니다.

Part 4: 원자성 — 락 파일과 트랜잭션

두 프로세스가 동시에 같은 브랜치를 갱신하면 어떻게 되나요?

락 파일로 막습니다. 갱신하려는 ref마다 <ref>.lock 파일을 O_CREAT | O_EXCL로 만듭니다. 이 플래그 조합은 파일이 이미 있으면 실패하므로, 파일 시스템 수준의 뮤텍스가 됩니다.

1. 락 획득
refs/heads/main.lock을 O_EXCL로 생성. 실패하면 "unable to lock ref"
→
2. 기대값 검증
현재 ref 값이 <oldvalue>와 같은지 확인 (compare-and-swap)
→
3. 락 파일에 기록
새 OID를 .lock에 쓰고 close (+ 필요 시 fsync)
→
4. rename
main.lock → main. 원자적 교체. reflog에도 한 줄 추가

03편의 객체 쓰기와 똑같은 패턴입니다. "임시 파일에 쓰고 rename"이 Git 전반의 원자성 관용구입니다. 차이는 여기서 compare-and-swap(기대값 검증)이 추가된다는 점인데, 이것이 동시 push 충돌을 잡아내는 근거입니다.

bash — CAS 직접 사용
# "지금 값이 정확히 f7d3c0e일 때만 a1b2c3d로 바꿔라"
$ git update-ref refs/heads/main a1b2c3d f7d3c0e

# 기대값이 틀리면 거부된다
$ git update-ref refs/heads/main a1b2c3d 0000000
error: cannot lock ref 'refs/heads/main': is at f7d3c0e but expected 0000000

# push도 같은 원리다. --force-with-lease가 바로 CAS 방식의 force push
$ git push --force-with-lease origin main
# ↑ "원격이 내가 마지막으로 본 값 그대로일 때만 덮어써라"
#   그 사이 동료가 push했다면 거부 → 동료 작업 유실 방지

--force는 무조건 덮어쓰므로 동료의 커밋을 소리 없이 날립니다. --force-with-lease를 기본으로 쓰십시오. 공유 브랜치를 rebase해야 하는 상황이라면 더욱 그렇습니다.

여러 ref를 한꺼번에 원자적으로 바꿀 수 있나요?

가능합니다. ref 트랜잭션입니다. git update-ref --stdin에 여러 명령을 주면 전부 성공하거나 전부 실패합니다.

bash — 원자적 다중 ref 갱신
$ git update-ref --stdin <<'EOF'
start
update refs/heads/main a1b2c3d f7d3c0e
update refs/heads/develop b2c3d4e a1b2c3d
delete refs/heads/old-feature
create refs/tags/v2.0 a1b2c3d
prepare
commit
EOF

# 하나라도 실패하면 아무것도 적용되지 않는다.
# 구현: 모든 .lock을 먼저 획득(prepare) → 전부 rename(commit) → 실패 시 전부 롤백(abort)

이것이 atomic push의 기반입니다. git push --atomic은 여러 브랜치를 한 번에 밀 때 "일부만 반영되는" 중간 상태를 방지합니다. 릴리스 태그와 브랜치를 동시에 밀어야 하는 배포 파이프라인에서 중요합니다.

다만 files 백엔드의 한계가 여기서 드러납니다. 락을 ref마다 따로 잡으므로, 갱신할 ref가 많으면 락 파일도 그만큼 만들어야 합니다. 그리고 packed-refs에 손대야 하는 경우에는 62MB짜리 파일 전체를 다시 쓰게 됩니다. ref 두 개를 바꾸려고 124MB를 읽고 쓰는 것입니다. 이 비효율이 바로 다음 주제 reftable이 등장한 이유입니다(12편).

락 파일이 남아서 작업이 막히는 경우는 어떻게 하나요?

프로세스가 비정상 종료하면 .lock 파일이 남아 이후 모든 갱신이 실패합니다. 흔한 운영 이슈입니다.

bash — 락 문제 진단과 해소
$ git commit -m "fix"
fatal: Unable to create '.git/index.lock': File exists.

# 1) 정말로 다른 git 프로세스가 돌고 있는지 확인 (가장 중요!)
$ ps aux | grep git                # Linux/macOS
$ Get-Process git -ErrorAction SilentlyContinue   # PowerShell

# 2) 없다면 잔존 락을 제거
$ find .git -name '*.lock' -print
.git/index.lock
.git/refs/heads/main.lock
$ find .git -name '*.lock' -delete

# 3) 상태 점검
$ git status && git fsck

돌고 있는 프로세스를 확인하지 않고 락을 지우면 진짜 경쟁 상태를 만듭니다. 특히 IDE가 백그라운드에서 git status를 주기적으로 돌리는 환경, CI 러너가 같은 워크스페이스를 공유하는 환경에서 위험합니다.

실무 교훈: 같은 저장소 디렉토리를 여러 프로세스가 동시에 쓰는 구성을 피하십시오. 병렬 CI 잡이 같은 체크아웃을 공유하면 락 충돌이 상시화됩니다. git worktree로 워킹 트리를 분리하거나(객체 DB는 공유, 인덱스는 분리), 잡마다 독립 클론을 쓰는 것이 정석입니다.

📌 핵심 정리

  • 브랜치는 OID 40자 + 개행 = 41바이트 텍스트 파일이다. 생성·삭제가 파일 하나 쓰기/지우기이므로 브랜치가 "공짜"다. symref(ref: refs/heads/main)는 다른 ref를 가리키는 간접 참조로, HEAD가 이 방식이다.
  • loose ref와 packed-refs는 "loose가 이긴다" 규칙으로 공존한다. 쓰기는 항상 loose로, 정리는 pack-refs가 한다. 느슨한 객체와 팩 파일의 관계와 같은 패턴이다.
  • reflog는 <old> <new> <committer> <time>\t<메시지> 줄의 나열이다. HEAD~1(커밋의 부모)과 HEAD@{1}(이전에 가리키던 값)은 전혀 다르며, 후자가 사고 복구의 핵심이다.
  • ref 갱신은 ".lock 생성(O_EXCL) → 기대값 검증(CAS) → 기록 → rename"으로 원자적이다. --force-with-lease가 바로 이 CAS를 push에 적용한 것이다.
  • update-ref --stdin과 push --atomic으로 다중 ref를 전부-또는-전무로 갱신할 수 있다. 다만 packed-refs를 건드리면 파일 전체를 다시 써야 하는 비효율이 있고, 이것이 reftable의 등장 배경이다.
