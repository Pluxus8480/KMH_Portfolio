객체 수십만 개를 파일 하나로

팩 파일 포맷 해부 — PACK 헤더 · 3비트 타입 + 가변 길이 크기 · 두 가지 델타 참조

Part 1: 왜 팩 파일이 필요한가

느슨한 객체만으로는 안 되나요? 압축도 되어 있는데요.

세 가지가 감당이 안 됩니다.

1) 디스크 블록 낭비. 파일 시스템은 파일 하나에 최소 1블록(보통 4KB)을 배정합니다. 압축 후 200바이트인 커밋 객체도 4KB를 먹습니다. 객체 30만 개면 실제 데이터가 60MB여도 디스크는 1.2GB를 씁니다.

2) inode와 탐색 비용. 객체마다 파일 하나이므로 inode도 30만 개입니다. git log 한 번에 수천 번의 open/read/close 시스템 콜이 발생합니다.

3) 객체 간 유사성을 못 살림. 가장 결정적입니다. 어떤 파일의 v1과 v2는 99% 같은데, 느슨한 객체는 각각 독립적으로 압축되므로 그 유사성이 전혀 활용되지 않습니다.

🎯 비유로 이해하기

느슨한 객체는 책 한 권마다 따로 상자에 담아 창고에 쌓는 것입니다. 얇은 팸플릿도 큰 상자 하나를 차지하고, 상자를 찾고 여는 데 시간이 걸립니다.

팩 파일은 모든 책을 한 컨테이너에 차곡차곡 넣고, 앞에 색인 카드를 붙이는 것입니다. 게다가 "이 책은 저 책과 3페이지만 다름"이라고 적어 두면 종이를 훨씬 아낄 수 있습니다.

팩 파일은 git gc, git repack 때 만들어지고, clone/fetch로 받은 데이터도 처음부터 팩 형태로 도착합니다. 즉 네트워크 전송 포맷과 디스크 저장 포맷이 동일합니다. 받은 팩을 그대로 디스크에 두면 되므로 변환 비용이 없습니다.

팩 파일은 몇 개의 파일로 구성되나요?

필수는 두 개, 선택이 세 개입니다.

파일필수내용
pack-*.pack필수객체 데이터 본체
pack-*.idx필수OID → 팩 내 오프셋 색인 (10편)
pack-*.rev선택오프셋 순 → 색인 위치 역매핑
pack-*.mtimes선택객체별 mtime (cruft pack용)
pack-*.bitmap선택도달 가능성 비트맵. clone/fetch 가속
multi-pack-index선택여러 팩을 한 번에 색인 (10편)

파일 이름의 * 부분은 팩에 담긴 객체 이름들의 해시(정확히는 정렬된 OID 목록의 해시)라서, 같은 객체 집합이면 같은 이름이 나옵니다.

Part 2: .pack 파일의 바이트 구조

팩 파일의 전체 레이아웃은 어떻게 되나요?

놀랄 만큼 단순합니다. 12바이트 헤더 + 객체들 + 체크섬이 전부이고, 객체 사이에 구분자나 색인이 없습니다.

헤더 (12B)
"PACK" (4B)버전 (4B) = 2객체 개수 (4B)
객체 1..N
타입+크기 헤더(델타면) base 참조zlib 압축 데이터
트레일러
앞 내용 전체의 체크섬 (SHA-1이면 20B)
bash — 진짜 헤더 보기
$ ls .git/objects/pack/
pack-a1b2c3d4e5f6...pack  pack-a1b2c3d4e5f6...idx

$ xxd -l 12 .git/objects/pack/pack-a1b2c3*.pack
00000000: 5041 434b 0000 0002 0000 1a2b            PACK........+

# 50 41 43 4b = "PACK"
# 00 00 00 02 = 버전 2 (Git은 2만 생성, 2와 3을 읽을 수 있음)
# 00 00 1a 2b = 객체 6699개

주의: 버전 필드가 4바이트인 것은 "4G 버전은 안 나오겠지"라는 농담 섞인 관찰이 Git 공식 문서에 그대로 적혀 있습니다. 반면 객체 개수가 4바이트인 것은 실질적 제약입니다 — 팩 하나에 43억 개 이상의 객체는 담을 수 없습니다.

객체마다 붙는 "타입+크기 헤더"가 특이하다고 들었습니다.

가장 정교한 부분입니다. 첫 바이트에 타입 3비트와 크기 하위 4비트를 함께 욱여넣고, 크기가 크면 바이트를 이어 붙입니다.

타입 + 크기 헤더의 비트 배치
첫 바이트:
  비트 7   : MSB. 1이면 "다음 바이트도 크기의 일부"
  비트 6-4 : 객체 타입 (3비트)
  비트 3-0 : 크기의 하위 4비트

이어지는 바이트 (MSB가 1인 동안 반복):
  비트 7   : 계속 플래그
  비트 6-0 : 크기의 다음 7비트

크기 = size0 + (size1 << 4) + (size2 << 11) + (size3 << 18) + ...
        \4비트/  \---- 7비트씩 ----------------------------/
       (앞쪽 바이트가 덜 중요한 자리 = 리틀엔디언식 누적)

타입 3비트가 표현하는 값은 02편에서 본 열거형과 같습니다.

값타입설명
1OBJ_COMMIT커밋
2OBJ_TREE트리
3OBJ_BLOB블롭
4OBJ_TAG태그
5(예약)미래 확장용. 현재 무효
6OBJ_OFS_DELTAbase를 "팩 내 상대 오프셋"으로 참조
7OBJ_REF_DELTAbase를 "OID"로 참조
0무효—

실제로 디코딩해 보겠습니다. 바이트 0x9E 0x0C를 읽는다고 합시다.

디코딩 예제
0x9E = 1001 1110
        | \+/ \-+/
        |  |    \-- 크기 하위 4비트 = 1110 = 14
        |  \------- 타입 = 001 = 1 = OBJ_COMMIT
        \---------- MSB=1 → 다음 바이트도 읽어라

0x0C = 0000 1100
        | \--+--/
        |    \----- 크기 다음 7비트 = 0001100 = 12
        \---------- MSB=0 → 여기서 끝

크기 = 14 + (12 << 4) = 14 + 192 = 206
→ "206바이트짜리 커밋 객체"

느슨한 객체와 달리 팩에는 "commit 206\0" 같은 텍스트 헤더가 없습니다. 타입과 크기를 이 2바이트가 대신하기 때문입니다. 다만 OID를 계산할 때는 그 텍스트 헤더를 다시 만들어 붙입니다. 그래야 느슨한 객체와 같은 OID가 나오기 때문입니다 — 저장 방식이 달라도 이름은 같아야 한다는 원칙이 지켜집니다.

왜 크기를 가변 길이로 인코딩하나요? 고정 8바이트면 간단할 텐데요.

대부분의 객체가 작기 때문입니다. 커밋은 보통 200바이트대, 트리는 수십~수백 바이트입니다. 고정 8바이트를 쓰면 객체 30만 개 × 낭비 6바이트 = 1.8MB가 순수 오버헤드로 날아갑니다.

가변 길이 인코딩(VLQ)이면 크기 127 이하는 1바이트, 2047 이하는 2바이트로 끝납니다. 동시에 상한이 없어서 4GB 넘는 blob도 표현할 수 있습니다. Git 문서의 표현대로 "길이가 32비트 같은 것에 제약되지 않습니다".

이 VLQ 아이디어는 Git 곳곳에 재사용됩니다. 인덱스 v4의 경로 접두사 길이, OFS_DELTA의 오프셋, 델타 명령의 크기 — 전부 같은 계열의 인코딩입니다. 포맷 설계에서 하나의 도구를 반복 사용해 구현 복잡도를 낮춘 사례입니다.

Part 3: 두 가지 델타 참조 — OFS vs REF

타입 6과 7은 무슨 차이인가요?

둘 다 "나는 다른 객체와의 차이만 저장했다"는 뜻이고, base 객체를 어떻게 가리키느냐만 다릅니다.

구분OBJ_OFS_DELTA (6)OBJ_REF_DELTA (7)
base 참조 방식 현재 위치로부터의 음의 상대 오프셋 base의 OID 전체 (20/32바이트)
차지하는 공간보통 1~4바이트20바이트 (SHA-1) / 32바이트 (SHA-256)
base 위치반드시 같은 팩 안, 앞쪽팩 밖에 있어도 됨
주 용도디스크에 저장되는 정상 팩thin pack (전송 시), 팩 경계를 넘는 참조
장점공간 효율 압도적위치에 독립적이라 팩 재구성에 강함

OFS_DELTA의 오프셋은 또 다른 가변 길이 인코딩을 씁니다. 크기 인코딩과 미묘하게 다르니 주의해야 합니다.

offset 인코딩 (size 인코딩과 다름!)
n바이트. 마지막을 제외한 모든 바이트의 MSB가 1.
각 바이트의 하위 7비트를 이어 붙이고,
n ≥ 2이면 2^7 + 2^14 + ... + 2^(7*(n-1)) 을 더한다.

왜 더하나? 같은 값을 여러 길이로 표현할 수 없게 만들어
정규형(canonical encoding)을 보장하기 위해서다.
(1바이트로 표현 가능한 값을 2바이트로 쓰는 것을 금지)

예) 바이트 [0x81, 0x23]
    하위 7비트 이어붙이기: 0000001 0100011 = 163
    n=2이므로 + 2^7 = 128
    최종 오프셋 = 291  (현재 객체 헤더 위치에서 291바이트 앞이 base)

오프셋이 "현재 객체의 타입 바이트 위치로부터 뒤로" 측정된다는 점이 중요합니다. 절대 오프셋이 아니라 상대 오프셋이므로, 팩 전체를 다른 위치에 이어 붙여도 참조가 깨지지 않습니다.

thin pack이 뭔가요? 왜 REF_DELTA가 필요하죠?

base 객체를 포함하지 않는 팩입니다. 전송 시에만 쓰입니다.

상황을 그려 보겠습니다. 서버와 클라이언트가 커밋 100개를 공유하고 있고, 서버에 커밋 1개가 추가되었습니다. 그 커밋의 blob은 클라이언트가 이미 가진 blob과 99% 같습니다.

서버의 판단
"클라이언트는 base 객체 X를 이미 갖고 있다"(네고시에이션으로 파악)
→
thin pack 전송
X를 빼고, X에 대한 REF_DELTA만 담아 보냄. 전송량 급감
→
클라이언트의 복원
index-pack --fix-thin이 로컬의 X를 팩 뒤에 덧붙여 자기 완결적 팩으로 만듦

Git 문서가 명시하듯 "디스크에 저장될 때 팩은 순환 의존을 피하기 위해 반드시 자기 완결적이어야" 합니다. thin pack은 네트워크 위에서만 존재하는 임시 형태입니다.

REF_DELTA가 필요한 이유는 명확합니다. OFS_DELTA는 "이 팩 안의 몇 바이트 앞"을 가리키는데, base가 팩 안에 없으면 가리킬 오프셋 자체가 없습니다. 그래서 팩 밖을 가리켜야 할 때는 OID로 지목할 수밖에 없습니다.

Part 4: 팩을 직접 열어 보기

팩 내용을 사람이 읽을 수 있는 형태로 볼 수 있나요?

git verify-pack -v가 팩의 모든 객체를 나열해 줍니다. 델타 체인까지 보여 주므로 학습에 최적입니다.

bash — 팩 내부 덤프
$ git verify-pack -v .git/objects/pack/pack-a1b2c3*.idx | head -20
a1b2c3d4... commit 206 141 12
e5f6a7b8... commit 211 146 153
c9d0e1f2... tree   1247 631 299
3f4a5b6c... blob   104832 31204 930
7d8e9f0a... blob   9 20 32134 1 3f4a5b6c...
                    |  |   |    |  \- base 객체 OID
                    |  |   |    \---- 델타 체인 깊이 = 1
                    |  |   \--------- 팩 내 오프셋
                    |  \------------- 팩 안에서 차지하는 크기 (압축 후)
                    \---------------- 복원했을 때의 크기

non delta: 1204 objects
chain length = 1: 872 objects
chain length = 2: 531 objects
...
chain length = 50: 3 objects              # ← 기본 최대 깊이

여기서 7d8e9f0a를 보십시오. 원래 크기는 9바이트인데 팩에서 20바이트를 씁니다. 델타 명령 자체의 오버헤드 때문입니다. 아주 작은 객체는 델타가 손해일 수 있어서, 팩 생성기가 이를 판단합니다(09편).

bash — 팩 통계 한눈에 보기
# 타입별 개수와 크기 분포
$ git verify-pack -v .git/objects/pack/*.idx \
    | grep -E '^[0-9a-f]{40}' \
    | awk '{t[$2]++; s[$2]+=$4} END {for(k in t) printf "%-8s %7d개  %10d bytes\n", k, t[k], s[k]}'
blob       284917   98234112
commit      12043    1802341
tree        71204    9823114

# 델타 체인 길이 분포 (깊을수록 복원이 느려짐)
$ git verify-pack -v .git/objects/pack/*.idx | grep 'chain length'
chain length = 1: 41282 objects
chain length = 2: 28114 objects
...

# 팩 자체의 무결성 검사 (체크섬 + 모든 객체 해시)
$ git verify-pack -s .git/objects/pack/*.idx && echo OK
팩 파일이 손상되면 어떻게 되나요?

팩에는 마지막 체크섬이 있고, 각 객체는 .idx에 CRC32가 기록되어 있으며(10편), 최종적으로는 객체 해시가 다시 검증됩니다. 세 겹입니다.

다만 위험 요소가 하나 있습니다. 델타 체인이 있으므로 base 객체 하나가 손상되면 그것에 의존하는 수백 개 객체가 함께 못 읽힙니다. 느슨한 객체는 서로 독립적이라 손상이 국소적이지만, 팩은 연쇄 피해가 생깁니다.

bash — 손상 복구 전략
# 1) 어떤 객체가 문제인지 확인
$ git verify-pack -v .git/objects/pack/pack-xxx.idx
error: pack-xxx.pack: object 3f4a5b6c... is corrupt

# 2) 원격에 있다면 그냥 다시 받는 것이 가장 빠르다
$ mv .git/objects/pack/pack-xxx.* /tmp/     # 손상된 팩을 치우고
$ git fetch --all                            # 다시 받는다

# 3) 다른 클론이 있다면 그 저장소를 대체 소스로 쓸 수 있다
$ git fsck --lost-found
$ echo /path/to/good-repo/.git/objects > .git/objects/info/alternates

실무 교훈은 "팩은 효율적이지만 계란을 한 바구니에 담는 구조"라는 것입니다. 그래서 Git 호스팅 서비스는 복제본을 여러 대 두고, 큰 저장소에서는 gc.autoPackLimit과 repack 전략을 신중하게 잡습니다.

📌 핵심 정리

  • 팩 파일 = "PACK" + 버전(2) + 객체 수 + 객체들 + 체크섬. 객체 사이에 구분자가 없고, 헤더의 크기 정보로 경계를 판단한다.
  • 객체 헤더는 첫 바이트에 타입 3비트 + 크기 하위 4비트를 담고, 필요하면 7비트씩 이어 붙이는 가변 길이 인코딩이다. 작은 객체가 대다수라 이 절약이 크게 효과적이다.
  • 팩 안에는 "commit 206\0" 같은 텍스트 헤더가 없다. 대신 OID 계산 시 그 헤더를 재구성해 붙이므로, 느슨한 객체와 같은 OID가 보장된다.
  • 델타는 OFS(상대 오프셋, 1~4바이트)와 REF(OID, 20/32바이트) 두 방식이다. 디스크 팩은 OFS를 쓰고, base를 포함하지 않는 thin pack(전송 전용)은 REF를 쓴다.
  • 디스크 팩은 자기 완결적이어야 한다. thin pack은 index-pack --fix-thin으로 base를 덧붙여 완결시킨 뒤 저장된다.
