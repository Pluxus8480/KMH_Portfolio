팩 안의 객체 하나를 어떻게 즉시 찾을까?

.idx v2의 fanout 테이블 · CRC32 · 8바이트 오프셋 · .rev · multi-pack-index

Part 1: 구분자 없는 파일에서 객체를 찾는 문제

팩 파일에는 객체 사이 구분자도 색인도 없다고 했습니다. 그럼 특정 OID를 어떻게 찾나요?

팩 파일만으로는 처음부터 순차적으로 풀어 보는 방법밖에 없습니다. 객체 30만 개짜리 팩에서 마지막 객체를 찾으려면 앞의 29만 9,999개를 전부 압축 해제해야 합니다. 명백히 불가능합니다.

그래서 짝을 이루는 .idx 파일이 존재합니다. 역할은 단 하나, "OID → 팩 내 바이트 오프셋" 매핑입니다.

질의
"객체 7d8e9f0a...를 다오"
→
.idx 조회
fanout으로 구간 좁히기 → 이진 탐색 → 오프셋 획득
→
.pack 접근
그 오프셋으로 seek → 헤더 파싱 → (델타면 base까지 따라가서) 복원
🎯 비유로 이해하기

.pack은 페이지 번호가 없는 두꺼운 백과사전입니다. 항목이 빽빽이 붙어 있어서 원하는 항목을 찾으려면 처음부터 읽어야 합니다.

.idx는 책 뒤에 붙은 색인입니다. "가나다순으로 정렬된 표제어 → 몇 번째 글자에서 시작"을 알려 줍니다. 게다가 "ㄱ으로 시작하는 항목은 1번부터 812번까지"라는 요약표(fanout)가 앞에 붙어 있어 탐색 범위를 단번에 좁혀 줍니다.

왜 .pack 안에 색인을 같이 넣지 않았나요?

세 가지 이유가 있습니다.

1) 전송 포맷과 저장 포맷의 분리. 네트워크로 오가는 것은 .pack뿐입니다. 색인은 받는 쪽이 git index-pack으로 스스로 만듭니다. 색인까지 전송하면 대역폭 낭비이고, 어차피 수신 측에서 검증하며 만들어야 합니다.

2) 색인은 재생성 가능한 파생물입니다. 손상되면 git index-pack으로 다시 만들면 됩니다. 원본과 파생물을 파일로 분리하는 것이 복구에 유리합니다.

3) 색인 포맷을 독립적으로 진화시킬 수 있습니다. 실제로 .idx는 v1에서 v2로 바뀌었고, .rev, .bitmap, MIDX 같은 부가 색인이 계속 추가되었습니다. .pack 포맷은 2005년 이래 사실상 고정입니다.

이 분리는 "불변의 데이터와 가변의 색인을 나눈다"는 일반적인 스토리지 설계 원칙의 사례입니다. 데이터베이스가 테이블과 인덱스를 분리하는 것과 같은 이유입니다.

Part 2: .idx v2의 다섯 블록

.idx 파일은 어떤 구조인가요?

버전 2가 현재 표준입니다. 테이블 다섯 개가 순서대로 이어 붙은 단순한 구조입니다.

헤더 (8B)
매직 \377tOc버전 = 2
① fanout
256 × 4바이트 = 1024B 고정
② OID 목록
N × 20바이트 (정렬됨)
③ CRC32
N × 4바이트
④ 오프셋(4B)
N × 4바이트. MSB=1이면 ⑤의 인덱스
⑤ 큰 오프셋
M × 8바이트 (2GiB 미만 팩이면 비어 있음)
트레일러
.pack의 체크섬 사본.idx 자신의 체크섬

헤더의 매직 \377tOc(FF 74 4F 63)가 재미있습니다. v1에는 헤더가 없고 곧바로 fanout이 시작되는데, fanout[0]이 0xFF744F63(약 42억)일 리 없으므로 이 값을 "이건 v2다"라는 표식으로 재활용한 것입니다. 하위 호환을 유지하면서 버전을 구분하는 전형적인 기법입니다.

fanout 테이블은 정확히 무엇을 담고 있나요?

Git 문서의 정의는 이렇습니다. "N번째 항목은 OID의 첫 바이트가 N 이하인 객체의 개수를 기록한다." 즉 누적 개수(prefix sum)입니다.

fanout의 의미
fanout[0x00] = 첫 바이트가 0x00인 객체 수
fanout[0x01] = 첫 바이트가 0x00 또는 0x01인 객체 수 (누적)
...
fanout[0xFF] = 전체 객체 수

⇒ 첫 바이트가 0x7d인 객체들이 놓인 구간은
     [ fanout[0x7c], fanout[0x7d] )

예) fanout[0x7c] = 121,043
    fanout[0x7d] = 122,198
  → 0x7d로 시작하는 객체는 1,155개이고,
    OID 목록의 121,043번째부터 122,197번째까지에 있다.

이 한 번의 조회로 탐색 범위가 평균 1/256로 줄어듭니다. 객체 30만 개면 1,170개 남짓으로 좁혀지고, 여기서 이진 탐색을 하면 11번 비교로 끝납니다.

조회 알고리즘 (개념 코드)
int find_object(idx, oid) {
        /* 1) fanout 한 번 읽어 구간 확정 — O(1) */
        first = oid.bytes[0];
        lo = (first == 0) ? 0 : fanout[first - 1];
        hi = fanout[first];

        /* 2) 정렬된 OID 목록에서 이진 탐색 — O(log(N/256)) */
        while (lo < hi) {
                mid = (lo + hi) / 2;
                cmp = memcmp(oid_table[mid], oid, 20);
                if      (cmp == 0) return mid;
                else if (cmp <  0) lo = mid + 1;
                else               hi = mid;
        }
        return -1;   /* 이 팩에 없음 */
}

이 구조의 진짜 강점은 캐시 지역성입니다. v1은 (오프셋 4바이트 + OID 20바이트)를 섞어서 24바이트 엔트리로 저장했습니다. 이진 탐색이 OID만 보는데도 오프셋 4바이트가 캐시 라인을 함께 차지했습니다. v2는 OID만 모아 두어, 한 캐시 라인(64B)에 OID 3개가 들어갑니다. Git 문서가 "바이너리 탐색의 캐시 사용량을 줄이기 위해"라고 명시한 부분입니다.

④번 4바이트 오프셋으로 2GiB 넘는 팩을 어떻게 다루나요?

MSB를 플래그로 씁니다. 4바이트 값의 최상위 비트가 0이면 "이 값 자체가 오프셋"(최대 2GiB − 1), 1이면 "나머지 31비트는 ⑤번 8바이트 테이블의 인덱스"라는 뜻입니다.

오프셋 해석
uint32_t v = offset_table[i];

if (!(v & 0x80000000))
        offset = v;                           /* 31비트 직접 값 */
else
        offset = large_offset_table[v & 0x7FFFFFFF];   /* 8바이트 테이블 참조 */

Git 문서가 덧붙이는 설명이 중요합니다. "팩은 자주 쓰이는 객체를 앞쪽에 배치하므로, 대부분의 참조는 이 테이블을 볼 필요가 없다." 즉 자주 읽히는 객체는 2GiB 이내에 놓여 4바이트 오프셋으로 끝나고, 8바이트 간접 참조는 예외적으로만 발생합니다.

이런 "흔한 경우를 작게, 드문 경우를 크게" 설계가 팩 포맷 전반에 일관되게 나타납니다. 08편의 가변 길이 크기 인코딩, 09편의 COPY 명령 비트맵, 그리고 여기의 오프셋 간접 참조가 모두 같은 철학입니다.

③번 CRC32는 왜 필요한가요? 어차피 객체 해시로 검증하지 않나요?

목적이 다릅니다. Git 문서의 설명이 정확합니다. "v2에서 새로 추가되어, 재패킹 시 압축 데이터를 팩에서 팩으로 그대로 복사할 때 감지되지 않은 손상이 생기지 않게 한다."

git repack은 성능을 위해 이미 압축된 바이트를 풀지 않고 그대로 복사합니다. 압축을 풀지 않으므로 객체 해시를 검증할 기회가 없습니다. 이때 CRC32가 "복사한 바이트가 원본과 같은가"를 싸게 확인해 줍니다.

정리하면 방어선이 층층이 다른 목적을 가집니다. CRC32는 "복사 중 손상", zlib Adler-32는 "압축 스트림 손상", 객체 해시는 "내용 자체의 진위", 팩/idx 트레일러 체크섬은 "파일 전체의 무결성"을 봅니다.

Part 3: .rev · .mtimes · .bitmap — 보조 색인들

.rev 파일은 무슨 역할인가요?

.idx가 답하지 못하는 질문에 답합니다. "팩의 오프셋 X에 있는 객체는 몇 번째 객체인가?"입니다.

왜 이게 필요할까요? 팩에서 객체 하나를 읽을 때 그 객체의 끝 위치를 알아야 할 때가 있습니다. 팩에는 길이 정보가 헤더에만 있고 "다음 객체가 어디서 시작하는지"는 오프셋 순으로 정렬해야만 알 수 있습니다. .idx는 OID 순으로 정렬되어 있어 이 질문에 못 답합니다.

.rev 포맷
매직 'RIDX' (0x52494458)   4바이트
버전 = 1                    4바이트
해시 ID (1=SHA-1, 2=SHA-256) 4바이트
인덱스 위치 테이블           N × 4바이트
    — 팩 내 오프셋 순으로 정렬되어 있고,
      각 값은 그 객체의 .idx상 위치(=OID 정렬 순서)
트레일러                     팩 체크섬 + 자신의 체크섬

.rev가 없으면 Git은 매번 메모리에서 오프셋 순 정렬을 수행해야 합니다(revindex). 객체 수백만 개짜리 저장소에서는 그 정렬만으로 수백 ms가 날아갑니다. .rev는 그 결과를 디스크에 캐싱한 것입니다.

실제로 쓰이는 곳은 git cat-file --batch-all-objects, 비트맵 기반 rev-list, 그리고 repack입니다. pack.writeReverseIndex로 생성을 제어합니다.

.mtimes와 cruft pack은요?

GC와 직결된 문제를 풀기 위해 도입되었습니다(20편에서 자세히 다룹니다).

도달 불가능한 객체는 "오래되면" 지웁니다(기본 2주). 그런데 객체가 팩 안에 들어가면 개별 mtime이 사라집니다 — 팩 파일 하나의 mtime만 남기 때문입니다. 그래서 예전 Git은 도달 불가능한 객체를 느슨한 객체로 풀어내서 mtime을 보존했고, 이것이 "GC 후 오히려 파일 수가 폭증"하는 악명 높은 현상을 낳았습니다.

cruft pack은 도달 불가능한 객체들을 별도 팩에 모으고, 짝이 되는 .mtimes 파일에 객체별 mtime을 4바이트씩 기록합니다. 느슨한 객체 폭발 없이 개별 만료 판정이 가능해집니다.

bash — cruft pack 확인
$ git gc --cruft
$ ls .git/objects/pack/
pack-aaa...pack  pack-aaa...idx                    # 도달 가능한 객체
pack-bbb...pack  pack-bbb...idx  pack-bbb...mtimes # cruft pack

# .mtimes가 있는 팩이 cruft pack이다
$ git repack --cruft --cruft-expiration=30.days -d
.bitmap은 뭔가요?

도달 가능성(reachability) 비트맵입니다. 서버 성능의 핵심 무기입니다.

git clone이나 fetch 때 서버는 "이 커밋에서 도달 가능한 모든 객체"를 나열해야 합니다. 순진하게 하면 커밋 그래프 전체를 걸으며 모든 트리를 펼쳐야 하고, 대형 저장소에서는 수십 초가 걸립니다.

비트맵은 선택된 커밋들에 대해 "도달 가능한 객체 집합"을 비트 벡터로 미리 저장합니다. 객체 N개짜리 팩이면 N비트 벡터이고, 도달 가능하면 1입니다.

비트맵 없이
커밋 → 트리 → 하위 트리 → blob 전부 방문. 수백만 객체 그래프 순회
→
비트맵으로
"원하는 집합" AND NOT "이미 가진 집합" = 비트 연산 몇 번. 보낼 객체 확정

"클라이언트가 가진 것을 빼고 보내라"는 요구가 정확히 집합 차집합이므로, 비트 벡터 표현과 완벽히 맞아떨어집니다. GitHub가 거대 저장소의 clone을 수 초 안에 시작할 수 있는 이유의 상당 부분이 여기에 있습니다.

bash — 비트맵 켜기
$ git config repack.writeBitmaps true
$ git repack -adb              # -b : 비트맵 생성
$ ls .git/objects/pack/*.bitmap

# 효과 측정
$ time git rev-list --count --objects --all
# 비트맵 전: 4.2s  →  비트맵 후: 0.3s

비트맵은 팩이 하나일 때 가장 잘 동작합니다. 팩이 여러 개면 커버리지가 떨어지므로, 비트맵을 쓰려면 repack -a로 단일 팩을 유지하거나 MIDX 비트맵을 써야 합니다.

Part 4: multi-pack-index — 팩이 많아질 때

팩이 여러 개면 객체 하나 찾는 데 팩 개수만큼 .idx를 뒤져야 하나요?

정확합니다. 그것이 문제입니다. fetch할 때마다 팩이 하나씩 늘어나므로, 활발한 저장소에서는 금세 팩이 수십 개가 됩니다. 객체 하나를 찾을 때마다 모든 팩의 .idx에 이진 탐색을 돌려야 합니다.

multi-pack-index(MIDX)는 여러 팩을 하나의 통합 색인으로 덮습니다. 팩 자체는 그대로 두고 색인만 합치므로, 비싼 repack 없이 조회 성능을 회복할 수 있습니다.

MIDX 헤더 구조
4바이트 시그니처  : 'M','I','D','X'
1바이트 버전      : midx.version 설정값 (기본 2, 1과 2를 읽을 수 있음)
1바이트 OID 버전  : 1=SHA-1, 2=SHA-256
1바이트 청크 개수
1바이트 base MIDX 개수 (현재 항상 0)
4바이트 팩 파일 개수

이후 "청크 룩업 테이블" — (C+1) × 12바이트
  각 항목: 4바이트 청크 ID + 8바이트 파일 내 오프셋
  ID 0은 종료 표식

청크 기반 설계가 핵심입니다. 파일 앞에 "어떤 청크가 어디 있는지" 목록을 두고, 실제 데이터는 청크 단위로 담습니다. 나중에 새 청크(예: 비트맵, bloom filter)를 추가해도 구버전 Git은 모르는 청크를 건너뛰면 되므로 호환성이 유지됩니다. commit-graph(14편)도 같은 청크 포맷을 씁니다.

bash — MIDX 사용
# 현재 팩 개수 확인
$ ls .git/objects/pack/*.pack | wc -l
37

$ git multi-pack-index write
$ ls -lh .git/objects/pack/multi-pack-index

# 자동화: fetch 후 자동으로 MIDX 갱신
$ git config core.multiPackIndex true
$ git config maintenance.incremental-repack.enabled true
$ git maintenance start        # 백그라운드 유지보수 작업 등록

# MIDX 기반 비트맵 (팩이 여러 개여도 비트맵 이득을 봄)
$ git multi-pack-index write --bitmap
실무에서 이 색인들을 언제 신경 써야 하나요?

세 가지 시나리오가 전형적입니다.

1) CI 러너의 fetch가 점점 느려진다. 팩이 계속 쌓여 .idx 탐색이 누적된 경우입니다. git maintenance를 켜거나 주기적으로 git multi-pack-index write를 돌립니다.

2) 모노레포에서 git log -- path/가 느리다. 이건 색인 문제가 아니라 커밋 그래프 + 경로 필터 문제입니다. git commit-graph write --reachable --changed-paths가 답입니다(14편).

3) 서버에서 clone이 느리다. 비트맵이 없거나 커버리지가 낮은 경우입니다. repack -adb 또는 MIDX 비트맵을 씁니다.

bash — 저장소 건강 점검 루틴
# 현재 상태 한눈에
$ git count-objects -vH
$ ls .git/objects/pack/ | sed 's/.*\.//' | sort | uniq -c
     37 idx
     37 pack
      1 rev
      0 bitmap                # ← 비트맵 없음

# 권장 조치
$ git gc --aggressive         # (드물게, 시간 여유 있을 때만)
$ git repack -adb             # 단일 팩 + 비트맵
$ git commit-graph write --reachable --changed-paths
$ git multi-pack-index write  # 팩이 여러 개 유지되는 환경이라면

# 자동 유지보수 (Git 2.31+, 권장)
$ git maintenance start

git gc --aggressive는 --window=250 --depth=250으로 전체를 다시 압축합니다. 대형 저장소에서 수십 분~수 시간이 걸리고 메모리를 많이 씁니다. 일상적으로 돌릴 명령이 아니며, 대부분의 경우 git maintenance가 더 나은 선택입니다.

📌 핵심 정리

  • .idx는 "OID → 팩 내 오프셋" 매핑 전용 파일이다. 전송되지 않고 수신 측이 index-pack으로 직접 만들며, 손상되면 언제든 재생성할 수 있는 파생물이다.
  • fanout 256칸으로 탐색 범위를 1/256로 좁힌 뒤 이진 탐색한다. v2는 OID만 따로 모아 캐시 라인 효율을 높였고, 매직 \377tOc는 "불가능한 fanout[0] 값"을 버전 표식으로 재활용한 것이다.
  • 오프셋은 4바이트에 담되, MSB가 1이면 8바이트 테이블로 간접 참조한다. 자주 쓰이는 객체가 팩 앞쪽에 놓이므로 간접 참조는 드물게만 발생한다.
  • CRC32는 "재패킹 시 압축 데이터를 그대로 복사할 때"의 손상을 잡는다. 객체 해시·Adler-32·트레일러 체크섬과 목적이 각각 다른 별도의 방어선이다.
  • 보조 색인이 성능을 좌우한다. .rev(오프셋 → 색인 위치), .mtimes(cruft pack의 객체별 만료), .bitmap(도달 가능성 집합 연산), MIDX(여러 팩의 통합 청크 색인).
