Git은 내 스크립트를 어떻게 찾아서 실행할까?

훅 메커니즘 해부 — find_hook · 세 입력 채널 · 배치 위치 4종 · 실행 환경과 병렬화

Part 1: 훅의 정체 — 마법은 없다

훅이 "자동으로 실행된다"는 게 내부적으로 어떤 의미인가요?

거창한 플러그인 시스템이 아닙니다. Git은 정해진 시점에 "정해진 이름의 파일이 있는지 보고, 있으면 exec 한다"가 전부입니다.

Git 소스의 hook.c에 있는 find_hook()이 그 전부를 보여 줍니다.

hook.c — 훅 탐색의 핵심
const char *find_hook(struct repository *r, const char *name)
{
        static struct strbuf path = STRBUF_INIT;
        int found_hook;

        if (!r || !r->gitdir)
                return NULL;

        repo_git_path_replace(r, &path, "hooks/%s", name);   /* <gitdir>/hooks/<name> */
        found_hook = access(path.buf, X_OK) >= 0;             /* 실행 권한이 있는가? */

        ...
        if (!found_hook) {
                if (errno == EACCES && advice_enabled(ADVICE_IGNORED_HOOK)) {
                        ...
                        advise(_("The '%s' hook was ignored because "
                                 "it's not set as executable.\n"
                                 "You can disable this warning with "
                                 "`git config set advice.ignoredHook false`."),
                               path.buf);
                }
        }

핵심은 access(path, X_OK) 한 줄입니다. 경로를 조립하고 실행 권한(X_OK)이 있는지만 봅니다. 파일 확장자도, 등록 절차도, 매니페스트도 없습니다.

githooks 문서가 이를 한 문장으로 못 박습니다.

"Hooks that don't have the executable bit set are ignored." — 실행 비트가 없는 훅은 조용히 무시됩니다. 에러도, 경고도 원래는 없었습니다. 최근 Git이 EACCES인 경우에 한해 advice.ignoredHook 힌트를 띄워 주게 되었지만, 파일이 아예 없으면 여전히 아무 말도 하지 않고 그냥 통과합니다.

🎯 비유로 이해하기

훅은 회사 현관에 붙여 둔 "출근 시 읽을 것" 메모함과 같습니다.

Git은 매번 정해진 시각에 그 자리를 들여다봅니다. 메모가 있으면 읽고 시키는 대로 하고, 없으면 아무 일도 없었다는 듯 지나갑니다. 메모를 코팅해서 읽을 수 없게(실행 권한 없이) 두면, 역시 못 본 척하고 지나갑니다.

즉 "훅이 안 먹는다"는 문제의 원인은 거의 항상 자리가 틀렸거나, 이름이 틀렸거나, 읽을 수 없는 상태 셋 중 하나입니다.

"훅이 안 먹어요"를 진단하는 순서가 있을까요?

find_hook()이 보는 것을 그대로 역순으로 확인하면 됩니다.

bash — 훅 진단 3단계
# 1) 자리가 맞는가? (core.hooksPath가 설정돼 있으면 .git/hooks가 아니다!)
$ git config --get core.hooksPath
$ git rev-parse --git-path hooks        # Git이 실제로 보는 경로를 물어본다
.git/hooks

# 2) 이름이 정확한가? (.sample이 붙어 있으면 실행 안 된다)
$ ls -l $(git rev-parse --git-path hooks)
-rwxr-xr-x  pre-commit          # ✅ 동작
-rw-r--r--  commit-msg          # ❌ 실행 비트 없음
-rwxr-xr-x  pre-commit.sample   # ❌ 이름 불일치

# 3) 실행 권한이 있는가?
$ chmod +x $(git rev-parse --git-path hooks)/commit-msg

# 4) 직접 실행해 본다 (Git을 거치지 않고 격리 테스트)
$ .git/hooks/pre-commit; echo "exit=$?"

# 5) Git의 훅 실행기로 테스트 (인자·환경을 Git과 동일하게)
$ git hook run pre-commit

git rev-parse --git-path hooks가 가장 확실한 확인법입니다. core.hooksPath 설정까지 반영한 "Git이 실제로 들여다보는 경로"를 알려 주므로, 경로 추측을 없애 줍니다.

git hook run <이름>도 유용합니다. Git이 훅을 부를 때와 동일한 방식으로 실행해 주므로, "직접 실행하면 되는데 커밋할 때만 안 된다" 같은 환경 차이 문제를 재현할 수 있습니다.

Part 2: 세 개의 입력 채널, 세 개의 출력 채널

훅은 Git에게서 정보를 어떻게 받나요?

githooks 문서의 표현대로 "환경 변수, 커맨드라인 인자, stdin" 세 가지입니다. 훅마다 무엇을 쓰는지가 정해져 있습니다.

입력 ①
커맨드라인 인자 $1 $2 $3개수가 적고 고정된 값
입력 ②
stdin (줄 단위)개수가 가변인 목록 — ref 목록 등
입력 ③
환경 변수GIT_DIR, GIT_PUSH_OPTION_*, GIT_SENDEMAIL_*

왜 나눠 놓았는지는 규칙이 명확합니다.

채널언제 쓰이나예
인자 개수가 고정되고 적을 때 commit-msg의 메시지 파일 경로, update의 <ref> <old> <new>
stdin 개수가 가변인 목록일 때 pre-push/pre-receive의 ref 목록, post-rewrite의 재작성 커밋 목록
환경 변수 부가 컨텍스트, 선택적 정보 GIT_PUSH_OPTION_COUNT, GIT_DIR, GIT_EDITOR=:

이 구분에는 실용적 이유가 있습니다. 인자에는 개수 제한(ARG_MAX)이 있습니다. ref 수천 개를 push하는 경우 인자로는 담을 수 없으므로, 목록성 데이터는 반드시 stdin으로 흐릅니다. 04편에서 본 "고정 길이 필드 vs 가변 길이"와 같은 설계 감각입니다.

stdin으로 들어오는 줄 포맷에 공통 규칙이 있나요?

있습니다. 거의 모두 <old> <new> <ref> 삼종 세트이고, 공백 구분에 LF로 끝납니다.

stdin 줄 포맷 비교
pre-receive / post-receive / reference-transaction:
  <old-oid> SP <new-oid> SP <ref-name> LF

pre-push (로컬/원격 양쪽을 알려 주므로 4칸):
  <local-ref> SP <local-oid> SP <remote-ref> SP <remote-oid> LF

post-rewrite (재작성 전/후):
  <old-oid> SP <new-oid> [ SP <extra-info> ] LF

여기서 반드시 알아야 할 관례가 하나 있습니다. 11편의 reflog 첫 줄에서 본 것과 같은 규칙입니다.

"존재하지 않음"은 전부 0으로 채운 OID(0000...0000)로 표현됩니다. 문서가 각 훅마다 이를 명시합니다 — 새 ref를 만들 때는 <old-oid>가 all-zeroes이고, pre-push에서 원격에 아직 없는 ref면 <remote-oid>가 all-zeroes입니다.

그래서 범위 계산을 할 때 0 검사를 빠뜨리면 반드시 터집니다. 0000000..abc123 같은 리비전 범위는 존재하지 않으므로 git rev-list가 실패합니다. 새 브랜치 push에서 훅이 깨지는 전형적인 원인입니다.

bash — all-zeroes를 안전하게 다루기
#!/bin/sh
# 해시 길이에 의존하지 않는 zero OID 얻기 (22편 — SHA-256이면 64자)
zero=$(git hash-object --stdin -t tree </dev/null | tr '[0-9a-f]' '0')

while read old new ref; do
    if [ "$old" = "$zero" ]; then
        echo "새 ref 생성: $ref"
        range="$new"                      # 범위가 아니라 단일 시작점
    elif [ "$new" = "$zero" ]; then
        echo "ref 삭제: $ref"
        continue                          # 검사할 커밋이 없다
    else
        range="$old..$new"                # 13편의 범위 표기
    fi

    git rev-list "$range" | while read c; do
        : # 커밋별 검사
    done
done

tr '[0-9a-f]' '0'으로 zero OID를 만드는 것이 요령입니다. SHA-1이든 SHA-256이든 그 저장소의 올바른 길이로 나옵니다. 22편에서 말한 "40 하드코딩 금지"의 실제 적용입니다.

출력은 어떻게 처리되나요?

세 개의 출력 채널이 있고, 각각 의미가 전혀 다릅니다.

채널의미주의
종료 코드 0이면 진행, 0이 아니면 중단(중단 가능한 훅에 한해) 알림용 훅(post-*)은 종료 코드를 무시한다
stderr 사용자에게 보여 줄 메시지 거부 사유는 반드시 여기에
stdout 대개 그냥 출력. 일부 훅은 데이터 채널 fsmonitor-watchman은 stdout으로 파일 목록을 반환한다
파일 수정 인자로 받은 파일을 제자리에서 고침 prepare-commit-msg, commit-msg의 주된 용도

종료 코드의 의미가 훅마다 미묘하게 다른 점을 놓치기 쉽습니다. 문서를 종합하면 네 부류입니다.

① 작업을 중단시킴
pre-commit, commit-msg, pre-push, pre-receive, pre-rebase, pre-auto-gc
/
② 그 항목만 막음
update — 해당 ref 하나만 거부, 나머지는 진행
③ 완전히 무시됨
post-commit, post-merge, post-receive, post-update, post-applypatch — 알림 전용
/
④ 특수
post-checkout: 결과에 영향은 없지만 훅의 종료 코드가 명령의 종료 코드가 됨

④가 함정입니다. 문서의 표현입니다 — "This hook cannot affect the outcome of git switch or git checkout, other than that the hook's exit status becomes the exit status of these two commands." 체크아웃 자체는 이미 끝났는데 명령은 실패로 보입니다. CI 스크립트에서 git checkout이 비정상 종료 코드를 뱉어 파이프라인이 죽는 원인이 되곤 합니다.

서버 훅에는 또 하나의 특성이 있습니다. pre-receive, update, post-receive, post-update는 stdout과 stderr가 모두 git send-pack으로, 즉 push한 사람의 터미널로 전달됩니다. 문서가 "you can simply echo messages for the user"라고 권합니다. 서버에서 echo한 안내가 개발자 화면에 그대로 뜹니다.

Part 3: 어디에 두는가 — 네 가지 배치 전략

훅을 두는 위치가 여러 개라고 들었습니다. 뭐가 어떻게 다른가요?

네 가지가 있고, "팀 전체에 배포되는가"가 선택의 기준입니다.

방식위치범위클론되나?
① 기본 디렉토리 $GIT_DIR/hooks/ 그 저장소만 안 됨
② core.hooksPath 임의 경로 설정 범위 경로가 저장소 안이면 됨
③ 템플릿 init.templateDir 앞으로 만들 저장소 init 시 복사
④ config 훅 hook.<이름>.command 설정 범위 config 파일을 통해

①의 치명적 한계를 먼저 짚어야 합니다. .git/hooks/는 객체도 ref도 아니므로(01편) 클론되지 않습니다. "팀 전체에 커밋 컨벤션을 강제하자"를 이 방식으로 하면 반드시 실패합니다. 각자 수동 설치해야 하고, 신규 입사자는 모릅니다.

그럼 팀 배포는 ②번으로 하는 건가요?

현재까지의 사실상 표준입니다. 훅을 저장소 안에 커밋하고, 설정으로 가리킵니다.

bash — core.hooksPath 방식
# 저장소에 커밋되는 디렉토리를 만든다
$ mkdir -p .githooks
$ cat > .githooks/commit-msg <<'EOF'
#!/bin/sh
grep -qE '^(feat|fix|docs|refactor|test|chore)(\(.+\))?: .+' "$1" || {
    echo "Conventional Commits 형식이어야 합니다." >&2
    exit 1
}
EOF

# 실행 비트를 인덱스에 박아 둔다 (04편의 100755)
$ chmod +x .githooks/commit-msg
$ git add .githooks/commit-msg
$ git update-index --chmod=+x .githooks/commit-msg   # Windows에서 특히 중요

$ git ls-files --stage .githooks/
100755 a1b2c3d... 0	.githooks/commit-msg    # ← 755로 기록되었다

# 각자 한 번만 실행 (또는 setup 스크립트에 포함)
$ git config core.hooksPath .githooks

git update-index --chmod=+x가 핵심입니다. Windows는 파일 시스템에 실행 비트가 없으므로(04편), 이걸 해 두지 않으면 리눅스·맥 팀원이 클론했을 때 100644로 떨어져 훅이 조용히 무시됩니다. 가장 흔한 "나는 되는데 쟤는 안 돼" 사고입니다.

다만 core.hooksPath는 설정이므로 강제력이 없습니다. 사용자가 git config --unset core.hooksPath 하면 끝입니다. 이 점은 26편에서 자세히 다룹니다.

③ 템플릿 방식은 언제 쓰나요?

개인 환경 표준화에 적합합니다. 앞으로 만들거나 클론하는 모든 저장소에 자동으로 들어갑니다.

bash — 템플릿 디렉토리
$ mkdir -p ~/.git-templates/hooks
$ cp my-pre-commit ~/.git-templates/hooks/pre-commit
$ chmod +x ~/.git-templates/hooks/pre-commit
$ git config --global init.templateDir ~/.git-templates

# 이후 init/clone 하는 저장소에 자동 복사된다
$ git init newrepo && ls newrepo/.git/hooks/pre-commit
newrepo/.git/hooks/pre-commit

# 기존 저장소에 소급 적용하려면 init을 다시 돌린다 (안전한 연산)
$ cd existing-repo && git init

git init을 기존 저장소에 다시 실행해도 안전합니다. 01편에서 본 대로 init은 없는 것만 만들 뿐 기존 객체나 ref를 건드리지 않습니다. 템플릿을 갱신한 뒤 재적용하는 관용적 방법입니다.

단점은 복사이지 링크가 아니라는 점입니다. 템플릿을 고쳐도 이미 만들어진 저장소에는 반영되지 않습니다. 그래서 팀 정책보다는 "내 모든 저장소에 기본으로 깔아 둘 것"에 적합합니다.

④ config 기반 훅은 처음 듣습니다.

최근 Git에 들어온 새 방식입니다. 훅을 파일 위치가 아니라 설정 값으로 등록합니다. git hook 문서의 예시가 개념을 잘 보여 줍니다.

config 기반 훅 (Documentation/git-hook.adoc)
[hook "linter"]
    event = pre-commit
    event = pre-push          # 여러 이벤트에 같은 명령을 붙일 수 있다
    command = ~/bin/linter --cpp20

[hook "no-leaks"]
    event = pre-commit
    command = ~/bin/leak-detector

이 방식이 해결하는 문제가 분명합니다.

기존 디렉토리 방식의 한계config 방식의 해결
한 이벤트에 훅 하나만 가능 — 여러 도구를 쓰려면 디스패처 스크립트를 직접 작성 여러 훅을 같은 이벤트에 등록 가능. 설정 파싱 순서대로 실행
여러 저장소에서 같은 훅을 쓰려면 복사 global config에 한 번 정의해 공유
임시 비활성화하려면 파일을 옮겨야 함 hook.<이름>.enabled = false
전부 순차 실행 hook.<이름>.parallel + hook.jobs로 병렬 실행
bash — config 훅 제어
# 특정 저장소에서만 전역 훅 끄기
$ git config hook.linter.enabled false

# 이벤트 전체를 끄기 (개별 설정보다 우선)
$ git config hook.pre-commit.enabled false

# 병렬 실행 (모든 훅이 parallel=true여야 효력이 있다)
$ git config hook.linter.parallel true
$ git config hook.no-leaks.parallel true
$ git config hook.pre-commit.jobs 4        # 또는 -1 = CPU 코어 수

# 등록된 훅 확인
$ git hook list pre-commit

주의할 점이 두 가지입니다. 첫째, 이 기능은 매우 최신입니다. 소스(v2.56 기준)에는 git hook list와 hook.<name>.command가 정식 문서화되어 있지만, 현재 널리 쓰이는 버전(예: 2.52)에는 git hook run만 있고 list와 config 훅은 없습니다. 팀 표준으로 삼기 전에 전원의 Git 버전을 확인해야 합니다.

둘째, 친숙한 이름(<friendly-name>)에 이벤트 이름을 쓰면 안 됩니다. 문서가 hook.pre-commit.event 같은 사용을 fatal error로 규정합니다 — hook.<event>.enabled와 모호해지기 때문입니다.

Part 4: 실행 환경 — 작업 디렉토리 · 환경 변수 · 병렬화

훅이 실행될 때 작업 디렉토리는 어디인가요?

githooks 문서가 정확히 규정합니다. 훅 종류에 따라 다릅니다.

githooks.adoc — 작업 디렉토리 규칙
기본: bare 저장소면 $GIT_DIR, 아니면 워킹 트리 루트

예외 — push 중에 발동하는 훅은 항상 $GIT_DIR에서 실행:
  pre-receive
  update
  post-receive
  post-update
  push-to-checkout

기본 규칙 덕분에 일반 훅에서는 상대 경로를 저장소 루트 기준으로 쓸 수 있습니다. 현재 디렉토리가 어디였든 상관없이 ./scripts/lint.sh가 동작합니다. 반대로 서버 훅에서 워킹 트리 경로를 가정하면 깨집니다 — 애초에 bare 저장소에는 워킹 트리가 없습니다(01편).

환경 변수 관련해서 주의할 점이 있다고 하셨는데요?

가장 악명 높은 함정입니다. 문서가 직접 경고합니다.

"Environment variables, such as GIT_DIR, GIT_WORK_TREE, etc., are exported so that Git commands run by the hook can correctly locate the repository."

편의를 위한 동작이지만, 훅 안에서 다른 저장소의 git 명령을 부르면 엉뚱한 곳을 가리킵니다. GIT_DIR이 이미 설정되어 있으니 git -C ../other조차 무시당합니다.

local_desc=$(git describe)
foreign_desc=$(unset $(git rev-parse --local-env-vars); git -C ../foreign-repo describe)

서브모듈이나 멀티 리포를 다루는 훅, 그리고 훅 안에서 임시 클론을 만들어 검증하는 CI성 훅에서는 이 처리가 필수입니다. GIT_INDEX_FILE이 남아 있으면 임시 저장소의 인덱스가 원본을 덮어쓰는 사고까지 납니다.

반대로 Git이 훅에게 일부러 넘겨 주는 변수도 있습니다.

push options가 실무에서 유용합니다. 개발자가 git push -o ci.skip -o reviewer=alice처럼 보내면 서버 훅이 읽어 동작을 바꿀 수 있습니다. GitLab의 push option 기능이 이 위에 구현되어 있습니다. 문서가 짚듯 옵션을 하나도 안 보냈으면 COUNT=0이고, 협상 자체가 안 됐으면 변수가 아예 없으므로 두 경우를 구분해 처리해야 합니다.

훅이 병렬로 실행될 수도 있나요?

config 기반 훅에 한해 가능합니다. hook.h의 구조체에 그 설계가 드러납니다.

hook.h
/**
 * Number of processes to parallelize across.
 *
 * If > 1, output will be buffered and de-interleaved (ungroup=0).
 * If == 1, output will be real-time (ungroup=1).
 * If == 0, the 'hook.jobs' config is used or, if the config is unset,
 * defaults to 1 (serial execution).
 */
unsigned int jobs;

여기서 중요한 트레이드오프가 보입니다. 병렬로 돌리면 출력이 섞이지 않도록 버퍼링되므로, 실시간 출력이 사라집니다. 오래 걸리는 린터의 진행 상황을 보고 싶다면 순차 실행이 낫습니다.

그리고 병렬화하면 안 되는 훅이 명시적으로 정해져 있습니다. 설정 문서가 이유까지 밝힙니다.

commit-msg
    → 커밋 메시지 파일을 받아 제자리에서 고칠 수 있다
      (동시에 쓰면 서로 덮어쓴다)

    → 워킹 트리·인덱스·저장소 상태에 접근한다
      (06편의 인덱스는 단일 파일이므로 동시 쓰기가 불가능)

이 목록이 곧 "훅이 공유 상태를 건드리는 지점"의 정리이기도 합니다. 11편에서 본 index.lock 경쟁이 훅 레벨에서 재현되는 것을 막는 장치입니다.

추가로 pre-push의 특수 처리가 있습니다. 문서에 따르면 pre-push는 평소 stdout과 stderr를 분리해 두지만, 병렬 실행(-j > 1)에서는 출력 순서를 올바르게 재조립하기 위해 stdout을 stderr로 합칩니다. 훅 출력을 파싱하는 스크립트를 짰다면 병렬 설정에서 깨질 수 있습니다.

정리하면 훅 하나가 실행되기까지의 전체 흐름은 어떻게 되나요?
1. 경로 결정
core.hooksPath 또는 $GIT_DIR/hooks + 훅 이름
→
2. 존재·권한 확인
access(path, X_OK). 실패하면 조용히 통과
→
3. 환경 구성
cwd 변경, GIT_* export, 훅별 추가 변수 설정
4. 실행
인자 전달 + (필요 시) stdin으로 데이터 스트리밍
→
5. 결과 수집
종료 코드 확인, stdout/stderr 전달(서버 훅은 클라이언트로)
→
6. 분기
중단 가능한 훅이고 종료 코드가 0이 아니면 작업 취소

이 여섯 단계가 29개 훅 전부에 동일하게 적용됩니다. 훅마다 다른 것은 "언제 호출되는가"와 "어떤 데이터를 어느 채널로 받는가"뿐입니다. 그 전수 목록이 다음 편(25편)이고, 이를 실제 정책으로 만드는 방법이 26편입니다.

📌 핵심 정리

  • 훅은 "정해진 이름 · 정해진 위치 · 실행 권한 있는 파일"이 전부다. find_hook()이 하는 일은 경로 조립과 access(path, X_OK) 한 번이며, 조건이 안 맞으면 조용히 통과한다. 진단은 git rev-parse --git-path hooks로 시작한다.
  • 입력은 인자(고정 개수) · stdin(가변 목록) · 환경 변수(부가 정보) 세 채널이다. stdin 줄은 대부분 <old> <new> <ref> 형태이고, "없음"은 all-zeroes OID로 표현되므로 범위 계산 전에 반드시 검사해야 한다.
  • 출력은 종료 코드(진행/중단) · stderr(사용자 메시지) · 파일 제자리 수정 세 가지다. post-*는 종료 코드가 무시되지만 post-checkout은 예외적으로 명령의 종료 코드가 되고, 서버 훅의 출력은 push한 사람 터미널로 전달된다.
  • 배치는 $GIT_DIR/hooks(클론 안 됨) · core.hooksPath(팀 배포 표준) · 템플릿(개인 표준화) · config 훅(최신) 네 가지다. 팀 배포에는 git update-index --chmod=+x로 실행 비트를 인덱스에 박아 두는 것이 필수다.
  • 작업 디렉토리는 워킹 트리 루트(서버 훅은 항상 $GIT_DIR)이고 GIT_* 변수가 export된다. 다른 저장소를 다룰 때는 unset $(git rev-parse --local-env-vars)가 필요하며, 메시지 파일·워킹 트리를 만지는 훅은 병렬화 대상에서 제외된다.
