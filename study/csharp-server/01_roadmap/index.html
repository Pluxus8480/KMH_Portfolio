무엇을, 어떤 순서로 공부해야 할까?

.NET 게임 백엔드 채용 공고를 시니어 서버 프로그래머 수준으로 정복하는 학습 로드맵

Part 1: 채용 공고를 학습 지도로 번역하기

공고에 기술이 너무 많습니다. 다 똑같이 중요한가요?

아닙니다. 채용 공고의 기술 스택은 "채용 후 매일 만질 것"과 "있으면 좋은 것"이 섞여 있습니다. 합격과 온보딩을 위해서는 우선순위를 매겨야 합니다.

이 공고의 키워드를 분석하면 회사의 정체성이 보입니다. .NET 10 + Orleans + Blazor는 "C#만으로 게임 백엔드 전체를 만든다"는 선언이고, Azure + Pulumi + Kubernetes + Helm + GitHub Actions는 "클라우드 네이티브 + 코드형 인프라(IaC)"를, ELK + Elastic APM은 "관측 가능성(Observability)을 진지하게 본다"는 신호입니다.

🎯 비유로 이해하기

이 스택은 한 채의 집과 같습니다.

C# / .NET 10 / async은 집의 골조와 벽돌입니다. 매일 만지고, 부실하면 집 전체가 무너집니다. → 최우선.

Orleans · PostgreSQL · Redis · TCP는 배관·전기·수도입니다. 보이지 않지만 실제로 일을 하는 핵심 설비입니다. → 핵심.

Azure · K8s · Helm · Pulumi · Actions · ELK는 집을 짓는 크레인·설계도·CCTV입니다. 직접 살지는 않지만 어떻게 동작하는지 알아야 합니다. → 운영 지식.

그래서 우선순위가 어떻게 되나요?
티어 항목 요구 깊이
🔴 T1 골조
(매일 만짐)		 C# / async·await / .NET 10 Host·DI / Syntactic Sugar(우대) / CS 기초 설명할 수 있고 디버깅까지 가능한 깊이
🟠 T2 설비
(핵심 로직)		 Orleans / PostgreSQL / Redis / TCP 네트워킹 직접 설계하고 트레이드오프를 말할 수 있는 깊이
🟡 T3 운영
(인프라·도구)		 Azure / Kubernetes·Helm / Pulumi / GitHub Actions / ELK·APM / Blazor 개념·역할을 알고 기존 설정을 읽고 고칠 수 있는 깊이

시니어 지원이라면 T1·T2는 "안다" 수준이 아니라 "왜 그렇게 동작하는지, 언제 무엇을 선택할지"를 말할 수 있어야 합니다. T3·T4는 "경험해봤고 막히면 찾아서 한다"는 자신감이면 충분합니다.

Part 3: 항목별 "어디까지" 공부할 것인가

각 기술을 정확히 어느 깊이까지 파야 면접에서 통하나요?

"어느 정도 지식"의 기준선을 항목별로 정리했습니다. 각 항목은 이 카테고리의 개별 학습 노트로 이어집니다.

🔴 T1 — 언어·런타임 (반드시 깊게) 필수 
[C# / async·await]  ☞ 03번 노트
  - async 메서드가 컴파일러에 의해 상태 머신(struct)으로 바뀌는 과정
  - await 시 스레드가 어떻게 ThreadPool로 반환되는가
  - sync-over-async(.Result/.Wait) 데드락이 왜 생기는가
  - ConfigureAwait(false), ValueTask, IAsyncEnumerable, CancellationToken
  - ThreadPool 고갈(starvation)과 백프레셔

[Syntactic Sugar / Low-Level]  ☞ 04번 노트  (★우대사항 직격)
  - using / lock / foreach / yield / 이벤트 / 람다 클로저가
    실제로 무슨 코드로 풀리는지 (디슈가링)
  - "IL까지는 아니어도 Low-Level 코드를 본 적 있는가"에 대한 정확한 답

[.NET 10 / Host / DI]  ☞ 02번 노트
  - Generic Host, 의존성 주입 수명(Singleton/Scoped/Transient)
  - Configuration, Options 패턴, Kestrel, 미들웨어 파이프라인
  - GC 세대·서버 GC, Span/Memory로 할당 줄이기 (기존 C# 카테고리와 연계)
🟠 T2 — 분산·데이터·네트워크 (설계까지) 핵심 
[Microsoft Orleans]  ☞ 05·06번 노트  (★이 회사의 정체성)
  - 가상 액터(Virtual Actor) 모델: Grain은 항상 살아있는 것처럼 보인다
  - Grain이 단일 스레드로 실행되어 "락 없이" 동시성을 다루는 원리
  - Silo 클러스터, Grain 배치(placement), 활성화/비활성화 생명주기
  - Persistence, Streams, Reentrancy, Timer/Reminder
  - 게임 도메인을 Grain으로 모델링 (PlayerGrain, RoomGrain, GuildGrain)

[PostgreSQL]  ☞ 08번 노트
  - 스키마/인덱스 설계, B-Tree, 복합 인덱스, 부분 인덱스
  - MVCC, 트랜잭션 격리 수준, 락, 데드락, VACUUM
  - 커넥션 풀(Npgsql), Dapper vs EF Core 선택 기준

[Redis]  ☞ 09번 노트
  - 자료구조별 용도(String/Hash/ZSet/List/Set), 캐시 무효화 전략
  - 분산 락, 원자성(Lua/MULTI), ZSet 실시간 랭킹, Pub/Sub
  - 영속성(RDB/AOF), 캐시 일관성 함정

[TCP 네트워킹]  ☞ 07번 노트
  - TCP vs UDP, Nagle/지연 ACK, 스트림 프레이밍(길이 접두사)
  - System.IO.Pipelines로 제로카피 파싱, 직렬화(MemoryPack 등)
🟡 T3 — 인프라·운영 (읽고 고칠 수 있게) 운영 
[Docker / Kubernetes / Helm]  ☞ 11번 노트
  - 이미지·레이어, Pod/Deployment/Service/Ingress, HPA 오토스케일
  - StatefulSet과 게임 서버, Helm 차트 구조와 values.yaml

[Pulumi (IaC)]  ☞ 12번 노트
  - C#으로 클라우드 리소스를 코드로 선언, 상태(state) 관리
  - Terraform과의 차이, 미리보기(preview)/적용(up)

[Azure]  ☞ 13번 노트
  - AKS, Container Apps, Storage, Service Bus, Key Vault 역할
  - 게임 백엔드 표준 아키텍처 그림 그리기

[GitHub Actions]  ☞ 14번 노트
  - 워크플로우·잡·스텝, 빌드→테스트→컨테이너 푸시→배포
  - 시크릿·환경·매트릭스, 반복작업 자동화

[Blazor]  ☞ 10번 노트
  - Server vs WebAssembly 차이, 컴포넌트·렌더링, 운영 백오피스 용도

[ELK Stack / Elastic APM]  ☞ 15번 노트
  - 구조화 로깅(Serilog), Elasticsearch/Kibana, 분산 추적, APM 지표
🟢 T4 — 협업·태도 (사례로 답하기) 문화 
[Git / Jira / Confluence / Slack]  ☞ 16번 노트
  - 브랜치 전략, 좋은 커밋·PR, 코드 리뷰 문화
  - 재현 가능한 버그 리포트 작성법 (공고가 강조하는 역량)
  - 반복작업을 스크립트/봇으로 자동화한 경험 만들기

[서브컬처 게임 이해]  (★우대사항)
  - 트릭컬 또는 서브컬처 게임을 실제로 플레이해보기
  - 가챠/수집/이벤트/시즌 운영이 백엔드에 주는 부하 특성 이해

함정: 인프라(T3)에 빠져 며칠을 쓰면서 정작 async 데드락이나 Orleans 동시성 모델을 설명 못 하면 역효과입니다. 면접 비중은 T1·T2 > T3·T4 입니다. 인프라는 "전체 그림 + 직접 한 번 배포"면 충분합니다.

Part 5: 모든 걸 하나로 묶는 미니 프로젝트

기술을 따로따로 배웠는데, 통합 감각은 어떻게 얻나요?

공고의 거의 모든 항목을 한 번에 꿰는 미니 프로젝트 하나를 만드세요. 면접 포트폴리오이자, 살아있는 학습 노트가 됩니다.

🎯 추천 프로젝트: "서브컬처 게임용 미니 백엔드"

예: 실시간 길드 레이드 랭킹 서버

플레이어가 TCP/HTTP로 접속하고, Orleans Grain이 플레이어·길드 상태를 들고, PostgreSQL에 영속화하고, Redis ZSet으로 실시간 랭킹을 매기고, Blazor 어드민으로 운영하고, ELK로 들여다보는 시스템.

미니 게임 백엔드 (한 프로젝트로 전 스택 커버)
접속 계층 · TCP/Pipelines + Kestrel (07·02)
도메인 · Orleans Grain: Player·Guild·Raid (05·06)
영속 · PostgreSQL + Redis 랭킹 (08·09)
운영 · Blazor 백오피스 (10)
배포 · Docker→K8s/Helm, Pulumi, Actions (11·12·13·14)
관측 · Serilog→ELK + APM (15)

이 한 프로젝트를 GitHub에 올리고, README에 아키텍처 다이어그램과 "왜 이 선택을 했는지"를 적으면 — T1~T4 전부를 증명하는 단 하나의 강력한 증거가 됩니다.

면접 직전에는 무엇을 점검해야 하나요?

아래 질문에 막힘없이 답할 수 있으면 준비된 것입니다.

  • async: "await를 만나면 스레드는 어디로 가나요?" / ".Result는 왜 위험한가요?"
  • Orleans: "Grain은 어떻게 락 없이 동시성을 보장하나요?" / "Silo가 죽으면 Grain은 어떻게 되나요?"
  • DB: "이 쿼리가 느립니다. 어디부터 보나요?" / "트랜잭션 격리 수준을 올리면 무엇을 잃나요?"
  • Redis: "캐시와 DB가 불일치하면 어떻게 막나요?" / "분산 락을 Redis로 어떻게 구현하나요?"
  • 운영: "배포 후 에러율이 튑니다. 어떻게 원인을 찾나요?" (→ APM·로그·롤백)
  • 태도: "반복적인 작업을 자동화한 경험은?" / "당신이 쓴 좋은 버그 리포트 한 건은?"

시니어 면접의 핵심은 암기가 아니라 트레이드오프 판단입니다. "정답"보다 "왜 그 상황에서 그 선택을 했는가"를 논리적으로 말하는 연습을 하세요.

📌 핵심 정리

  • 공고 스택은 T1 언어·런타임 → T2 분산·데이터 → T3 인프라 → T4 협업의 우선순위로 나눠서 정복한다
  • 이 회사의 정체성은 "C#으로 끝까지 + 클라우드 네이티브 + 관측 가능성"이며, Orleans 가상 액터가 가장 변별력 있는 주제다
  • 공부는 공식문서 → 따라 만들기 → 파괴 → 내 말로 정리의 4단계 루프로, 우대사항인 Low-Level은 SharpLab 디슈가링으로 채운다
  • 미니 게임 백엔드 프로젝트 하나로 전 스택을 한 번에 묶어 GitHub 포트폴리오로 만든다
  • 면접은 암기가 아니라 트레이드오프 판단이다 — "왜 그 선택을 했는가"를 말로 설명할 수 있어야 한다
