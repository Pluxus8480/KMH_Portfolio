락 없이 동시성을 다루는 법

Microsoft Orleans 가상 액터(Virtual Actor) 모델 입문

Part 1: 분산 서버의 동시성 고통

전통적인 락 기반 게임 서버는 왜 그렇게 만들기 어렵나요?

게임 서버의 본질은 공유 상태(shared mutable state)입니다. 한 명의 플레이어 인벤토리, 한 방의 매치 상태, 길드 자금 같은 데이터를 수십~수천 개의 스레드(혹은 요청)가 동시에 읽고 씁니다. 멀티코어 시대에 이 공유 상태를 안전하게 다루려면 결국 락(lock)이 필요합니다.

그리고 락은 세 가지 고질병을 데려옵니다.

문제 무엇이 일어나는가 증상
경쟁 조건
(Race Condition)		 락을 깜빡 잊은 한 줄 때문에 두 스레드가 같은 값을 동시에 갱신 재화 복제, 잃어버린 갱신(lost update). 재현이 어려움
데드락
(Deadlock)		 A가 락1→락2, B가 락2→락1 순서로 잡으며 서로를 영원히 대기 특정 스레드가 멈추고, 서버 일부가 응답 불능
락 경합
(Contention)		 인기 자원에 모든 스레드가 몰려 줄을 섬 코어를 늘려도 처리량이 안 늘어남(확장 실패)

진짜 문제는 "락을 잘 쓰는 법"이 아니라, 분산 환경에서는 락이 한 프로세스를 넘어가는 순간 더 이상 통하지 않는다는 점입니다. 서버를 2대로 늘리면 메모리 락(lock, Monitor)은 무력해지고, 분산 락(Redis, ZooKeeper)을 도입하는 순간 네트워크 지연·만료·고아 락이라는 새 지옥이 열립니다.

그래서 액터 모델(Actor Model)이 답이라는 건가요?

그렇습니다. 액터 모델의 발상은 단순합니다. "공유 상태를 없애면 락도 필요 없다."

각 상태 조각(플레이어 하나, 방 하나)을 액터(actor)라는 독립된 단위에 가둡니다. 액터의 내부 데이터는 오직 그 액터만 만질 수 있고, 외부에서는 메시지를 보내서 부탁할 수만 있습니다. 메시지는 한 번에 하나씩 처리됩니다. 동시에 두 스레드가 같은 액터의 상태를 건드리는 일 자체가 구조적으로 불가능해지므로, 경쟁 조건이 설계 단계에서 사라집니다.

🎯 비유로 이해하기

락 기반 서버는 공용 화이트보드 하나를 여러 사람이 동시에 고쳐 쓰는 사무실입니다. 누군가 지우개를 들 때마다 "잠깐, 내가 쓰는 중!"이라고 외쳐야 하고(락), 두 사람이 서로의 펜을 기다리면 일이 멈춥니다(데드락).

액터 모델은 사람마다 자기 노트를 한 권씩 가진 사무실입니다. 남의 노트를 직접 펼치는 건 금지이고, 필요하면 쪽지(메시지)를 보내 "이 줄 고쳐 주세요"라고 부탁합니다. 각자는 받은 쪽지를 한 장씩 차례로 처리하므로, 자기 노트에는 락이 아예 필요 없습니다.

Microsoft Orleans는 이 액터 모델을 게임/분산 백엔드에 맞게 한 단계 더 진화시킨 프레임워크입니다. 핵심 진화가 바로 다음 파트의 가상 액터(Virtual Actor)입니다.

Part 2: 가상 액터(Virtual Actor)란

전통적인 액터(Akka 등)와 Orleans의 "가상 액터"는 뭐가 다른가요?

전통적 액터 시스템에서는 개발자가 액터를 직접 생성(spawn)하고, 참조(reference)를 관리하고, 더 이상 안 쓰면 종료(stop)시켜야 합니다. 액터의 생명주기가 곧 개발자의 책임입니다. 액터가 죽었는데 누가 메시지를 보내면? 그 메시지는 사라집니다(dead letter). 분산 환경에서 이 생명주기 관리는 끔찍하게 복잡합니다.

Orleans의 가상 액터(Orleans에서는 그레인, Grain이라 부릅니다)는 정반대입니다. 그레인은 "항상 존재하는 것처럼" 보입니다. 개발자는 생성도, 소멸도 신경 쓰지 않습니다. 그저 ID로 호출할 뿐입니다.

"가상(virtual)"이라는 이름은 운영체제의 가상 메모리에서 따왔습니다. 가상 메모리에서 모든 페이지는 항상 존재하는 것처럼 보이지만, 실제로는 일부만 물리 RAM에 올라와 있고(활성), 나머지는 디스크에 있습니다(비활성). OS가 알아서 스왑 인/아웃 합니다.

그레인도 똑같습니다. 개념적으로는 클러스터 어딘가에 항상 존재하지만, 실제 메모리상의 인스턴스(활성화, activation)는 호출이 들어올 때만 생깁니다. 한동안 호출이 없으면 Orleans가 알아서 메모리에서 내립니다(비활성화, deactivation). 그다음 호출이 다시 오면 또 알아서 올립니다. 개발자 코드는 이 과정을 전혀 모릅니다.

활성화/비활성화가 자동이라는 게 실무에서 어떤 의미인가요?

두 가지 거대한 고통이 사라집니다.

1) 생명주기 관리 코드가 통째로 사라집니다. "이 플레이어 객체를 메모리에 올릴까? 내릴까? 캐시 만료는 언제?" 같은 결정을 Orleans가 대신합니다. 1억 명의 유저가 있어도 메모리에는 지금 활동 중인 그레인만 올라옵니다. 나머지는 그냥 ID와 영속 저장소(DB)로만 존재합니다.

2) "객체가 없어서 NullReference" 류의 문제가 사라집니다. 그레인은 호출하는 순간 없으면 자동 생성됩니다. 신규 가입한 플레이어든, 10년 전 휴면 유저든, 똑같이 GetGrain<IPlayerGrain>(id) 한 줄로 즉시 다룰 수 있습니다.

Part 3: Grain의 단일 스레드 턴 기반 실행 — "락 없는 동시성"의 핵심

그레인 안에서 락을 안 써도 된다는 게 정말인가요? 어떻게 안전합니까?

핵심은 단 한 문장입니다.

하나의 그레인 활성화는 한 번에 단 하나의 요청만 처리합니다. (single-threaded, turn-based execution)

같은 그레인에 100개의 요청이 동시에 들어와도, Orleans 런타임은 그것들을 큐에 줄 세우고 하나씩 실행합니다. 한 요청이 끝나기 전까지 다음 요청은 시작되지 않습니다. 즉 그레인 내부 코드는 사실상 싱글 스레드로 도는 것과 같습니다.

그래서 그레인의 내부 상태(필드)에는 락이 필요 없습니다. 두 요청이 동시에 같은 필드를 건드릴 수 없으니, 경쟁 조건이 원천적으로 발생하지 않습니다. 이것이 바로 이 페이지 제목 "락 없이 동시성을 다루는 법"의 정체입니다.

C#
// 이 그레인은 한 번에 하나의 요청만 처리하므로
// _balance 에 lock 이 전혀 필요 없습니다.
public class WalletGrain : Grain, IWalletGrain
{
    private long _balance;          // 공유 상태이지만 락이 불필요

    public Task DepositAsync(long amount)
    {
        // 동시에 들어온 다른 Deposit/Withdraw 호출은
        // 이 메서드가 끝날 때까지 큐에서 대기합니다.
        _balance += amount;          // 안전한 read-modify-write
        return Task.CompletedTask;
    }

    public Task<bool> WithdrawAsync(long amount)
    {
        if (_balance < amount)
            return Task.FromResult(false);   // 잔액 부족
        _balance -= amount;          // 경쟁 조건 없음
        return Task.FromResult(true);
    }
}
"턴 기반"이라는 게 정확히 무슨 의미인가요? await가 끼면 어떻게 되죠?

여기가 시니어 면접에서 갈리는 지점입니다. Orleans의 실행 단위는 턴(turn)입니다. 하나의 턴은 다음 await를 만나기 전까지의 동기 코드 조각입니다.

메서드가 await로 멈추면, 그 그레인은 그 사이에 다른 요청의 턴을 실행할 수 있습니다. 즉 그레인은 "한 메서드를 처음부터 끝까지 독점"하는 게 아니라, "한 번에 한 턴"을 보장합니다.

🎯 비유로 이해하기

그레인은 한 명의 은행 창구 직원입니다. 한 번에 한 손님만 응대합니다(싱글 스레드 보장).

그런데 손님 A가 "잠깐 서류를 떼 올게요(await DB)"라며 자리를 비우면, 직원은 그동안 손님 B를 응대할 수 있습니다(다른 턴 인터리빙). A가 서류를 들고 돌아오면 다시 A를 마저 처리합니다. 직원은 절대 두 명을 동시에 응대하지 않지만, 누군가 자리를 비운 빈 시간은 알뜰히 씁니다.

함정: await 전후로 그레인 상태가 바뀌어 있을 수 있습니다(그 사이 다른 턴이 끼어들었을 수 있으니). 그래서 "await 직전에 읽은 값이 await 직후에도 같다"고 가정하면 안 됩니다. 다만 턴 자체는 깨지지 않으므로, 동기 코드 한 덩어리 안에서는 항상 일관성이 보장됩니다. 기본값(non-reentrant) 그레인이면 인터리빙은 서로 다른 요청 사이에서만 일어납니다.

Part 4: Silo와 클러스터

그레인은 실제로 어디에서 도나요? Silo가 뭔가요?

Silo(사일로)는 그레인을 호스팅하는 서버 프로세스입니다. 게임 서버 한 대(혹은 하나의 컨테이너/파드)가 하나의 Silo라고 보면 됩니다. 여러 Silo가 모이면 클러스터(cluster)가 되고, 그레인들은 이 클러스터 전체에 흩어져 활성화됩니다.

Orleans 클러스터
Silo A
PlayerGrain(1), RoomGrain(42)
Silo B
PlayerGrain(2), PlayerGrain(7)
Silo C
RoomGrain(99), GuildGrain(3)

클러스터를 굴리려면 네 가지 메커니즘이 맞물려 돌아갑니다.

메커니즘 역할
멤버십
(Clustering)		 지금 살아있는 Silo가 누구인지 공유 저장소(예: ADO.NET/PostgreSQL, Azure Table, Redis)에 기록. 죽은 Silo 감지·축출
그레인 디렉터리
(Directory)		 "PlayerGrain(7)은 지금 어느 Silo에 활성화돼 있나"를 추적하는 분산 레지스트리
배치
(Placement)		 새 그레인을 활성화할 때 어느 Silo에 둘지 결정(랜덤/부하 기반/지정)
라우팅 호출을 디렉터리에서 찾은 올바른 Silo로 전달(클라이언트는 위치를 몰라도 됨)
한 그레인이 두 Silo에서 동시에 활성화되면 락 없는 보장이 깨지지 않나요?

정확한 질문입니다. 그래서 Orleans의 가장 중요한 불변식(invariant)이 이것입니다.

같은 ID의 그레인은 클러스터 전체에서 단 한 곳에만 활성화됩니다 (single activation).

디렉터리가 이 단일 활성화를 보증합니다. RoomGrain(42)를 어느 Silo에서 호출하든, 디렉터리가 "42번 방은 Silo A에 있다"고 알려주고 호출은 모두 Silo A의 그 인스턴스로 모입니다. 덕분에 Part 3의 "한 번에 한 요청" 보장이 분산 환경에서도 유지됩니다. 단일 활성화 × 단일 스레드 = 클러스터 전체에서 락 없는 직렬화.

Silo가 죽으면? 멤버십이 죽음을 감지하고, 그 Silo에 있던 그레인들은 다음 호출 시 다른 Silo에서 자동으로 다시 활성화됩니다. 활성화는 일시적이고, 진짜 정체성은 ID + 영속 상태에 있기 때문에 가능한 일입니다.

Part 5: 첫 Grain 만들기

실제 코드는 어떻게 생겼나요? 인터페이스부터 보여주세요.

그레인은 항상 인터페이스 + 구현 한 쌍으로 만듭니다. 인터페이스는 키 타입에 따라 IGrainWithIntegerKey, IGrainWithStringKey, IGrainWithGuidKey 중 하나를 상속합니다. 모든 그레인 메서드는 비동기여야 하므로 반환형은 Task / Task<T>(또는 ValueTask)입니다.

현행 Orleans(Microsoft.Orleans, .NET)에서는 소스 제너레이터가 직렬화 코드를 생성하므로, 전송되는 타입에는 [GenerateSerializer]와 [Id(n)]를, 버전 안정성을 위해 인터페이스/메서드에는 [Alias]를 붙이는 것이 표준입니다.

C# — IPlayerGrain.cs (인터페이스)
using Orleans;

// 정수 키 기반 그레인. 키 = 플레이어 ID
[Alias("IPlayerGrain")]
public interface IPlayerGrain : IGrainWithIntegerKey
{
    [Alias("AddExp")]
    Task<int> AddExpAsync(int amount);   // 경험치 추가 후 누적 경험치 반환

    [Alias("GetProfile")]
    Task<PlayerProfile> GetProfileAsync();
}

// 그레인 사이를 오가는 DTO는 직렬화 대상이므로 어트리뷰트 필수
[GenerateSerializer]
public sealed class PlayerProfile
{
    [Id(0)] public int Level { get; set; }
    [Id(1)] public int Exp { get; set; }
    [Id(2)] public string Nickname { get; set; } = "";
}

구현 클래스는 Grain을 상속하고 인터페이스를 구현합니다. 내부 필드가 곧 그 플레이어의 상태입니다.

C# — PlayerGrain.cs (구현)
public class PlayerGrain : Grain, IPlayerGrain
{
    private int _level = 1;
    private int _exp;
    private string _nickname = "";

    // 이 그레인이 메모리에 처음 올라올 때(활성화) 호출됩니다.
    // 보통 여기서 DB/영속 상태를 불러옵니다.
    public override Task OnActivateAsync(CancellationToken ct)
    {
        long playerId = this.GetPrimaryKeyLong();   // 키 = 플레이어 ID
        _nickname = $"Player#{playerId}";
        return base.OnActivateAsync(ct);
    }

    public Task<int> AddExpAsync(int amount)
    {
        // 락 없음: 한 번에 한 요청만 들어오므로 안전
        _exp += amount;
        while (_exp >= 100)         // 100마다 레벨업
        {
            _exp -= 100;
            _level++;
        }
        return Task.FromResult(_exp);
    }

    public Task<PlayerProfile> GetProfileAsync() =>
        Task.FromResult(new PlayerProfile
        {
            Level = _level, Exp = _exp, Nickname = _nickname
        });
}
호출하는 쪽은요? 서브컬처 게임의 방(Room) 입장 같은 예시로 보여주세요.

같은 클러스터 안의 다른 그레인에서는 GrainFactory.GetGrain으로, 클러스터 바깥(예: API 게이트웨이, Blazor 백엔드)에서는 IClusterClient로 호출합니다. 둘 다 진짜 객체를 받는 게 아니라, 그레인의 위치를 추상화한 프록시(reference)를 받습니다. 호출 한 줄이 곧 그 그레인이 어느 Silo에 있든 라우팅됩니다.

C# — RoomGrain에서 PlayerGrain 호출
[Alias("IRoomGrain")]
public interface IRoomGrain : IGrainWithIntegerKey
{
    [Alias("Join")]   Task<bool> JoinAsync(long playerId);
    [Alias("Members")] Task<IReadOnlyList<long>> GetMembersAsync();
}

public class RoomGrain : Grain, IRoomGrain
{
    private const int Capacity = 4;            // 4인 협동 방
    private readonly HashSet<long> _members = new();

    public async Task<bool> JoinAsync(long playerId)
    {
        if (_members.Count >= Capacity) return false;   // 정원 초과

        // 다른 그레인을 ID로 호출 — 위치는 몰라도 됩니다.
        var player = GrainFactory.GetGrain<IPlayerGrain>(playerId);
        var profile = await player.GetProfileAsync();   // 턴 경계(await)

        _members.Add(playerId);
        return true;
    }

    public Task<IReadOnlyList<long>> GetMembersAsync() =>
        Task.FromResult((IReadOnlyList<long>)_members.ToList());
}

Part 6: Orleans vs 전통적 락 기반 서버

전통적인 락 기반 서버와 직접 비교하면 어떻게 다른가요?
구분 전통적 락 기반 서버 Orleans (가상 액터)
동시성 모델 공유 상태 + 락/뮤텍스로 보호 그레인별 단일 스레드 직렬화, 락 불필요
확장(Scale-out) 분산 락·세션 어피니티 필요, 직접 설계 Silo 추가 → 그레인이 자동 분산·재배치
생명주기 객체 생성/소멸·캐시 만료를 직접 관리 활성화/비활성화 자동(가상 액터)
디버깅 데드락·경쟁 조건, 재현 난해 경쟁 조건 구조적 소멸. 단, 분산 추적 필요
적합 사례 단일 노드 고처리량, 정밀 제어가 필요한 코어 루프 수많은 독립 엔티티(플레이어·방·길드) 상태 관리
그럼 Orleans는 만능인가요? 한계나 주의점은요?

아닙니다. "락이 사라진다"는 말은 "동시성을 공짜로 얻는다"는 뜻이 아니라 "동시성의 단위를 그레인으로 바꿨다"는 뜻입니다. 그래서 새로운 규칙과 함정이 생깁니다.

턴 안에서 절대 블로킹하지 마세요. 그레인은 싱글 스레드이므로, 한 턴에서 Thread.Sleep, .Result, .Wait() 같은 동기 블로킹을 하면 그 그레인 전체가 그동안 마비됩니다(그 큐에 줄 선 모든 요청이 멈춤). 반드시 await로 비동기 대기하세요.

핫스팟 그레인을 조심하세요. 모든 요청이 한 그레인(예: 전역 랭킹 그레인 1개)으로 몰리면, 그 그레인의 단일 스레드가 병목이 됩니다. 상태를 여러 그레인으로 쪼개(샤딩) 부하를 분산해야 합니다.

상태 영속화는 별개 주제입니다. 그레인 필드는 활성화 중에만 메모리에 삽니다. 비활성화·장애에도 데이터를 지키려면 [PersistentState] + Grain Storage(또는 직접 DB 저장)로 영속화해야 합니다. 이건 다음 학습 주제(그레인 영속성)에서 다룹니다.

정리하면, Orleans는 "수백만 개의 독립적이고 작은 상태 단위"를 다루는 데 압도적으로 강합니다. 서브컬처 게임의 플레이어·방·길드·우편함처럼 "ID로 식별되는 무수한 엔티티"가 정확히 그 모양입니다. 반면 한 덩어리의 거대한 공유 상태를 초저지연으로 갈아 넣는 코어 루프는 여전히 전통적 기법이 어울릴 수 있습니다. 도구의 결을 아는 것이 시니어의 판단입니다.

📌 핵심 정리

  • 락 없는 동시성의 원리: 공유 상태를 그레인에 가두고, "단일 활성화 × 단일 스레드 턴 기반 실행"으로 같은 그레인의 요청을 직렬화하므로 내부 상태에 락이 필요 없습니다.
  • 가상 액터(Grain): 항상 존재하는 것처럼 보이며, 활성화/비활성화는 Orleans가 자동 관리합니다. 개발자는 생성·소멸이 아니라 ID로 호출만 합니다.
  • Silo와 클러스터: Silo가 그레인을 호스팅하고, 멤버십·디렉터리·배치가 맞물려 클러스터 전체에서 그레인 단일 활성화를 보장합니다. Silo가 죽으면 다른 Silo에서 자동 재활성화됩니다.
  • 코드 패턴: IGrainWithIntegerKey 인터페이스 + Grain 상속 구현, [Alias]/[GenerateSerializer]/[Id] 어트리뷰트, GetGrain<T>(id) 프록시 호출이 기본 형태입니다.
  • 한계와 주의: 턴 안 블로킹 금지(반드시 await), 핫스팟 그레인은 샤딩으로 분산, 상태 영속화는 별도 처리. 무수한 독립 엔티티 관리에 강하고 거대 단일 코어 루프에는 부적합할 수 있습니다.
