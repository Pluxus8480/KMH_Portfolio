GitHub Actions로 빌드·테스트·배포 자동화 (반복작업 박멸)

Part 1: CI/CD가 왜 필요한가

"로컬에서 빌드해서 서버에 올리면 되지 않나요? 굳이 CI/CD를 왜 도입합니까?"

게임 서버를 수동으로 배포하던 시절의 하루를 떠올려 보겠습니다. 코드를 머지한 뒤 누군가의 PC에서 dotnet publish를 돌리고, 결과물을 압축해 서버에 SCP로 올리고, 기존 프로세스를 죽이고, 새 바이너리를 띄우고, 로그를 눈으로 확인합니다. 이 과정이 매번 사람의 손을 거치면 다음 문제가 반복됩니다.

"제 PC에서는 됐는데요"는 빌드 환경이 사람마다 다르기 때문에 발생합니다. .NET SDK 버전, NuGet 캐시 상태, 환경 변수가 제각각이면 재현 불가능한 버그가 운영에서 터집니다.

CI(Continuous Integration)는 모든 변경을 깨끗한 환경에서 자동으로 빌드·테스트해 통합 시점의 문제를 즉시 잡아냅니다. CD(Continuous Delivery/Deployment)는 검증된 결과물을 사람의 실수 없이 동일한 절차로 배포합니다.

🎯 비유로 이해하기

수동 배포는 매번 손으로 라면을 끓이는 것과 같습니다. 물의 양, 불 세기, 면을 넣는 타이밍이 끓일 때마다 미세하게 달라져 맛이 들쭉날쭉합니다.

CI/CD는 자판기 라면입니다. 버튼(푸시) 한 번에 정해진 물 양, 정해진 시간으로 항상 같은 결과가 나옵니다. 맛이 이상하면 자판기(파이프라인)를 고치면 되지, 사람의 손맛을 탓할 필요가 없습니다.

반복적이고 지루한 작업은 사람이 가장 실수하기 쉬운 작업입니다. "반복 작업에 불편함을 느끼고 개선하려는 의지"란, 단순히 부지런함이 아니라 실수가 끼어들 틈을 구조적으로 없애는 엔지니어링 태도입니다. 배포를 자동화하면 사람은 도구를 누르는 일이 아니라 도구를 설계하는 일에 시간을 씁니다.

특히 게임 서버는 패치 주기가 빠르고, 핫픽스가 잦으며, 새벽 점검이 일상입니다. 빠른 피드백 루프(푸시 → 수 분 내 빌드·테스트 결과)가 없으면 장애 대응 속도가 곧 매출 손실로 직결됩니다.

구분수동 빌드·배포GitHub Actions CI/CD

Part 2: 워크플로우 구조 — 이벤트·잡·스텝·러너

"GitHub Actions의 YAML을 보면 on, jobs, steps가 나오는데 각각 어떤 단위인가요?"

GitHub Actions는 .github/workflows/ 디렉터리의 YAML 파일을 워크플로우로 인식합니다. 핵심 구성 요소는 다음과 같습니다.

요소역할비유
on (이벤트)워크플로우를 언제 실행할지 결정(push, pull_request, tag, schedule, workflow_dispatch)방아쇠
jobs (잡)독립적으로 실행되는 작업 묶음. 기본 병렬, needs로 의존 순서 지정작업조
runs-on (러너)잡이 실행될 가상머신(ubuntu-latest 등) 또는 self-hosted작업장
steps (스텝)잡 안에서 순차 실행되는 명령. uses(액션 재사용) 또는 run(셸 명령)작업 절차

잡은 기본적으로 서로 다른 VM에서 격리 실행됩니다. 따라서 한 잡에서 빌드한 결과물을 다른 잡으로 넘기려면 actions/upload-artifact로 올리고 download-artifact로 받아야 합니다. 같은 잡 안의 스텝끼리는 같은 파일시스템을 공유합니다.

uses로 불러오는 액션(action)은 재사용 가능한 빌딩 블록입니다. actions/checkout@v4처럼 마켓플레이스에 공개된 것을 가져다 쓰며, 공급망 보안을 위해 신뢰할 수 있는 액션은 커밋 SHA로 핀 고정하는 것이 권장됩니다.

YAML
# .github/workflows/structure-demo.yml
name: 구조 데모               # 워크플로우 이름(Actions 탭에 표시)

on:                          # 이벤트 트리거 정의
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:         # 수동 실행 버튼 활성화

jobs:
  build:                     # 잡 식별자
    runs-on: ubuntu-latest   # 러너 환경
    steps:
      - name: 소스 체크아웃
        uses: actions/checkout@v4      # 액션 재사용
      - name: 셸 명령 실행
        run: echo "커밋 ${{ github.sha }} 빌드 시작"

  deploy:
    needs: build             # build 잡이 성공해야 실행(의존 관계)
    runs-on: ubuntu-latest
    steps:
      - run: echo "배포 단계"

${{ ... }}는 표현식 문맥입니다. github, secrets, env, matrix 등의 컨텍스트에 접근할 때 사용합니다. 예를 들어 ${{ github.ref_name }}은 현재 브랜치/태그 이름입니다.

Part 3: .NET CI — 빌드·테스트·캐싱·매트릭스

"우리 게임 서버는 .NET입니다. restore/build/test를 어떻게 구성하고, NuGet 복원이 매번 느린데 캐싱은 어떻게 합니까?"

.NET CI의 표준 흐름은 체크아웃 → SDK 설치 → 의존성 복원 → 빌드 → 테스트입니다. 다음은 게임 서버 솔루션을 검증하는 실전 CI 워크플로우입니다.

YAML
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: 소스 체크아웃
        uses: actions/checkout@v4

      - name: .NET SDK 설치
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'

      - name: NuGet 패키지 캐싱
        uses: actions/cache@v4
        with:
          # 복원된 패키지가 저장되는 전역 경로
          path: ~/.nuget/packages
          # lock 파일이 바뀌지 않으면 캐시 재사용
          key: nuget-${{ runner.os }}-${{ hashFiles('**/packages.lock.json') }}
          restore-keys: |
            nuget-${{ runner.os }}-

      - name: 의존성 복원
        run: dotnet restore GameServer.sln

      - name: 빌드 (복원 생략으로 속도 향상)
        run: dotnet build GameServer.sln --configuration Release --no-restore

      - name: 단위 테스트 + 커버리지
        run: >
          dotnet test GameServer.sln
          --configuration Release
          --no-build
          --logger "trx;LogFileName=test-results.trx"
          --collect:"XPlat Code Coverage"

      - name: 테스트 결과 아티팩트 업로드
        if: always()          # 실패해도 결과는 남긴다
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: '**/test-results.trx'

캐싱의 핵심은 key입니다. hashFiles('**/packages.lock.json')로 의존성 잠금 파일의 해시를 키에 넣으면, 의존성이 바뀌지 않은 한 캐시를 그대로 복원해 restore 시간을 수십 초에서 수 초로 줄입니다. 정확한 캐싱을 위해 프로젝트에 RestorePackagesWithLockFile을 켜 packages.lock.json을 커밋해 두는 것을 권장합니다.

여러 OS·런타임 조합을 한 번에 검증하려면 매트릭스 빌드를 씁니다. 게임 서버를 리눅스 컨테이너로 배포하더라도, 개발자들이 Windows에서 작업한다면 양쪽 모두 깨지지 않는지 확인하는 것이 안전합니다.

YAML
  matrix-build:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false        # 한 조합이 실패해도 나머지는 계속
      matrix:
        os: [ ubuntu-latest, windows-latest ]
        dotnet: [ '8.0.x' ]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ matrix.dotnet }}
      - run: dotnet test --configuration Release
        # ${{ matrix.os }} 조합마다 별도 잡으로 병렬 실행됨

README에 상태 배지를 붙이면 main 브랜치의 건강 상태가 한눈에 보입니다. 마크다운에 ![CI](https://github.com/<org>/<repo>/actions/workflows/ci.yml/badge.svg) 형태로 추가하면, CI가 깨진 채 방치되는 상황을 시각적으로 압박할 수 있습니다.

PR에서 테스트가 실패하면 머지를 막아야 합니다. 저장소의 Branch protection rule에서 test 잡을 "Required status check"로 지정하면, 녹색 체크가 뜨기 전에는 main에 머지할 수 없게 강제됩니다.

Part 4: CD — 컨테이너 이미지 빌드·푸시·K8s 배포

"테스트가 통과하면 그다음은요? Docker 이미지를 만들어 쿠버네티스에 올리는 흐름을 보고 싶습니다."

CI를 통과한 커밋을 컨테이너 이미지로 굳혀 레지스트리(GHCR, ACR 등)에 푸시하고, 그 이미지 태그를 쿠버네티스에 반영하는 것이 CD의 핵심입니다. 전체 파이프라인은 다음과 같이 흐릅니다.

→

→
test
단위·통합 테스트
→
image
docker build·push
→
deploy

이미지 태그 전략이 중요합니다. latest만 쓰면 어떤 커밋이 운영에 떠 있는지 추적할 수 없고 롤백이 불가능합니다.

태그 전략예시용도
커밋 SHA:sha-3f9a1c2불변·추적용. 모든 이미지에 부여
시맨틱 버전:1.4.2릴리스 태그 푸시 시
이동 태그:latest, :staging"현재 운영본"을 가리키는 포인터

운영 배포에 :latest만 사용하면 안 됩니다. 동일한 :latest가 어제와 오늘 다른 바이너리를 가리키므로, 장애 발생 시 "정확히 무엇을 되돌려야 하는가"를 알 수 없습니다. 반드시 :sha-... 같은 불변 태그를 함께 푸시하고, 배포 매니페스트에는 불변 태그를 박아 넣습니다.

다음은 GHCR에 이미지를 푸시하고 쿠버네티스에 롤아웃하는 CD 워크플로우입니다.

전체 CD 워크플로우 — 이미지 빌드·푸시 + K8s 배포 YAML 
# .github/workflows/cd.yml
name: CD

on:
  push:
    branches: [ main ]       # main 머지 시 staging 자동 배포
    tags: [ 'v*.*.*' ]       # 버전 태그 푸시 시 release

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}   # org/game-server

jobs:
  image:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write        # GHCR 푸시 권한
    outputs:
      image_tag: ${{ steps.meta.outputs.version }}
    steps:
      - uses: actions/checkout@v4

      - name: GHCR 로그인
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}   # 자동 발급 토큰

      - name: 이미지 메타데이터(태그) 산출
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=sha,prefix=sha-          # 불변 태그(필수)
            type=ref,event=branch         # 브랜치명 태그
            type=semver,pattern={{version}}   # v1.4.2 -> 1.4.2

      - name: Buildx 설정
        uses: docker/setup-buildx-action@v3

      - name: 이미지 빌드 및 푸시
        uses: docker/build-push-action@v6
        with:
          context: .
          file: ./src/GameServer/Dockerfile
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha            # Actions 캐시로 레이어 재사용
          cache-to: type=gha,mode=max

  deploy:
    needs: image
    runs-on: ubuntu-latest
    environment: production              # 보호 규칙(승인) 연결
    steps:
      - uses: actions/checkout@v4

      - name: kubeconfig 구성
        run: |
          mkdir -p $HOME/.kube
          echo "${{ secrets.KUBE_CONFIG }}" | base64 -d > $HOME/.kube/config

      - name: Helm 배포 (이미지 태그 주입)
        run: |
          helm upgrade --install game-server ./deploy/helm/game-server \
            --namespace game --create-namespace \
            --set image.repository=${{ env.REGISTRY }}/${{ env.IMAGE_NAME }} \
            --set image.tag=sha-${{ github.sha }} \
            --wait --timeout 5m

      - name: 롤아웃 상태 확인
        run: kubectl rollout status deployment/game-server -n game --timeout=180s

--wait와 kubectl rollout status가 핵심입니다. 새 파드가 readiness probe를 통과해 정상 기동했는지 확인될 때까지 워크플로우가 기다립니다. 기동에 실패하면 잡이 빨갛게 떨어져 즉시 알 수 있고, 쿠버네티스의 롤링 업데이트 특성상 구버전 파드가 살아 있어 무중단이 유지됩니다.

Helm --set image.tag=sha-...로 불변 태그를 주입했기 때문에, 롤백은 이전 SHA 태그로 같은 명령을 한 번 더 돌리면 끝입니다. 또는 helm rollback game-server로 직전 릴리스로 되돌릴 수 있습니다.

Part 5: 시크릿·환경·승인 — 그리고 키 없는 OIDC 인증

"DB 비밀번호나 클라우드 키를 워크플로우에 어떻게 안전하게 넣습니까? 운영 배포는 자동으로 나가면 위험할 것 같은데요."

민감한 값은 코드에 절대 넣지 않고 Secrets로 관리합니다. 저장소·조직·환경(Environment) 단위로 등록할 수 있으며, 로그에 출력되면 자동으로 마스킹됩니다.

시크릿을 echo로 찍거나 빌드 산출물에 포함시키면 안 됩니다. 또한 pull_request 이벤트는 포크에서 온 PR에 대해 시크릿을 노출하지 않습니다. 외부 기여자의 코드가 시크릿을 탈취하지 못하도록 하는 보안 장치이므로, 배포처럼 시크릿이 필요한 잡은 신뢰된 브랜치 푸시에서만 실행해야 합니다.

Environment(환경)은 staging/production을 분리하고 보호 규칙을 거는 단위입니다. production 환경에 "Required reviewers"를 설정하면, 배포 잡이 그 환경에 진입할 때 지정된 사람의 수동 승인을 기다렸다가 진행합니다. 새벽에 main에 머지돼도, 사람이 승인 버튼을 누르기 전까지 운영 반영은 멈춰 있습니다.

한 단계 더 나아가면 OIDC(OpenID Connect)로 클라우드 키 자체를 없앨 수 있습니다. AWS·Azure에 장기 액세스 키를 시크릿으로 저장하는 대신, GitHub가 발급한 단기 OIDC 토큰을 클라우드가 신뢰하도록 설정합니다. 키가 저장소에 존재하지 않으므로 유출 위험이 원천 차단되고, 만료된 단기 토큰이라 회수 부담도 없습니다.

YAML
  deploy-aws:
    runs-on: ubuntu-latest
    permissions:
      id-token: write        # OIDC 토큰 발급에 필수
      contents: read
    steps:
      - uses: actions/checkout@v4

      - name: AWS 자격 증명 (키 없이 OIDC로)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          # 장기 키 대신 IAM 역할을 신뢰 관계로 가정(assume)
          role-to-assume: arn:aws:iam::123456789012:role/github-actions-deploy
          aws-region: ap-northeast-2

      - name: EKS 배포
        run: |
          aws eks update-kubeconfig --name game-cluster
          kubectl set image deployment/game-server \
            game-server=$ECR/game-server:sha-${{ github.sha }} -n game

Part 6: 한 걸음 더 — 반복작업을 계속 깎아내기

"빌드·배포는 자동화했습니다. 그 외에 사람이 손으로 하던 자잘한 반복작업도 자동화할 수 있나요?"

바로 이 지점이 "반복 작업에 불편함을 느끼고 개선하려는" 태도가 빛나는 곳입니다. 자동화는 빌드·배포에서 끝나지 않습니다. 리뷰에서 매번 지적하던 것, 매주 손으로 하던 것을 하나씩 봇에게 넘깁니다.

반복작업자동화 방법없애는 수고
코드 포맷·스타일 지적dotnet format --verify-no-changes CI 검사리뷰에서 포맷 코멘트 소멸
정적 분석·경고 누적-warnaserror + Roslyn 분석기"나중에 고치자"가 쌓이는 것 방지
의존성 보안 패치Dependabot 자동 PR취약 패키지 수동 추적
릴리스 노트 작성release-drafter / 자동 태그 릴리스변경 이력 손으로 정리
PR 분류·라벨링labeler 액션(경로 기반)매 PR 라벨 수동 부착

포맷 검사는 단 몇 줄로 리뷰의 소모적인 논쟁을 끝냅니다. 사람이 "여기 들여쓰기가요…"라고 적을 필요 없이, CI가 객관적으로 막아 줍니다.

YAML
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'
      # 포맷이 어긋나면 비정상 종료 -> 잡 실패
      - run: dotnet format GameServer.sln --verify-no-changes --severity warn

Dependabot은 코드가 아니라 .github/dependabot.yml 설정 파일로 동작합니다. NuGet 의존성에 새 버전·보안 패치가 나오면 자동으로 PR을 열어 주고, CI가 그 PR을 검증하므로 "올려도 안전한지"까지 자동으로 확인됩니다.

YAML
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "nuget"
    directory: "/"
    schedule:
      interval: "weekly"      # 매주 의존성 점검·PR 생성
    open-pull-requests-limit: 5
  - package-ecosystem: "docker"
    directory: "/src/GameServer"
    schedule:
      interval: "weekly"      # 베이스 이미지 보안 업데이트도 추적
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "monthly"     # 액션 버전도 최신·안전하게 유지
🎯 비유로 이해하기

자동화는 한 번 깎고 끝나는 일이 아니라, 톱니바퀴에 기름칠을 계속하는 일과 같습니다. 손이 자주 가는 곳을 발견할 때마다 그곳에 작은 자동화 톱니를 하나씩 끼워 넣습니다.

시간이 지나면 사람이 직접 돌리던 톱니는 거의 사라지고, 사람은 새로운 톱니를 설계하는 데 집중하게 됩니다.

중요한 것은 도구의 개수가 아니라 "이 반복은 사람이 안 해도 된다"는 관점입니다. 면접에서 이 주제를 다룰 때는, 특정 액션의 이름을 나열하기보다 "어떤 반복을 발견했고, 그것을 어떻게 파이프라인에 흡수시켜 팀 전체의 실수와 시간 낭비를 줄였는가"를 이야기하는 편이 훨씬 강합니다.

📌 핵심 정리

  • CI/CD의 본질은 재현성과 피드백 속도입니다. 깨끗한 러너에서 항상 같은 절차로 빌드·테스트·배포해 "제 PC에서는 됐는데요"와 수동 실수를 구조적으로 제거합니다.
  • 워크플로우는 이벤트(on) → 잡(jobs) → 스텝(steps) → 러너(runs-on) 구조이며, 잡은 격리·병렬 실행되고 needs로 순서를, 아티팩트로 결과를 주고받습니다.
  • .NET CI는 checkout → setup-dotnet → restore → build → test가 표준이며, actions/cache의 lock-file 해시 키로 NuGet 복원을 가속하고 매트릭스로 다중 환경을 검증합니다.
  • CD는 이미지를 불변 SHA 태그로 레지스트리에 푸시하고, Helm/kubectl로 K8s에 롤아웃하며 rollout status로 검증합니다. latest만 쓰면 추적·롤백이 불가능합니다.
  • 안전과 한 걸음 더: 시크릿·Environment 보호 규칙으로 운영 배포에 수동 승인을 걸고, OIDC로 키 없는 인증을 구현하며, 포맷 검사·Dependabot·릴리스 봇으로 남은 반복작업까지 계속 박멸합니다.
