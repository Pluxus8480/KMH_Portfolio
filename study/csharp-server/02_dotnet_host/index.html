Part 1: .NET 10 런타임 — 게임 백엔드에 왜 적합한가

C# 코드가 실행되기까지 무슨 일이 일어나나요? CLR, JIT, AOT가 다 뭔가요?

C#은 컴파일하면 기계어가 아니라 IL(Intermediate Language)이라는 중간 코드가 됩니다. 이 IL을 실제 CPU 명령어로 바꾸고, 메모리·스레드·예외를 관리하는 가상 머신이 CLR(Common Language Runtime)입니다.

C# 소스
.cs 파일
→
Roslyn 컴파일

(.dll)
→
JIT 컴파일
실행 직전 IL→기계어
(런타임)
→
CPU 실행
네이티브 코드

JIT(Just-In-Time)는 메서드가 처음 호출될 때 IL을 그 자리에서 기계어로 번역합니다. 실행 중 수집한 정보(어떤 분기가 자주 타는지 등)로 코드를 다시 최적화하는 Tiered Compilation과 PGO(Profile-Guided Optimization)가 .NET 10 기본 동작이라, 오래 켜두는 게임 서버일수록 시간이 지나며 더 빨라집니다.

Native AOT는 반대로 빌드 시점에 미리 전부 기계어로 만들어 둡니다. JIT 워밍업이 없어 시작이 빠르고 메모리가 작아, 빠르게 뜨고 죽는 함수형 워커나 사이드카에 유리합니다.

함정: Native AOT는 런타임 코드 생성(Reflection.Emit), 동적 어셈블리 로드, 일부 무제한 리플렉션을 쓸 수 없습니다. Orleans처럼 코드 생성·리플렉션에 의존하는 프레임워크가 핵심인 게임 서버 본체는 보통 JIT(Server GC) 기반으로 운영하는 편이 안전합니다.

"서버 GC"와 "워크스테이션 GC"는 뭐가 다른가요? 면접에서 자주 묻던데요.

둘 다 자동 메모리 회수(GC)지만 지연시간(latency)과 처리량(throughput) 중 무엇을 우선하느냐가 다릅니다.

구분 Workstation GC Server GC
힙 구성 단일 힙, GC 스레드 1개 코어(또는 지정)마다 힙·GC 스레드 분리
최적화 대상 UI 반응성, 낮은 메모리 높은 처리량, 멀티코어 병렬 회수
적합한 곳 데스크톱 앱, CLI 도구 다수 동접을 받는 게임 서버
주의점 코어 많아도 못 살림 힙이 코어 수만큼 늘어 메모리 사용량↑

ASP.NET Core 서버 프로젝트는 Server GC가 기본값입니다. 추가로 컨테이너에서는 코어를 다 쓰지 못하게 막히는 경우가 많으므로, GCHeapCount나 DOTNET_GCHeapHardLimitPercent로 힙 수·상한을 명시해 K8s 메모리 limit과 충돌하지 않게 맞추는 것이 시니어의 튜닝 포인트입니다.

C#
<!-- .csproj: 동접을 받는 게임 서버는 Server GC + Concurrent -->
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
  <!-- TieredPGO는 .NET 10에서 기본 on, 명시해도 무방 -->
  <TieredPGO>true</TieredPGO>
</PropertyGroup>

정리하면 .NET이 게임 백엔드에 맞는 이유는 (1) Server GC + Tiered/PGO로 장시간 운영 시 처리량이 우수하고, (2) async/await로 수만 동접 I/O를 적은 스레드로 처리하며, (3) Orleans·Kestrel·DI 같은 1급 서버 생태계가 한 언어로 통합되기 때문입니다.

Part 2: Generic Host — 앱의 진짜 시작점

제목이 "Main에서 시작하지 않는다"인데, 그럼 어디서 시작하나요?

물리적으로는 여전히 Main입니다. 다만 현대 .NET 서버에서 Main은 한두 줄이고, 실제 일은 Host라는 컨테이너가 합니다. Host는 (1) DI 컨테이너, (2) Configuration, (3) Logging, (4) 생명주기 관리, (5) 백그라운드 서비스 실행을 하나로 묶은 앱의 런타임 셸입니다.

WebApplication.CreateBuilder()는 내부적으로 Generic Host 위에 Kestrel·라우팅을 얹은 버전입니다. 즉 웹 서버든 순수 워커든 같은 Host 골격을 공유합니다.

C#
// Program.cs — top-level statements. Main이 보이지 않지만 컴파일러가 감싸줍니다.
var builder = WebApplication.CreateBuilder(args);

// 1) 서비스(=의존성)를 DI 컨테이너에 등록하는 "구성" 단계
builder.Services.AddSingleton<IMatchRepository, RedisMatchRepository>();
builder.Services.AddHostedService<MatchCleanupWorker>();

var app = builder.Build();   // 여기서 컨테이너가 "동결(freeze)"됩니다

// 2) 미들웨어 파이프라인과 엔드포인트를 꽂는 "실행" 단계
app.MapGet("/players/{id}", (string id, ISessionService s) => s.Find(id));

await app.RunAsync();        // 종료 신호가 올 때까지 블록

핵심 흐름은 구성(Build 전) → 동결(Build) → 실행(Run) 3단계입니다. Build() 이후에는 서비스를 더 등록할 수 없습니다. 이 경계를 모르면 "왜 등록이 안 먹히지?" 류의 버그를 만듭니다.

서버가 켜진 뒤 계속 도는 백그라운드 작업(매치 정리 같은)은 어떻게 만드나요?

IHostedService를 구현하면 Host가 시작될 때 StartAsync, 종료될 때 StopAsync를 호출해 줍니다. 주기적/지속 작업은 이를 감싼 BackgroundService를 상속해 ExecuteAsync 하나만 채우면 됩니다.

C#
// 좀비 매치(아무도 안 남은 방)를 주기적으로 청소하는 워커
public sealed class MatchCleanupWorker(
    IMatchRepository repo,
    ILogger<MatchCleanupWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        // stoppingToken은 graceful shutdown 시 신호가 옵니다
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(30));
        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            var removed = await repo.PurgeEmptyMatchesAsync(stoppingToken);
            if (removed > 0)
                logger.LogInformation("빈 매치 {Count}개 정리", removed);
        }
    }
}

함정: ExecuteAsync 안에서 while(true)로 돌면서 stoppingToken을 무시하면, 서버가 종료를 시도해도 워커가 멈추지 않아 종료가 영원히 매달립니다. 모든 루프와 비동기 호출에 stoppingToken을 반드시 전파해야 합니다.

"우아한 종료(graceful shutdown)"는 정확히 무슨 의미인가요? K8s에서 중요하다던데요.

SIGTERM(K8s가 파드를 내릴 때 보내는 신호)을 받으면 바로 죽는 게 아니라, 새 요청은 거부하되 처리 중인 요청·세션은 안전하게 마무리하고 나서 종료하는 것을 말합니다. Host에는 IHostApplicationLifetime이 있어 ApplicationStopping 토큰으로 이 순간을 잡을 수 있습니다.

SIGTERM 수신
K8s가 파드 종료 시작
→
ApplicationStopping
신규 요청 차단
HostedService StopAsync
→
Drain
진행 요청 완료
세션 flush · 연결 정리
→
프로세스 종료
코드 0 반환

기본 종료 타임아웃은 ShutdownTimeout(기본 30초)입니다. 이 안에 끝내지 못하면 강제 종료되어 세션 유실이 발생할 수 있으니, K8s의 terminationGracePeriodSeconds를 이 값보다 넉넉히 잡아야 합니다. 실제 flush 코드는 Part 6에서 다룹니다.

Part 3: 의존성 주입 — 수명(Lifetime)이 곧 버그의 근원

Singleton, Scoped, Transient — 셋의 차이를 한 번에 정리해 주세요.

DI 컨테이너가 "이 의존성의 인스턴스를 언제 새로 만들고 언제 재사용할지" 정하는 규칙이 수명입니다.

수명 인스턴스 생성 시점 게임 백엔드 예시
Singleton 앱 전체에 1개. 프로세스 생명주기 동안 공유 Redis 연결 풀, 매치 큐, 설정 캐시
Scoped 스코프(=HTTP 요청)마다 1개 요청별 DbContext, 요청 단위 UnitOfWork
Transient 주입될 때마다 매번 새로 가벼운 stateless 헬퍼, 검증기
🎯 비유로 이해하기

게임 서버를 식당이라고 생각해 봅시다.

Singleton은 주방(하나뿐이고 모두가 공유). Scoped는 손님 한 테이블에 배정된 담당 웨이터(그 손님 식사 동안만 유효). Transient는 주문할 때마다 새로 뽑는 영수증(매번 새 종이)입니다.

C#
builder.Services.AddSingleton<IRedisConnection, RedisConnection>();   // 연결 풀: 공유
builder.Services.AddScoped<GuildUnitOfWork>();                       // 요청 단위 트랜잭션
builder.Services.AddTransient<IDamageCalculator, DamageCalculator>(); // 매번 새로
"captive dependency"가 뭔가요? 이걸로 사고 났다는 얘기를 들었어요.

긴 수명이 짧은 수명을 붙잡아 가두는 현상입니다. Singleton이 생성자에서 Scoped를 주입받으면, 그 Scoped 인스턴스는 Singleton과 함께 앱 전체 동안 살아남습니다. 요청마다 새로 만들어져야 할 것이 첫 요청 것에 고정되어 버리는 것입니다.

C#
// 잘못된 예: Singleton이 Scoped DbContext를 캡처해 버림
public sealed class MatchmakingService          // Singleton으로 등록됨
{
    private readonly GameDbContext _db;          // Scoped여야 정상!
    public MatchmakingService(GameDbContext db) => _db = db; // 첫 요청 컨텍스트에 고정
}

DbContext는 스레드 안전하지 않습니다. 이렇게 캡처되면 모든 요청이 같은 컨텍스트를 동시에 건드려 InvalidOperationException("A second operation started...")이나 데이터 오염이 터집니다.

해결은 Singleton이 직접 Scoped를 들고 있지 않고, 필요할 때 스코프를 직접 열어서 꺼내 쓰는 것입니다.

C#
public sealed class MatchmakingService(IServiceScopeFactory scopeFactory)
{
    public async Task ProcessTickAsync(CancellationToken ct)
    {
        // 매 작업마다 짧은 스코프를 만들어 Scoped 의존성을 안전하게 사용
        await using var scope = scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<GameDbContext>();
        await db.SaveChangesAsync(ct);
    } // 스코프가 닫히며 DbContext가 정상 폐기됩니다
}

.NET은 개발 환경에서 ValidateScopes를 켜 두어, Singleton이 Scoped를 직접 주입받으면 Build() 시점에 예외로 막아 줍니다. CI에서 이 검증이 켜진 상태로 부팅 테스트를 돌리면 captive dependency를 배포 전에 잡을 수 있습니다.

Part 4: Configuration & Options — 설정을 코드처럼 다루기

설정값(접속 정보, 매치 정원 등)은 어디서 읽고 어떻게 합쳐지나요?

.NET의 Configuration은 여러 소스를 순서대로 겹쳐 쌓는(layered) 구조입니다. 같은 키가 여러 곳에 있으면 나중에 추가된 소스가 이깁니다. 기본 순서는 아래와 같습니다.

appsettings.json
공통 기본값
→
appsettings.{Env}.json
환경별 덮어쓰기
→
환경변수
컨테이너/K8s 주입
→
명령행 인자
최종 승자

덕분에 비밀번호 같은 민감값은 파일에 두지 않고 환경변수로 주입할 수 있습니다. K8s에서는 보통 Secret을 환경변수로 마운트하며, Redis__ConnectionString처럼 이중 밑줄(__)이 JSON의 계층(콜론)으로 매핑됩니다.

C#
// appsettings.json
{
  "Match": { "MaxPlayers": 8, "SessionTimeoutSeconds": 120 },
  "Redis": { "ConnectionString": "localhost:6379" }
}

// 환경변수로 덮어쓰기 (K8s Secret/ConfigMap)
//   Match__MaxPlayers=10
//   Redis__ConnectionString=redis-prod:6379
IOptions, IOptionsSnapshot, IOptionsMonitor — 비슷한데 뭐가 다른가요?

설정을 문자열 키로 꺼내 쓰는 대신, 강타입 클래스에 바인딩해 주입받는 것이 Options 패턴입니다. 세 인터페이스의 차이는 "언제 값을 읽고, 변경을 반영하느냐"입니다.

인터페이스 수명/갱신 언제 쓰나
IOptions<T> Singleton, 앱 시작 시 1회 고정 실행 중 안 바뀌는 값(매치 정원 등)
IOptionsSnapshot<T> Scoped, 요청마다 새로 읽음 요청 단위로 최신값을 원할 때
IOptionsMonitor<T> Singleton, 변경 시 즉시 알림(OnChange) 싱글톤·백그라운드 워커에서 실시간 반영
C#
// 강타입 옵션 클래스
public sealed class MatchOptions
{
    public int MaxPlayers { get; init; } = 8;
    public int SessionTimeoutSeconds { get; init; } = 120;
}

// 등록 + 검증(부팅 시점에 잘못된 설정을 잡음)
builder.Services
    .AddOptions<MatchOptions>()
    .Bind(builder.Configuration.GetSection("Match"))
    .Validate(o => o.MaxPlayers is > 0 and <= 64, "MaxPlayers는 1~64")
    .ValidateOnStart();   // 위반 시 앱이 아예 안 뜨게 함
C#
// 백그라운드 워커에서 핫 리로드: IOptionsMonitor로 실시간 반영
public sealed class MatchmakingWorker(IOptionsMonitor<MatchOptions> opts)
{
    public int CurrentMaxPlayers => opts.CurrentValue.MaxPlayers; // 항상 최신
}

함정: Singleton 서비스에 IOptionsSnapshot<T>를 주입하면 안 됩니다. Snapshot은 Scoped라 captive dependency가 되어 ValidateScopes에서 막힙니다. 싱글톤에서는 IOptionsMonitor<T>를 쓰세요.

Part 5: Kestrel & 미들웨어 파이프라인

요청이 들어오면 어디를 거쳐 처리되나요? Kestrel은 또 뭔가요?

Kestrel은 .NET에 내장된 크로스플랫폼 웹 서버입니다. 소켓에서 바이트를 읽어 HTTP로 파싱하고, 그 요청을 미들웨어 파이프라인이라는 양파 껍질 구조로 흘려보냅니다. 각 미들웨어는 다음(next)을 부르기 전과 후에 코드를 실행할 수 있습니다.

🎯 비유로 이해하기

미들웨어 파이프라인은 공항 입국 심사대와 같습니다. 들어올 때 여권 검사(인증)→세관(검증)→입국(엔드포인트) 순으로 통과하고, 나갈 때는 역순으로 거칩니다. 앞 단계에서 막히면(인증 실패) 뒤 단계까지 가지 않고 바로 돌아갑니다(short-circuit).

순서가 곧 동작입니다. 인증(Authentication)은 인가(Authorization)보다 앞서야 하고, 예외 처리·로깅은 가장 바깥쪽에 두어야 안쪽에서 던진 예외를 잡을 수 있습니다.

C#
var app = builder.Build();

app.UseExceptionHandler("/error"); // 가장 바깥: 아래 단계의 예외를 포착
app.UseSerilogRequestLogging();    // 요청 로깅 (ELK로 흘러감)
app.UseAuthentication();           // 너는 누구인가 (JWT 검증)
app.UseAuthorization();            // 권한이 있는가 (반드시 Authn 다음)

app.MapGet("/matches/{id}", GetMatch); // 엔드포인트(가장 안쪽)
await app.RunAsync();

함정: UseAuthorization을 UseAuthentication보다 먼저 두면, 인가 단계에서 사용자 정보가 아직 채워지지 않아 항상 401/403이 나거나 인증이 무력화됩니다. 순서 실수는 컴파일 에러가 아니라 런타임 보안 구멍이 됩니다.

엔드포인트는 Minimal API로 짜나요? 커스텀 미들웨어는 어떻게 만드나요?

게임 백엔드의 가벼운 HTTP 엔드포인트(상태 조회, 매치 생성 등)는 Minimal API로 간결하게 작성합니다. 핸들러 파라미터에 DI 서비스를 그대로 받을 수 있습니다.

C#
// Minimal API: 라우트 그룹으로 묶고 서비스를 파라미터로 주입
var matches = app.MapGroup("/matches");

matches.MapPost("/", async (CreateMatchReq req, IMatchService svc, CancellationToken ct) =>
{
    var match = await svc.CreateAsync(req.HostPlayerId, ct);
    return Results.Created($"/matches/{match.Id}", match);
});

matches.MapGet("/{id}", async (string id, IMatchService svc, CancellationToken ct) =>
    await svc.FindAsync(id, ct) is { } m
        ? Results.Ok(m)
        : Results.NotFound());

공통 관심사(요청별 추적 ID 부여 등)는 커스텀 미들웨어로 분리합니다. 고성능 경로라면 매 요청 할당을 줄이도록 IMiddleware 대신 규약 기반(생성자 주입 + Invoke) 미들웨어를 쓰되, 안에서 무거운 동기 블로킹을 절대 하지 않는 것이 핵심입니다.

커스텀 미들웨어 — 요청 상관관계 ID 주입 C# 
public sealed class CorrelationIdMiddleware(RequestDelegate next)
{
    private const string Header = "X-Correlation-Id";

    public async Task InvokeAsync(HttpContext ctx)
    {
        // 들어오는 헤더가 있으면 잇고, 없으면 새로 발급
        var id = ctx.Request.Headers.TryGetValue(Header, out var v)
            ? v.ToString()
            : Guid.NewGuid().ToString("N");

        ctx.Response.Headers[Header] = id;

        // 로그 스코프에 넣어 두면 ELK에서 한 요청을 끝까지 추적 가능
        using (ctx.RequestServices
                  .GetRequiredService<ILogger<CorrelationIdMiddleware>>()
                  .BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
        {
            await next(ctx); // 다음 미들웨어로
        }
    }
}

// 등록: 로깅보다 앞에 두어 모든 로그에 ID가 찍히게 함
app.UseMiddleware<CorrelationIdMiddleware>();

Part 6: 게임 백엔드에 통째로 적용하기

지금까지 배운 걸 묶어서 실제 게임 서버 부팅 코드로 보고 싶어요.

아래는 세션 관리 + 백그라운드 워커 + 헬스체크 + 우아한 종료를 갖춘 최소 게임 백엔드 부팅 코드입니다. 앞 파트의 조각들이 어떻게 한 자리에 모이는지 보여 줍니다.

WebApplication Host
DI: SessionService(Singleton) · MatchService(Scoped)
BackgroundService: MatchCleanupWorker
Middleware: 예외 → 로깅 → 인증/인가
Endpoints: /matches · /healthz
Lifetime: ApplicationStopping → 세션 flush
C#
var builder = WebApplication.CreateBuilder(args);

// 1) 설정 바인딩 + 부팅 검증
builder.Services.AddOptions<MatchOptions>()
    .Bind(builder.Configuration.GetSection("Match")).ValidateOnStart();

// 2) 의존성 등록 (수명 선택이 핵심)
builder.Services.AddSingleton<ISessionService, RedisSessionService>(); // 공유 상태
builder.Services.AddScoped<IMatchService, MatchService>();            // 요청 단위
builder.Services.AddHostedService<MatchCleanupWorker>();              // 상시 워커

// 3) 헬스체크: K8s liveness/readiness probe가 찌를 엔드포인트
builder.Services.AddHealthChecks()
    .AddCheck<RedisHealthCheck>("redis");

var app = builder.Build();

// 4) 파이프라인 (순서 = 동작)
app.UseExceptionHandler("/error");
app.UseAuthentication();
app.UseAuthorization();

// 5) 엔드포인트
app.MapHealthChecks("/healthz");           // readiness probe
app.MapGet("/matches/{id}", async (string id, IMatchService s, CancellationToken ct)
    => await s.FindAsync(id, ct) is { } m ? Results.Ok(m) : Results.NotFound());

await app.RunAsync();
종료 신호가 왔을 때 메모리에 있던 세션을 Redis/DB로 flush하려면요?

핵심은 IHostApplicationLifetime.ApplicationStopping 토큰이나, 종료 시 StopAsync가 보장 호출되는 IHostedService에 flush 로직을 거는 것입니다. 후자가 더 견고합니다. Host가 종료 단계에서 반드시 기다려 주기 때문입니다.

C#
// 종료 시 메모리 세션을 Redis로 안전하게 내보내는 서비스
public sealed class SessionFlushService(
    ISessionService sessions,
    ILogger<SessionFlushService> logger) : IHostedService
{
    public Task StartAsync(CancellationToken ct) => Task.CompletedTask;

    public async Task StopAsync(CancellationToken ct)
    {
        // ct는 ShutdownTimeout 안에서만 유효 — 이 안에 끝내야 함
        logger.LogInformation("종료 감지 — 활성 세션 flush 시작");
        var flushed = await sessions.FlushAllAsync(ct);
        logger.LogInformation("세션 {Count}건 영속화 완료", flushed);
    }
}

builder.Services.AddHostedService<SessionFlushService>();

HostedService의 StopAsync는 등록의 역순으로 호출됩니다. 따라서 새 요청을 받는 워커를 먼저 멈추고, flush 서비스를 나중에 등록하면 "더 이상 세션이 늘지 않는 상태에서 마지막으로 비우기"라는 순서를 자연스럽게 보장할 수 있습니다.

flush가 ShutdownTimeout(기본 30초)을 넘기면 토큰이 취소되어 작업이 잘립니다. 세션이 많다면 타임아웃을 늘리고(HostOptions.ShutdownTimeout), K8s terminationGracePeriodSeconds도 그보다 크게 설정해 강제 SIGKILL을 피해야 데이터 유실이 없습니다.

C#
// 세션이 많은 서버라면 종료 유예시간을 늘립니다
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(45));

📌 핵심 정리

  • 런타임: IL을 JIT(Tiered/PGO)이 실행 중 최적화 → 오래 켜둘수록 빨라지는 게임 서버에 유리. 동접 서버는 Server GC가 정답이며 컨테이너 메모리 limit과 힙 수를 맞춰야 합니다.
  • Host는 DI·Config·Logging·생명주기를 묶은 셸. 구성 → Build(동결) → Run 3단계를 이해하고, 상시 작업은 BackgroundService에 stoppingToken을 끝까지 전파합니다.
  • DI 수명: Singleton/Scoped/Transient를 도메인에 맞게 고르되, Singleton이 Scoped를 붙드는 captive dependency는 IServiceScopeFactory로 회피하고 ValidateScopes로 부팅 시 검증합니다.
  • Configuration/Options는 소스를 겹쳐 쌓고 환경변수(__)로 덮어씁니다. 싱글톤·워커에는 IOptionsMonitor, 요청 단위 최신값은 IOptionsSnapshot, 고정값은 IOptions를 쓰며 ValidateOnStart로 잘못된 설정을 부팅에서 차단합니다.
  • 파이프라인 순서가 곧 동작입니다. 예외→로깅→인증→인가→엔드포인트 순서를 지키고, 종료 시에는 헬스체크·StopAsync·세션 flush를 ShutdownTimeout·terminationGracePeriodSeconds 안에서 우아하게 마무리합니다.
