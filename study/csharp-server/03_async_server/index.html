서버는 멀쩡한데 응답이 멈췄다?

ThreadPool 고갈 · sync-over-async 데드락 · 백프레셔

Part 1: 서버에서 async가 의미하는 것

클라이언트 코드에서는 async가 "UI 안 멈추게 하는 것"이었습니다. 서버에서는 무엇을 위한 건가요?

서버에서 async는 사용자 경험이 아니라 처리량(throughput)을 위한 것입니다. 한 문장으로 요약하면 "적은 스레드로 많은 동시 요청을 처리하기 위한 것"입니다.

이를 이해하려면 두 가지 서버 모델을 비교해야 합니다. 고전적인 요청당 스레드(thread-per-request) 모델과, 현대 .NET의 async I/O 모델입니다.

요청당 스레드 모델에서 동시 접속 5,000명을 받으려면, I/O를 기다리는 동안 블로킹되는 스레드 5,000개가 필요합니다. 스레드 하나는 기본 1MB 스택을 잡으므로 5GB가 스택만으로 증발하고, 컨텍스트 스위칭 비용이 폭발합니다.

반면 async 모델에서는 DB 응답이나 소켓 수신을 기다리는 동안 스레드를 점유하지 않습니다. await 지점에서 스레드를 풀에 반납하고, I/O가 완료되면 그제서야 ThreadPool 스레드 하나를 빌려와 이어서 실행합니다. 그래서 코어 수에 가까운 적은 스레드(수십 개)로 수천 개의 동시 요청을 처리할 수 있습니다.

🎯 비유로 이해하기

식당의 종업원을 떠올려 보십시오.

요청당 스레드는 손님 한 명마다 전담 종업원을 붙이는 방식입니다. 손님이 음식을 먹는 30분 동안(=I/O 대기) 그 종업원은 옆에 멀뚱히 서서 아무것도 못 합니다. 손님 100명이면 종업원 100명이 필요합니다.

async는 종업원 3명이 주문만 받아 주방(=I/O)에 넘기고 다른 테이블로 갑니다. 음식이 나왔다는 신호가 오면(=await 완료) 그때 손이 빈 종업원이 서빙합니다. 손님 100명을 종업원 3명이 처리합니다.

핵심은 "async는 일을 더 빨리 끝내주지 않는다"는 점입니다. DB 쿼리 하나가 빨라지는 게 아닙니다. 다만 기다리는 동안 스레드를 다른 요청에 양보하므로 같은 하드웨어로 더 많은 동시 요청을 소화합니다.

그럼 두 모델의 동작을 그림으로 보면 어떻게 다른가요?
요청당 스레드 (블로킹)
요청 도착 → 스레드 점유 → DB 응답까지 스레드가 잠듦 → 응답 → 스레드 해제
→
결과
동시 요청 = 잠든 스레드 수. 스레드 수천 개 필요. 메모리·스위칭 폭발.
async I/O (논블로킹)
요청 도착 → 스레드 점유 → await db에서 스레드 반납 → (스레드는 다른 요청 처리) → I/O 완료 콜백 → 풀에서 스레드 빌려 이어감
→
결과
동시 요청 ≫ 스레드 수. 코어 수 수준의 스레드로 수천 동시성.
C#
// 패킷 핸들러 — 이 안에서 await로 스레드를 양보해야 throughput이 산다
public async Task HandleLoginAsync(LoginPacket packet, CancellationToken ct)
{
    // await 지점: DB가 응답하는 수십 ms 동안 이 스레드는 풀로 반납되어
    // 다른 접속자의 패킷을 처리합니다. 스레드가 잠들지 않습니다.
    Account? account = await _db.FindAccountAsync(packet.UserId, ct);

    if (account is null)
    {
        await SendAsync(new LoginFail("존재하지 않는 계정"), ct);
        return;
    }

    // 또 다른 비동기 I/O. 역시 스레드를 점유하지 않고 대기합니다.
    await _redis.SetSessionAsync(account.Id, _connectionId, ct);

    await SendAsync(new LoginOk(account.Nickname), ct);
}

Part 2: ThreadPool 고갈 — 풀을 말려 죽이는 한 줄

"서버 CPU는 5%인데 응답이 다 타임아웃 난다"는 장애를 봤습니다. 무슨 일인가요?

전형적인 ThreadPool 고갈(starvation) 증상입니다. CPU가 한가한데도 요청이 줄줄이 밀리는 이유는, 일을 처리할 스레드가 없기 때문입니다. 코드 어딘가에서 비동기여야 할 호출을 동기 블로킹으로 처리하고 있는 것이 원인입니다.

async 메서드 안에서 .Result, .Wait(), .GetAwaiter().GetResult(), 동기 Thread.Sleep, 동기 DB/HTTP API를 호출하면, 그 스레드는 I/O가 끝날 때까지 풀로 반납되지 못하고 점유됩니다. 양보하라고 만든 모델에서 양보를 막아버리는 것입니다.

고갈이 진행되는 과정을 단계로 보면 이렇습니다.

1. 부하 유입
동시 요청이 풀의 워커 스레드 수를 넘어섬
→
2. 스레드 점유
각 요청이 .Result로 블로킹 → 스레드 반납 안 됨
→
3. 풀 고갈
대기 큐에 작업이 쌓임. 새 스레드는 ~1초에 1개씩만 천천히 주입
→
4. 응답 멈춤
지연 폭증 → 클라 타임아웃 → 재시도로 부하 가중 → 악순환

결정적 단서는 "스레드 주입 속도"입니다. ThreadPool은 고갈을 감지하면 스레드를 즉시 무한정 늘리지 않고 약 1초에 하나꼴로 천천히 추가합니다(hill-climbing). 그래서 갑자기 100개가 막히면 회복에 100초가 걸리는 듯한 "응답이 멈췄다"가 발생합니다.

고갈을 일으키는 코드와 올바른 코드를 비교해 주세요.
C# — 안티패턴 (풀을 말려 죽임)
public MatchResult ProcessMatch(MatchRequest req)
{
    // ❌ 비동기 메서드를 동기로 블로킹. 이 스레드는 DB 응답까지 풀로 못 돌아감.
    var players = _db.LoadPlayersAsync(req.PlayerIds).Result;

    // ❌ .Wait()도 동일. 동시 요청이 몰리면 이 줄들이 풀을 통째로 잠가버림.
    _redis.PublishMatchAsync(players).Wait();

    return Calculate(players);
}
C# — 올바른 패턴 (스레드를 양보)
public async Task<MatchResult> ProcessMatchAsync(MatchRequest req, CancellationToken ct)
{
    // ✅ await로 대기 중 스레드를 풀에 반납. 다른 매치 요청이 그 스레드를 씀.
    var players = await _db.LoadPlayersAsync(req.PlayerIds, ct);

    await _redis.PublishMatchAsync(players, ct);

    return Calculate(players); // CPU 작업만 동기로 수행
}

규칙은 단순합니다. "async는 끝까지 async로(async all the way)." 호출 체인 한 곳이라도 동기로 블로킹하면 그 지점이 풀의 병목이 됩니다.

실제 장애 상황에서 ThreadPool 고갈을 어떻게 진단하나요?

핵심 지표는 "큐에 쌓인 작업 수"와 "사용 중 스레드 수"입니다. .NET은 EventCounters로 이를 노출합니다. 운영에서는 dotnet-counters로 즉시 확인할 수 있습니다.

bash — 운영 중 라이브 진단
# ThreadPool 카운터를 실시간으로 관찰
dotnet-counters monitor --process-id <PID> \
    --counters System.Runtime[threadpool-thread-count,threadpool-queue-length]

# threadpool-queue-length 가 계속 증가하면서
# threadpool-thread-count 가 천천히만 오르면 → 고갈 확정

코드 내부에서 직접 모니터링 메트릭으로 내보낼 수도 있습니다. ELK/APM 대시보드에 큐 길이를 올려두면 장애 전조를 잡을 수 있습니다.

C# — 큐 길이를 메트릭으로 노출
// 백그라운드에서 주기적으로 ThreadPool 상태를 관측치로 기록
ThreadPool.GetAvailableThreads(out int worker, out int io);
long pending = ThreadPool.PendingWorkItemCount; // 큐에 대기 중인 작업 수

_metrics.RecordGauge("threadpool.queue_length", pending);
_metrics.RecordGauge("threadpool.available_worker", worker);
// pending 이 지속적으로 0보다 크게 유지되면 경보를 울립니다.
증상 관찰값 의심 원인
응답 지연 폭증 + 타임아웃 CPU 낮음, queue-length 증가 sync-over-async 블로킹
점진적으로 회복 thread-count가 초당 1개씩 증가 풀 hill-climbing 주입 속도 한계
응답 지연 + CPU 100% queue-length 정상 고갈 아님. 실제 CPU 병목/핫루프

임시방편으로 ThreadPool.SetMinThreads를 크게 잡아 고갈을 가리려는 유혹이 있습니다. 일시적으로 증상은 완화되지만 근본 원인인 동기 블로킹은 그대로입니다. 면접에서는 "MinThreads를 올린다"가 아니라 "블로킹 호출을 찾아 await로 바꾼다"가 정답입니다.

Part 3: sync-over-async 데드락 — 한 스레드가 자기 자신을 기다린다

".Result 한 줄 썼더니 스레드가 완전히 멈췄다"는 데드락은 어떻게 생기나요?

고갈과는 다른, 더 치명적인 현상입니다. 고갈은 "느려짐"이지만 이건 "영원히 안 풀림"입니다. 원인은 SynchronizationContext입니다.

핵심 메커니즘은 이렇습니다. SynchronizationContext가 존재하는 환경(예: Unity 메인 스레드, WPF/WinForms UI 스레드, 구형 ASP.NET)에서는 await 이후의 이어지는 코드(continuation)가 반드시 원래의 그 컨텍스트(같은 스레드)에서 실행되도록 예약됩니다.

1. 메인 스레드
SomeAsync().Result 호출 → 메인 스레드가 블로킹
→
2. await 완료
continuation을 "메인 스레드에서 실행해줘"라고 컨텍스트에 예약
→
3. 데드락
메인 스레드는 .Result로 막혀 있어 continuation을 실행할 수 없음. 서로 영원히 대기.

정리하면, 메인 스레드는 continuation이 끝나야 .Result에서 풀리는데, continuation은 메인 스레드가 비어야 실행되는 순환 대기입니다. 한 스레드가 자기 자신이 비기를 기다리는 셈입니다.

"ASP.NET Core에는 SynchronizationContext가 없다"고 들었습니다. 그럼 서버는 안전한가요?

맞습니다. ASP.NET Core는 의도적으로 SynchronizationContext를 제거했습니다. 그래서 ASP.NET Core 요청 처리 안에서 .Result를 써도 이 종류의 데드락은 발생하지 않습니다. 대신 Part 2의 ThreadPool 고갈이 발생합니다. (느려지긴 하지만 영원히 멈추진 않습니다.)

그러나 "서버 = 안전"이라고 단정하면 안 됩니다. 게임 백엔드 현실에서 데드락이 나는 경로는 따로 있습니다.

환경 SyncContext .Result 사용 시
ASP.NET Core / 콘솔 서버 없음 데드락 X, 대신 ThreadPool 고갈
Unity 클라이언트 (메인 스레드) 있음 (UnitySynchronizationContext) 데드락 O — 게임이 통째로 멈춤
구형 ASP.NET (.NET Framework) 있음 (AspNetSynchronizationContext) 데드락 O
WPF/WinForms 운영툴 있음 데드락 O

게임 서버 개발에서 데드락은 주로 (1) 공유 라이브러리가 클라이언트(Unity)와 서버 양쪽에서 쓰이는데 라이브러리 내부에 .Result가 박혀 있을 때, 또는 (2) 운영툴/패치 도구가 WPF·구형 프레임워크일 때 터집니다. 즉 "서버 코드"가 아니라 "클라이언트와 공유하는 코드"가 위험합니다.

C# — Unity와 공유되는 라이브러리에서 데드락을 부르는 코드
// 이 메서드가 Unity 메인 스레드에서 .Result로 호출되면 게임이 멈춥니다.
public string GetPlayerName(int id)
{
    // ❌ 동기 메서드 안에서 비동기를 .Result로 블로킹.
    //    Unity 메인 스레드의 SyncContext와 만나면 즉시 데드락.
    return _api.FetchPlayerAsync(id).Result.Name;
}

근본 해법은 역시 호출자까지 async로 전파하는 것입니다. 정말 동기 진입점이 강제될 때만, 컨텍스트를 우회하는 차선책을 씁니다.

C# — 불가피한 동기 진입점에서의 차선책
// 차선책 1: continuation을 원래 컨텍스트로 되돌리지 않게 하여 데드락 회피
var name = Task.Run(() => _api.FetchPlayerAsync(id)).GetAwaiter().GetResult().Name;
// Task.Run으로 풀 스레드에서 실행 → 그 스레드엔 SyncContext가 없어 continuation이
// 메인 스레드를 기다리지 않습니다. (단, 추가 스레드 점유 비용은 감수)

// 정답: 애초에 메서드 시그니처를 async Task<string> 로 만들고 await로 호출

Part 4: ConfigureAwait(false)와 ValueTask — 라이브러리·핫패스의 무기

ConfigureAwait(false)는 언제, 왜 붙이나요?

ConfigureAwait(false)는 "await 이후의 continuation을 원래 SynchronizationContext로 되돌리지 말고, 아무 ThreadPool 스레드에서 이어서 실행하라"는 지시입니다. 두 가지 효과가 있습니다.

(1) 데드락 예방 — Part 3의 순환 대기를 끊습니다. continuation이 메인 스레드를 기다리지 않습니다. (2) 약간의 성능 이득 — 컨텍스트 캡처/전환 오버헤드를 제거합니다.

핵심 지침: "라이브러리 코드에는 거의 항상 붙이고, 애플리케이션 코드에서는 신경 쓰지 않는다." 라이브러리는 자신이 어떤 환경(Unity, WPF, 서버)에서 호출될지 모르므로, 컨텍스트에 의존하지 않게 만들어야 안전합니다.

C# — 공유 라이브러리(SDK) 내부
public async Task<Account> FetchAccountAsync(int id, CancellationToken ct)
{
    // 라이브러리이므로 ConfigureAwait(false). 어떤 컨텍스트에서 불려도 안전.
    var raw = await _http.GetAsync($"/account/{id}", ct).ConfigureAwait(false);
    var json = await raw.Content.ReadAsStringAsync(ct).ConfigureAwait(false);
    return Deserialize(json);
}

주의: ASP.NET Core 애플리케이션 코드에는 컨텍스트가 없으므로 ConfigureAwait(false)를 붙여도 효과가 거의 없고, 오히려 코드를 지저분하게 만듭니다. 또 한 가지 함정 — HttpContext 같은 요청 스코프 상태를 await 뒤에서 쓰는데 컨텍스트를 버리면 안 되는 경우가 있으니, 효과가 없는 곳에 기계적으로 붙이지 말아야 합니다.

ValueTask<T>는 Task<T>와 뭐가 다르고, 핫패스에서 왜 쓰나요?

Task<T>는 참조 타입(클래스)이라 await할 때마다 힙에 객체를 할당합니다. 대부분의 경우 이 비용은 무시할 만하지만, 초당 수십만 번 호출되는 핫패스에서, 게다가 대부분 동기적으로 즉시 완료되는 경우에는 이 할당이 GC 압박으로 누적됩니다.

ValueTask<T>는 구조체(struct)입니다. 결과가 이미 캐시에 있어 동기적으로 즉시 반환되는 경우, 힙 할당 없이 값으로 결과를 돌려줍니다.

🎯 비유로 이해하기

Task<T>는 매번 "택배 송장"을 새로 발급하는 것입니다. 물건이 이미 손에 있어도 송장부터 끊습니다.

ValueTask<T>는 "물건이 지금 손에 있으면 그냥 건네주고, 없을 때만 송장을 끊는" 방식입니다. 캐시 적중률이 높은 핫패스에서 송장 발급(=힙 할당) 횟수를 크게 줄입니다.

C# — Redis 캐시 적중 시 동기 완료되는 핫패스
// 패킷마다 호출되는 세션 조회. 99%는 로컬 캐시에서 즉시 반환됩니다.
public ValueTask<Session?> GetSessionAsync(long playerId)
{
    // 캐시 적중: 힙 할당 없이 동기적으로 값 반환 → GC 부담 제로
    if (_localCache.TryGetValue(playerId, out var session))
        return new ValueTask<Session?>(session);

    // 캐시 미스(드물게): 진짜 비동기 Redis 조회를 ValueTask로 감쌈
    return new ValueTask<Session?>(LoadFromRedisAsync(playerId));
}

ValueTask는 공짜가 아닙니다. 사용 규칙이 엄격합니다.

  • 두 번 await 금지 — ValueTask는 한 번만 소비할 수 있습니다. 같은 인스턴스를 두 번 await하면 동작이 정의되지 않습니다.
  • .Result 직접 접근 금지 — 완료 전에 접근하면 깨집니다.
  • 병렬 보관 금지 — Task.WhenAll에 여럿 모아 넘기려면 먼저 .AsTask()로 변환해야 합니다.

결론: 대부분 비동기로 끝나는 일반 메서드는 그냥 Task<T>를 쓰십시오. ValueTask<T>는 "고빈도 호출 + 높은 동기 완료율"이라는 두 조건이 동시에 성립하고, 벤치마크로 이득을 확인한 핫패스에 한정해 씁니다. 섣부른 최적화는 버그만 부릅니다.

구분 Task<T> ValueTask<T>
타입 참조 타입(클래스) 구조체
힙 할당 await마다 발생 동기 완료 시 없음
재사용/멀티 await 안전 1회만 소비 (위험)
권장 용도 기본값. 대부분의 코드 고빈도+동기완료 핫패스만

Part 5: 취소와 타임아웃 — CancellationToken 전파와 스트리밍

왜 모든 async 메서드에 CancellationToken을 받아야 하나요?

서버에서 응답 없는 작업을 무한정 붙들고 있는 것은 곧 리소스 누수이자 고갈의 씨앗입니다. 클라이언트가 이미 접속을 끊었는데 서버가 그 요청의 DB 쿼리를 끝까지 수행하는 것은 낭비입니다. CancellationToken은 "이 작업 그만둬도 된다"는 신호를 호출 체인 끝까지 전달하는 표준 수단입니다.

철칙은 "토큰은 받은 즉시 끝까지 전파한다(token threading)." 패킷 핸들러가 받은 토큰을 DB 호출, Redis 호출, 내부 HTTP 호출 모든 await에 빠짐없이 넘겨야 합니다. 한 곳이라도 토큰을 빠뜨리면 그 지점에서 취소가 멈춥니다.

C# — 토큰을 끝까지 전파
public async Task HandleQueryRankingAsync(RankingRequest req, CancellationToken ct)
{
    // ct를 모든 하위 await에 전파합니다. 접속이 끊기면 연쇄적으로 취소됩니다.
    var top = await _db.GetTopRankingAsync(req.Season, ct);
    var myRank = await _redis.GetRankAsync(req.PlayerId, ct);
    await SendAsync(new RankingResponse(top, myRank), ct);
}
"요청 타임아웃"과 "클라이언트 접속 끊김"을 동시에 처리하려면요? linked token이 그건가요?

맞습니다. CancellationTokenSource.CreateLinkedTokenSource로 여러 취소 원인을 하나의 토큰으로 묶습니다. 둘 중 어느 쪽이 먼저 발생해도 작업이 취소됩니다.

C# — 접속 끊김 + 3초 타임아웃을 linked token으로 결합
public async Task<MatchResult> FindMatchAsync(MatchRequest req, CancellationToken connectionCt)
{
    // 1) 자체 타임아웃 토큰
    using var timeoutCts = new CancellationTokenSource(TimeSpan.FromSeconds(3));

    // 2) 접속 끊김 토큰 + 타임아웃 토큰을 하나로 결합
    using var linked = CancellationTokenSource.CreateLinkedTokenSource(
        connectionCt, timeoutCts.Token);

    try
    {
        // 접속이 끊기거나, 3초가 지나거나, 둘 중 먼저 발생하면 취소됩니다.
        return await _matchmaker.QueryAsync(req, linked.Token);
    }
    catch (OperationCanceledException) when (timeoutCts.IsCancellationRequested)
    {
        // 타임아웃으로 인한 취소만 별도 처리 (접속 끊김과 구분)
        throw new MatchTimeoutException("매칭 시간 초과");
    }
}

함정: CancellationTokenSource는 반드시 using으로 dispose해야 합니다. 특히 타이머가 걸린 CTS를 dispose하지 않으면 타이머 콜백이 객체를 붙잡아 누수가 쌓입니다. 고빈도 경로에서 이게 누적되면 또 다른 메모리 장애가 됩니다.

랭킹처럼 데이터가 많은 응답을 조각조각 흘려보내려면 IAsyncEnumerable<T>를 쓴다던데요?

IAsyncEnumerable<T>는 비동기 스트리밍을 위한 타입입니다. 결과 전체를 한 번에 메모리에 올려 List<T>로 반환하는 대신, 한 건씩 비동기로 산출(yield)합니다. 10만 행을 한 번에 메모리로 올리지 않고 흘려보낼 수 있어 메모리 스파이크를 막습니다.

C# — DB 커서를 스트리밍으로 흘려보내기
// [EnumeratorCancellation]으로 await foreach의 토큰을 내부 await에 연결합니다.
public async IAsyncEnumerable<RankingRow> StreamRankingAsync(
    int season,
    [EnumeratorCancellation] CancellationToken ct = default)
{
    await using var reader = await _db.OpenRankingReaderAsync(season, ct);

    // 한 행씩 비동기로 읽어 즉시 산출. 전체를 메모리에 쌓지 않습니다.
    while (await reader.ReadAsync(ct))
    {
        yield return new RankingRow(reader.GetInt64(0), reader.GetInt32(1));
    }
}

// 소비 측: 한 건씩 처리하며 토큰 전파
await foreach (var row in StreamRankingAsync(season, ct).WithCancellation(ct))
{
    await SendChunkAsync(row, ct);
}

[EnumeratorCancellation] 어트리뷰트가 핵심입니다. await foreach의 .WithCancellation(ct)로 넘긴 토큰을, 메서드 내부의 ReadAsync(ct)로 자동 연결해 줍니다. 이게 없으면 스트리밍 도중 취소가 전파되지 않습니다.

Part 6: 백프레셔와 동시성 제한 — 부하를 흘려보내지 말고 받아낼 만큼만

async는 "기다려도 스레드를 안 막는다"는데, 그럼 동시 요청을 무한정 받아도 되나요?

아닙니다. 이것이 async의 가장 흔한 오해입니다. await가 스레드를 양보하는 것은 맞지만, 그렇다고 하위 자원이 무한한 것은 아닙니다. DB 커넥션 풀, Redis 연결, 외부 API 레이트리밋은 모두 한정되어 있습니다.

동시 요청 5,000개가 한꺼번에 await _db.QueryAsync()를 호출하면, async 덕에 스레드는 안 막히지만 DB 커넥션 풀(보통 수십~수백)이 즉시 고갈되어 모든 쿼리가 풀 대기에 걸립니다. 또는 DB 자체가 동시 쿼리 폭주로 무너집니다. 스레드 병목이 자원 병목으로 위치만 옮겨간 것입니다.

백프레셔(backpressure)는 "받아낼 수 있는 만큼만 받고, 그 이상은 대기시키거나 거절하는" 흐름 제어입니다. 무한히 받아 안에서 터지는 대신, 입구에서 통제합니다.

SemaphoreSlim으로 동시성을 제한하는 방법은요?

SemaphoreSlim은 "동시에 N개까지만 통과"시키는 비동기 친화적 카운터입니다. 외부 API 호출이나 무거운 DB 쿼리의 동시 실행 수를 제한할 때 씁니다.

C# — 외부 결제 API를 동시에 최대 10개만 호출
// 동시 10개로 제한. 11번째 요청은 자리가 날 때까지 await에서 비동기로 대기합니다.
private readonly SemaphoreSlim _gate = new(initialCount: 10, maxCount: 10);

public async Task<Receipt> PurchaseAsync(PurchaseRequest req, CancellationToken ct)
{
    // WaitAsync는 스레드를 막지 않고 비동기로 자리를 기다립니다.
    await _gate.WaitAsync(ct);
    try
    {
        return await _paymentApi.ChargeAsync(req, ct);
    }
    finally
    {
        _gate.Release(); // 반드시 finally에서 반납. 안 하면 영구 누수.
    }
}

Release()를 finally에 두지 않으면, 예외 발생 시 세마포어 자리가 영영 반납되지 않아 결국 모든 요청이 입구에서 멈춥니다. 이것 역시 사실상의 데드락입니다.

패킷이 몰려들 때 생산자-소비자로 부하를 고르게 펴려면 Channel<T>를 쓴다던데요?

System.Threading.Channels의 Channel<T>는 비동기 생산자-소비자 큐입니다. 패킷 핸들러(생산자)는 작업을 채널에 넣기만 하고 빠르게 반환하며, 별도의 소비자가 정해진 동시성으로 꺼내 처리합니다. 버퍼 크기(capacity)를 정해 백프레셔를 자연스럽게 구현하는 것이 핵심입니다.

생산자 (패킷 핸들러)
수신 패킷을 채널에 Write. 버퍼가 차면 Write가 비동기로 대기(=백프레셔)
→
Channel (유한 버퍼)
capacity로 폭주를 흡수. 넘치면 Wait/Drop 정책
→
소비자 (워커 N개)
정해진 동시성으로 Read해 처리. 하위 자원을 보호
C# — 유한 버퍼 채널로 매치 처리 부하 제어
// capacity=1000 + FullMode.Wait: 버퍼가 차면 생산자가 비동기로 대기 = 백프레셔
private readonly Channel<MatchJob> _channel = Channel.CreateBounded<MatchJob>(
    new BoundedChannelOptions(capacity: 1000)
    {
        FullMode = BoundedChannelFullMode.Wait, // 가득 차면 거절 대신 대기
        SingleReader = false, // 소비자 워커 여러 개
        SingleWriter = false
    });

// 생산자: 패킷 핸들러는 큐에 넣고 즉시 반환 (처리 시간을 떠안지 않음)
public async ValueTask EnqueueAsync(MatchJob job, CancellationToken ct)
    => await _channel.Writer.WriteAsync(job, ct);

// 소비자: 백그라운드 워커가 채널을 끝까지 비동기로 소비
public async Task ConsumeLoopAsync(CancellationToken ct)
{
    await foreach (var job in _channel.Reader.ReadAllAsync(ct))
    {
        await ProcessMatchAsync(job, ct); // 정해진 워커 수만큼만 동시 처리
    }
}
여러 소비자 워커를 동시성 N으로 띄우는 패턴 C# 
// 소비자 워커를 동시성 N개로 기동. 채널 capacity와 워커 수가
// 백프레셔의 두 손잡이입니다.
public Task StartConsumersAsync(int workerCount, CancellationToken ct)
{
    var workers = Enumerable.Range(0, workerCount)
        .Select(_ => Task.Run(() => ConsumeLoopAsync(ct), ct));
    return Task.WhenAll(workers);
}

// 생산이 끝났음을 알릴 때:
// _channel.Writer.Complete(); → ReadAllAsync 루프가 자연스럽게 종료됩니다.
도구 용도 백프레셔 방식
SemaphoreSlim 동시 실행 개수 제한 N개 초과 시 입구에서 비동기 대기
Channel<T> (Bounded) 생산자-소비자 큐잉 버퍼 가득 차면 Wait 또는 Drop
Channel<T> (Unbounded) 버퍼 무제한 백프레셔 없음 — 메모리 폭주 위험, 지양

면접 포인트: "Unbounded 채널은 백프레셔가 없어 부하 폭주 시 메모리를 먹다 OOM으로 죽는다"를 짚을 수 있어야 합니다. 게임 서버처럼 트래픽이 스파이크치는 환경에서는 Bounded + FullMode 정책(대기/드롭/최신유지)으로 명시적 한계를 두는 것이 시니어의 선택입니다.

📌 핵심 정리

  • 서버 async = 처리량: UI 반응성이 아니라, I/O 대기 중 스레드를 양보해 적은 스레드로 수천 동시 요청을 받는 것이 목적입니다. 그래서 "async는 끝까지 async로"가 철칙입니다.
  • ThreadPool 고갈: .Result/.Wait() 등 동기 블로킹이 풀 스레드를 점유하면, CPU가 한가한데도 큐가 쌓여 지연이 폭증합니다. dotnet-counters의 queue-length 증가가 결정적 단서입니다.
  • sync-over-async 데드락: SynchronizationContext가 있는 Unity 메인 스레드·WPF·구형 ASP.NET에서 발생합니다. ASP.NET Core엔 컨텍스트가 없어 데드락 대신 고갈이 납니다. 위험은 "클라이언트와 공유하는 코드"에 있습니다.
  • ConfigureAwait(false) / ValueTask: 전자는 라이브러리에 거의 항상 붙여 컨텍스트 의존과 데드락을 끊습니다. 후자는 "고빈도+동기완료" 핫패스에서만 할당을 줄이되, 멀티 await 금지 등 규칙을 지켜야 합니다.
  • 취소·백프레셔: CancellationToken은 끝까지 전파(+linked token으로 타임아웃 결합)하고, SemaphoreSlim·Bounded Channel<T>로 하위 자원이 받아낼 만큼만 받습니다. Unbounded 큐는 OOM 위험으로 지양합니다.
